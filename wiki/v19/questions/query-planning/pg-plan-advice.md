## Question

Follow AGENTS.md.
In PostgreSQL 19, give a comprehensive explanation of how `pg_plan_advice` works, and explain all commits to the feature.

## Answer

### Main idea

[`pg_plan_advice`](../../../glossary.md#pg_plan_advice) is a PostgreSQL 19 [contrib](../../../glossary.md#contrib) module that writes down the key decisions of a finished query plan as a short text string, called *plan advice*, and can feed such a string back into later planning to make the [planner](../../../glossary.md#planner) repeat or change those decisions [pgplanadvice.sgml#intro](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L10-L16) [README#Plan-Advice](../../../../raw/postgres-19/contrib/pg_plan_advice/README#L6-L17). The two directions are designed to "round-trip": advice generated from a plan should apply to exactly the same parts of the query and reproduce the same decisions, as long as no DDL intervenes [README#round-trip](../../../../raw/postgres-19/contrib/pg_plan_advice/README#L29-L40).

The surprising part is how enforcement works. Advice reads like a command, such as `HASH_JOIN(d)` or `INDEX_SCAN(t t_pkey)`, but the module never builds a plan or forces one. It only takes options away. It clears bits in a per-relation strategy mask, [`pgs_mask`](../../../glossary.md#pgs_mask), and marks other indexes disabled; the documentation states the design directly: the module "works by telling the core planner what should not be done" [pgplanadvice.sgml#how-it-works](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L133-L155) [pgpa_planner.c#scan-enforcement](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1850-L1864) [pgpa_planner.c#index-disable](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1817-L1825).

Core planner code then turns each cleared bit into one of two things: it skips generating that kind of [path](../../../glossary.md#path), or it still generates the path but counts it as disabled [pathnodes.h#PGS-comment](../../../../raw/postgres-19/src/include/nodes/pathnodes.h#L38-L65). Because `add_path()` ranks a path with fewer disabled nodes ahead of any path with more, regardless of cost, the advised plan is guaranteed to win only when the planner actually generated it and every competing option was disabled [pathnode.c#add_path-disabled-first](../../../../raw/postgres-19/src/backend/optimizer/util/pathnode.c#L396-L406).

This design has four direct consequences:

1. Advice can never re-enable a strategy that an `enable_*` setting turned off, because every mask write in the module only clears bits [pgpa_planner.c#joinrel-clear-only](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L903-L935) [pgpa_planner.c#join-path-clear-only](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1138-L1150) [pgpa_planner.c#scan-enforcement](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1850-L1864).
2. Advice can never produce a plan the planner did not consider, because it only filters candidates [pgplanadvice.sgml#limitations-viable](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L807-L813).
3. Advice that asks for something impossible does not cause an error. Planning still finishes: the path with the fewest disabled nodes wins, the cheapest among them, and `EXPLAIN` marks the nodes that could not be avoided `Disabled: true` [pgplanadvice.sgml#never-fails](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L157-L194) [pathnode.c#compare_path_costs](../../../../raw/postgres-19/src/backend/optimizer/util/pathnode.c#L67-L77).
4. The feedback says `failed` only for advice that was fully matched, such as scan advice for a relation that exists [pgpa_planner.c#failed-only-if-full](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1892-L1900) [scan.out#impossible-index-advice](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/scan.out#L171-L182). Impossible advice that was never fully matched, such as an illegal join order, stays `partially matched` with no `failed` [pgplanadvice.sgml#impossible-join-order](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L166-L179) [join_order.out#partial-no-failed](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/join_order.out#L555-L571).

The other half of the module runs after planning. It walks the finished [`PlannedStmt`](../../../glossary.md#plannedstmt), renders the advice that would reproduce it, and checks which pieces of supplied advice the plan actually obeys; both results ride inside the plan for [`EXPLAIN`](../../../glossary.md#explain) to print [pgpa_planner.c#pgpa_planner_shutdown](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L300-L399) [pg_plan_advice.c#explain-hook](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L346-L410).

This page describes the pinned `REL_19_STABLE` commit `1ecc48b9bcc`, stamped `19beta4` [configure.ac:20](../../../../raw/postgres-19/configure.ac#L20). Its feature history is 22 core planner commits, 36 commits that touch `contrib/pg_plan_advice/`, 8 test, documentation, and build support commits, and 4 release-note commits; they are listed at the end of this answer, together with two adjacent commits that were checked and excluded.

### Mental model

Five ideas carry the whole mechanism.

- A **path** is one candidate way to produce a relation's rows. The planner keeps paths in each [`RelOptInfo`](../../../glossary.md#reloptinfo), which represents either one base relation or one set of joined relations [pathnodes.h#RelOptInfo-comment](../../../../raw/postgres-19/src/include/nodes/pathnodes.h#L740-L751) [pathnodes.h:803](../../../../raw/postgres-19/src/include/nodes/pathnodes.h#L803).
- A **strategy mask** (`pgs_mask`) is a 64-bit set of `PGS_*` bits, one per path-generation strategy: five scan types, seven join methods, [Append, Merge Append](../../../glossary.md#append-and-mergeappend), Gather, Gather Merge, and three "consider" switches [pathnodes.h#PGS-constants](../../../../raw/postgres-19/src/include/nodes/pathnodes.h#L66-L97).
- A **disabled node count** (`disabled_nodes`) is stored on each path. Cost functions add one when the path needs a strategy bit that the relation's mask lacks, and `add_path()` compares this count before cost [costsize.c#cost_seqscan-disabled](../../../../raw/postgres-19/src/backend/optimizer/path/costsize.c#L332-L336) [pathnode.c#compare_path_costs](../../../../raw/postgres-19/src/backend/optimizer/util/pathnode.c#L67-L77).
- A **relation identifier** such as `s#2@x` names exactly one range-table entry so that advice can point at it, even when the same alias appears twice, in a subquery, or as a partition [README#Relation-Identifiers](../../../../raw/postgres-19/contrib/pg_plan_advice/README#L51-L77).
- A **trove** is the parsed supplied advice, split into scan, join, and "rel" slices and hashed by identifier, with a feedback flag word on every entry [pgpa_trove.c#slices](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_trove.c#L32-L57) [pgpa_trove.h#pgpa_trove_entry](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_trove.h#L22-L31).

The values below matter. The "live or stored" column is the key to the plan-cache behavior later on: advice is read live while the planner runs, but everything the module produces is stored inside the plan and is only as fresh as that plan.

Two pairs of similarly named values come from different places. `default_pgs_mask` is per query and reflects only the `enable_*` settings, while `RelOptInfo.pgs_mask` is per relation and also reflects advice; this is why advice can be selective where the GUCs cannot [planner.c#default_pgs_mask](../../../../raw/postgres-19/src/backend/optimizer/plan/planner.c#L490-L535) [pathnodes.h#PGS-comment](../../../../raw/postgres-19/src/include/nodes/pathnodes.h#L25-L37). The join relation's mask applies to every way of building that join, while `JoinPathExtraData.pgs_mask` applies to one choice of outer and inner input; the module therefore puts "regardless of sides" advice on the first and order- or method-specific advice on the second [joinpath.c#extra-mask-and-hook](../../../../raw/postgres-19/src/backend/optimizer/path/joinpath.c#L155-L176) [pgpa_trove.h#lookup-types](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_trove.h#L33-L56).

### Step 1: load the module

**Input:** a session that wants advice. **Output:** GUCs, an `EXPLAIN` option, and installed [hooks](../../../glossary.md#hook).

`pg_plan_advice` is a loadable library, not an [extension](../../../glossary.md#extension): the build defines `MODULE_big` (make) or `shared_module` (meson), and there is no control file or SQL script [Makefile#MODULE_big](../../../../raw/postgres-19/contrib/pg_plan_advice/Makefile#L3-L20) [meson.build#shared_module](../../../../raw/postgres-19/contrib/pg_plan_advice/meson.build#L38-L43). The documentation offers three ways to load it [pgplanadvice.sgml#getting-started](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L31-L40):

| Method | Setting context | What applying it requires |
|---|---|---|
| [`shared_preload_libraries`](../../../glossary.md#shared_preload_libraries) | `PGC_POSTMASTER` [guc_parameters.dat:2746](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L2746) | Server restart |
| `session_preload_libraries` | `PGC_SUSET` [guc_parameters.dat:2694](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L2694) | A superuser (or a role granted the right to set it) changes it; sessions started afterwards load the module |
| `LOAD 'pg_plan_advice'` | Not a setting | Current session only; every regression script starts this way [syntax.sql:1](../../../../raw/postgres-19/contrib/pg_plan_advice/sql/syntax.sql#L1). A non-superuser may `LOAD` only a library named under `$libdir/plugins/` [utility.c#LoadStmt](../../../../raw/postgres-19/src/backend/tcop/utility.c#L845-L852) [dfmgr.c#check_restricted_library_name](../../../../raw/postgres-19/src/backend/utils/fmgr/dfmgr.c#L515-L529). The build installs this module into `$(pkglibdir)`, the directory `$libdir` names, not into `plugins/` [Makefile.shlib:427](../../../../raw/postgres-19/src/Makefile.shlib#L427) [dfmgr.c:484](../../../../raw/postgres-19/src/backend/utils/fmgr/dfmgr.c#L484). So `LOAD 'pg_plan_advice'` needs a superuser unless an administrator also places the library under `plugins/` |

A module that supplies advice loads `pg_plan_advice` as a side effect, which is a fourth way it gets loaded. `pg_stash_advice` and `test_plan_advice` look up `pg_plan_advice_add_advisor` with `load_external_function("pg_plan_advice", ...)` from their own `_PG_init()` [pg_stash_advice.c#advisor-registration](../../../../raw/postgres-19/contrib/pg_stash_advice/pg_stash_advice.c#L141-L145) [test_plan_advice.c#_PG_init](../../../../raw/postgres-19/src/test/modules/test_plan_advice/test_plan_advice.c#L41-L54). That call loads the library if it is not loaded yet, and loading a library runs its `_PG_init()` [dfmgr.c#load_external_function](../../../../raw/postgres-19/src/backend/utils/fmgr/dfmgr.c#L95-L121) [dfmgr.c#_PG_init-call](../../../../raw/postgres-19/src/backend/utils/fmgr/dfmgr.c#L295-L299).

Loading runs `_PG_init()`. It defines five `PGC_USERSET` [GUCs](../../../glossary.md#guc), reserves the `pg_plan_advice.` prefix, obtains an `EXPLAIN` extension ID, registers the `plan_advice` `EXPLAIN` option with a Boolean check handler, installs the five planner hooks, and chains onto `explain_per_plan_hook` [pg_plan_advice.c#_PG_init](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L67-L139) [pgpa_planner.c#pgpa_planner_install_hooks](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L181-L195). Every planner hook saves the previous hook value and calls it after its own work, and the `EXPLAIN` hook calls the previous one first, so the module coexists with other extensions on the same hooks [pgpa_planner.c#saved-hooks](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L90-L95) [pgpa_planner.c#setup-chain](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L291-L294) [pg_plan_advice.c#explain-chain](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L358-L360).

All five GUCs have `user` [context](../../../glossary.md#guc-context), so `SET` changes them for the session and `SET LOCAL` for the transaction, with no reload or restart [pg_plan_advice.c#gucs](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L70-L123):

| GUC | Type and default | Effect |
|---|---|---|
| `pg_plan_advice.advice` | string, unset [pg_plan_advice.c#advice-guc](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L70-L79) | Advice applied to later planning. Its check hook parses the value, so a syntax error fails the `SET` itself [pg_plan_advice.c#check-hook](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L415-L445) [syntax.out#JOIN_ORDER-empty](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/syntax.out#L36-L38) |
| `pg_plan_advice.always_explain_supplied_advice` | bool, `true` [pg_plan_advice.c#always_explain](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L81-L90) | Prints supplied-advice feedback in every `EXPLAIN`, not only `EXPLAIN (PLAN_ADVICE)` |
| `pg_plan_advice.always_store_advice_details` | bool, `false` [pg_plan_advice.c#always_store](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L92-L101) | Generates advice and feedback in every planning cycle, so plans built outside `EXPLAIN` still carry them |
| `pg_plan_advice.feedback_warnings` | bool, `false` [pg_plan_advice.c#feedback_warnings](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L103-L112) | Raises a `WARNING` when supplied advice is not applied cleanly |
| `pg_plan_advice.trace_mask` | bool, `false` [pg_plan_advice.c#trace_mask](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L114-L123) | Raises a `WARNING` each time advice changes a strategy mask; documented as a debugging aid for the module itself [pgplanadvice.sgml#trace_mask](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L764-L783) |

Long-lived module data, such as the advisor list, goes in a dedicated child [memory context](../../../glossary.md#memory-context) of `TopMemoryContext`, created on first use [pg_plan_advice.c#pg_plan_advice_get_mcxt](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L141-L154).

### Step 2: the core control surface

**Input:** the `enable_*` GUCs. **Output:** a mask on every relation, which cost functions turn into disabled-node counts.

`pg_plan_advice` depends on planner machinery that core PostgreSQL 19 added for extensions; most of it came in the core commits listed in the history below [pathnodes.h#PGS-comment](../../../../raw/postgres-19/src/include/nodes/pathnodes.h#L25-L37).

**The default mask.** `standard_planner()` starts every query with `PGS_APPEND`, `PGS_MERGE_APPEND`, `PGS_FOREIGNJOIN`, `PGS_GATHER`, and `PGS_CONSIDER_NONPARTIAL`, which have no `enable_*` setting, and then adds one or more bits for each enabled `enable_*` GUC [planner.c#default_pgs_mask](../../../../raw/postgres-19/src/backend/optimizer/plan/planner.c#L490-L535). Two mappings are easy to misread: `enable_indexscan` sets both `PGS_INDEXSCAN` and `PGS_INDEXONLYSCAN`, while `enable_indexonlyscan` sets only `PGS_CONSIDER_INDEXONLY`; and the materialized and memoized join variants need both their own GUC and the parent join GUC [planner.c#default_pgs_mask](../../../../raw/postgres-19/src/backend/optimizer/plan/planner.c#L497-L529).

**Default versus partitionwise.** By default `PGS_CONSIDER_PARTITIONWISE` is *not* in the mask, because `enable_partitionwise_join` has boot value `false` [guc_parameters.dat#enable_partitionwise_join](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L998-L1003) [planner.c#partitionwise-bit](../../../../raw/postgres-19/src/backend/optimizer/plan/planner.c#L534-L535). Without that bit, `build_joinrel_partition_info()` returns before setting up partitioning for a join relation, so no [partitionwise join](../../../glossary.md#partitionwise-join) path exists [relnode.c#build_joinrel_partition_info-gate](../../../../raw/postgres-19/src/backend/optimizer/util/relnode.c#L2211-L2216). Advice only clears bits, so advice that asks for a partitionwise join can only be satisfied in a session that turns `enable_partitionwise_join` on. The setting has `user` context, so `SET` turns it on for the session and `SET LOCAL` for the transaction, with no reload or restart [guc_parameters.dat#enable_partitionwise_join](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L998-L1003). The documentation says so, and the module's partitionwise test runs `SET enable_partitionwise_join = true` first [pgplanadvice.sgml#partitionwise](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L445-L453) [partitionwise.sql:3](../../../../raw/postgres-19/contrib/pg_plan_advice/sql/partitionwise.sql#L3).

With the default `off`, such advice is not ignored; it misfires. `PARTITIONWISE((a b))` still clears every ordinary join bit on the `{a, b}` join relation in Step 7 [pgpa_planner.c#joinrel-decisions](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L791-L795) [pgpa_planner.c#joinrel-clear-only](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L929-L932), while the gate above means no partitionwise path is built to replace them. Only disabled join paths remain, so the join comes out marked `Disabled: true`. No regression test runs partitionwise advice with the setting off, so this outcome is derived from source only (see Open Questions).

**The copies.** Every base, join, and child-join relation starts with a copy of the default mask, and an extension may edit that copy in the hook that runs right after creation [relnode.c:234](../../../../raw/postgres-19/src/backend/optimizer/util/relnode.c#L234) [relnode.c#build_simple_rel_hook](../../../../raw/postgres-19/src/backend/optimizer/util/relnode.c#L400-L410) [relnode.c:847](../../../../raw/postgres-19/src/backend/optimizer/util/relnode.c#L847) [relnode.c#joinrel_setup_hook](../../../../raw/postgres-19/src/backend/optimizer/util/relnode.c#L985-L992) [relnode.c:1054](../../../../raw/postgres-19/src/backend/optimizer/util/relnode.c#L1054) [relnode.c#child-joinrel-hook](../../../../raw/postgres-19/src/backend/optimizer/util/relnode.c#L1145-L1153). Upper relations, such as the ones grouping and sorting are planned in, copy it too, but no hook runs for them [relnode.c:1648](../../../../raw/postgres-19/src/backend/optimizer/util/relnode.c#L1648). `add_paths_to_joinrel()` copies the join relation's mask again into `JoinPathExtraData` for each candidate pair of inputs and calls `join_path_setup_hook` on that copy; its comment notes that an extension could even set bits there, which `pg_plan_advice` deliberately never does [joinpath.c#extra-mask-and-hook](../../../../raw/postgres-19/src/backend/optimizer/path/joinpath.c#L153-L179).

**Two enforcement styles.** A cleared bit either marks the generated paths disabled or skips generation, and the header comment says skipping is allowed only when it cannot leave the planner without a path [pathnodes.h#PGS-comment](../../../../raw/postgres-19/src/include/nodes/pathnodes.h#L38-L65):

| Cleared bit | What core does | Evidence |
|---|---|---|
| `PGS_SEQSCAN` | Builds the sequential scan anyway and sets `disabled_nodes = 1`, because it may be the only path | [costsize.c#cost_seqscan-disabled](../../../../raw/postgres-19/src/backend/optimizer/path/costsize.c#L279-L336) |
| `PGS_INDEXSCAN`, `PGS_INDEXONLYSCAN` | Builds the index path and marks it disabled | [costsize.c#cost_index-disabled](../../../../raw/postgres-19/src/backend/optimizer/path/costsize.c#L603-L607) |
| `PGS_CONSIDER_INDEXONLY` | Does not consider [index-only scans](../../../glossary.md#index-only-scan) at all; what would have been one becomes an index scan | [indxpath.c#check_index_only](../../../../raw/postgres-19/src/backend/optimizer/path/indxpath.c#L2234-L2236) [pathnodes.h#two-bits](../../../../raw/postgres-19/src/include/nodes/pathnodes.h#L47-L52) |
| Both `PGS_MERGEJOIN_PLAIN` and `PGS_MERGEJOIN_MATERIALIZE` | Skips [merge join](../../../glossary.md#merge-join) generation, except for a full [outer join](../../../glossary.md#outer-join), which may have no other method | [joinpath.c#mergejoin-gate](../../../../raw/postgres-19/src/backend/optimizer/path/joinpath.c#L236-L249) |
| `PGS_NESTLOOP_PLAIN` | Builds the plain [nested loop](../../../glossary.md#nested-loop-join) and counts one disabled node | [joinpath.c#plain-nestloop](../../../../raw/postgres-19/src/backend/optimizer/path/joinpath.c#L1957-L1964) [costsize.c#initial_cost_nestloop-disabled](../../../../raw/postgres-19/src/backend/optimizer/path/costsize.c#L3387-L3390) |

| `PGS_FOREIGNJOIN` | Does not ask the [foreign data wrapper](../../../glossary.md#foreign-data-wrapper) (FDW) for foreign-join paths | [joinpath.c#hash-and-foreign-gates](../../../../raw/postgres-19/src/backend/optimizer/path/joinpath.c#L357-L366) |
| `PGS_NESTLOOP_MEMOIZE` | Skips [Memoize](../../../glossary.md#memoize) paths | [joinpath.c#get_memoize_path-gate](../../../../raw/postgres-19/src/backend/optimizer/path/joinpath.c#L723-L725) |
| `PGS_GATHER` | Builds the Gather path and adds one disabled node | [costsize.c#cost_gather-disabled](../../../../raw/postgres-19/src/backend/optimizer/path/costsize.c#L453-L454) |
| `PGS_CONSIDER_PARTITIONWISE` | Skips partitionwise-join setup for that relation, which also blocks higher joins built from its children | [relnode.c#build_joinrel_partition_info-gate](../../../../raw/postgres-19/src/backend/optimizer/util/relnode.c#L2211-L2216) [pathnodes.h#partitionwise-bits](../../../../raw/postgres-19/src/include/nodes/pathnodes.h#L52-L58) |
| `PGS_CONSIDER_NONPARTIAL` | Marks every non-partial path disabled except Gather and Gather Merge, which is the only way to push the planner toward [parallelism](../../../glossary.md#parallel-query) | [pathnodes.h#nonpartial](../../../../raw/postgres-19/src/include/nodes/pathnodes.h#L60-L64) [costsize.c#cost_seqscan-disabled](../../../../raw/postgres-19/src/backend/optimizer/path/costsize.c#L311-L336) |

**Per-index disabling.** A mask bit covers every index of a relation, so core also added `IndexOptInfo.disabled`. `create_index_path()` sets `disabled_nodes = 1` for a path that uses a disabled index, after `cost_index()` has applied the mask [pathnodes.h#IndexOptInfo.disabled](../../../../raw/postgres-19/src/include/nodes/pathnodes.h#L1427-L1428) [pathnode.c#index-disabled](../../../../raw/postgres-19/src/backend/optimizer/util/pathnode.c#L1125-L1131).

**Disabled first, then cost.** `compare_path_costs()` returns early when two paths differ in `disabled_nodes`, and `add_path()` treats the count as a higher-order cost component and keeps each `pathlist` sorted by it [pathnode.c#compare_path_costs](../../../../raw/postgres-19/src/backend/optimizer/util/pathnode.c#L67-L77) [pathnode.c#add_path-disabled-first](../../../../raw/postgres-19/src/backend/optimizer/util/pathnode.c#L396-L406) [pathnode.c#add_path-sorted](../../../../raw/postgres-19/src/backend/optimizer/util/pathnode.c#L431-L436). `EXPLAIN` prints `Disabled: true` on a plan node whose own `disabled_nodes` exceeds the sum of its children's [explain.c#plan_is_disabled](../../../../raw/postgres-19/src/backend/commands/explain.c#L1251-L1336) [explain.c#Disabled-property](../../../../raw/postgres-19/src/backend/commands/explain.c#L1893-L1895). That marks every node the planner counted as disabled: a node whose strategy bit was cleared, and also an index scan on an index marked disabled [pathnode.c#index-disabled](../../../../raw/postgres-19/src/backend/optimizer/util/pathnode.c#L1125-L1131). The BRIN row in the branches table below shows the second kind: advice naming a BRIN index disables the primary-key index, and that index's scan is printed `Disabled: true` [scan.out#brin-index](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/scan.out#L361-L373).

**Private state.** The `extendplan` API lets an extension attach a pointer to `PlannerGlobal`, [`PlannerInfo`](../../../glossary.md#plannerinfo), or `RelOptInfo` by integer ID. The module stores its per-query state on `PlannerGlobal` and a per-join cache on each join `RelOptInfo` [extendplan.h#api](../../../../raw/postgres-19/src/include/optimizer/extendplan.h#L19-L70) [pgpa_planner.c#planner-state](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L281-L289) [pgpa_planner.c#join-state-cache](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L644-L671).

### Step 3: the setup hook prepares the advice

**Input:** the query, the `ExplainState` if `EXPLAIN` is planning it, and the GUCs. **Decisions:** whether to generate advice, whether to generate feedback, and what advice to enforce. **Output:** a `pgpa_planner_state` on `PlannerGlobal`, or nothing.

`standard_planner()` calls `planner_setup_hook` right after computing the default mask [planner.c#setup-hook-call](../../../../raw/postgres-19/src/backend/optimizer/plan/planner.c#L537-L540). `pgpa_planner_setup()` makes three decisions in order:

1. **Generate an advice string?** Yes if `always_store_advice_details` is on, if another module has an outstanding generation request, or if the `EXPLAIN` options include `PLAN_ADVICE` [pgpa_planner.c#generate-decision](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L212-L222). The last test needs the `ExplainState`: `pg_plan_advice_should_explain()` returns false when it is NULL [pg_plan_advice.c#should_explain](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L156-L167). Ordinary `EXPLAIN` passes it, because `standard_ExplainOneQuery()` calls `pg_plan_query(..., es)` [explain.c#pg_plan_query-es](../../../../raw/postgres-19/src/backend/commands/explain.c#L358-L359).
2. **What advice applies?** Registered advisors are consulted in registration order, and the first non-NULL string wins; only if all return NULL does the module use `pg_plan_advice.advice` [pg_plan_advice.c#get_supplied_query_advice](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L172-L197). A non-empty string is parsed again here: the GUC's check hook cannot keep its parse tree, because a check hook's private data must be a single allocation [pg_plan_advice.c#check-hook-note](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L430-L436). An advisor's string was never checked at all, so a parse failure here raises a `WARNING` and leaves no advice [pgpa_planner.c#parse-and-trove](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L232-L258). If the parse yields at least one item, `pgpa_build_trove()` organizes it [pgpa_trove.c#pgpa_build_trove](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_trove.c#L127-L221).
3. **Generate feedback?** Only when a trove exists, and then if `EXPLAIN` is running (`es != NULL`), `feedback_warnings` is on, or `always_store_advice_details` is on [pgpa_planner.c#feedback-decision](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L259-L265). Any `EXPLAIN` qualifies, with or without `PLAN_ADVICE`, which is why supplied advice shows up in plain `EXPLAIN` output by default [prepared.out#plain-explain-feedback](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/prepared.out#L36-L46).

If any of the three produced work, the hook allocates a `pgpa_planner_state` and stores it on `PlannerGlobal`. It records the current memory context, because GEQO may later call the module's hooks in a shorter-lived one [pgpa_planner.c#planner-state](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L269-L289) [pgpa_planner.c#pgpa_planner_state](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L45-L53). With no state, the later hooks find nothing to do and only pass control on, so a loaded module with no advice and no generation request does little work per query [pgpa_planner.c#no-state-base-rel](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L410-L424) [pgpa_planner.c#no-state-exit](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L636-L642).

**How the trove is organized.** Each advice item becomes one trove entry per target, filed in one of three slices by tag [pgpa_trove.c#pgpa_build_trove](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_trove.c#L127-L221):

| Slice | Tags | Read by |
|---|---|---|
| scan | `SEQ_SCAN`, `INDEX_SCAN`, `INDEX_ONLY_SCAN`, `BITMAP_HEAP_SCAN`, `TID_SCAN`, `DO_NOT_SCAN` | base-relation hook |
| join | `JOIN_ORDER` (one entry for the whole list), the six join-method tags, `FOREIGN_JOIN`, `SEMIJOIN_UNIQUE`, `SEMIJOIN_NON_UNIQUE` | join-path hook |
| rel | `PARTITIONWISE`, `GATHER`, `GATHER_MERGE`, `NO_GATHER` | base-relation, join-relation, and join-path hooks |

`PARTITIONWISE` sits in the rel slice even though it sounds like join advice, because it also applies to single relations and because its join-level effect must be set on the join relation, not per input pair [pgpa_trove.h#lookup-types](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_trove.h#L33-L56). Each slice has a hash table keyed on alias, partition name, and plan name only; a lookup then checks occurrence number and partition schema against every candidate entry [pgpa_trove.c#hash-key](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_trove.c#L59-L74) [pgpa_trove.c#pgpa_trove_slice_lookup](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_trove.c#L480-L515).

### Step 4: the advice language

**Input:** an advice string. **Output:** a list of `pgpa_advice_item`, each a tag plus a list of targets [pgpa_ast.h#pgpa_advice_item](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_ast.h#L104-L116).

Advice is whitespace-separated items of the form `TAG(target ...)` [README#syntax](../../../../raw/postgres-19/contrib/pg_plan_advice/README#L18-L27). A target is a relation identifier, an ordered sublist `( ... )`, or an unordered sublist `{ ... }` [pgpa_ast.h#target-types](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_ast.h#L19-L71). There are 20 tags [pgpa_ast.h#pgpa_advice_tag_type](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_ast.h#L73-L102).

**The lexer.** `pgpa_scanner.l` is a stripped-down copy of the core SQL scanner. It downcases unquoted identifiers, keeps double-quoted ones as written, accepts C-style comments (not nested), and reads decimal integers with optional `_` separators through `pg_strtoint32_safe()` [pgpa_scanner.l#overview](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_scanner.l#L67-L98) [pgpa_scanner.l#integer-rules](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_scanner.l#L139-L154) [pgpa_scanner.l#comments-and-quotes](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_scanner.l#L156-L214). Tags are therefore case-insensitive; `seq_scan(x@y)` and `SEQ_scan(x#2)` are both valid [syntax.out#case-variants](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/syntax.out#L50-L66). The lexer classifies each identifier by tag, and that token type selects the grammar rule [pgpa_scanner.l#tag-classification](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_scanner.l#L104-L137).

**The grammar.** Four tag classes accept different targets [pgpa_parser.y#advice_item](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_parser.y#L84-L146):

| Class | Tags | Targets allowed | Extra checks |
|---|---|---|---|
| `JOIN_ORDER` | `JOIN_ORDER` | Identifiers, nested ordered sublists, and unordered sublists of identifiers | At least one target, and no empty sublist [pgpa_parser.y#JOIN_ORDER](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_parser.y#L84-L92) [pgpa_parser.y#join_order_sublist](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_parser.y#L244-L271) |
| index | `INDEX_SCAN`, `INDEX_ONLY_SCAN` | Pairs of identifier and index name, the index optionally schema-qualified | [pgpa_parser.y#index_name](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_parser.y#L164-L175) [pgpa_parser.y#index_target_list](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_parser.y#L234-L242) |
| simple | `SEQ_SCAN`, `TID_SCAN`, `BITMAP_HEAP_SCAN`, `NO_GATHER`, `DO_NOT_SCAN` | Identifiers only; `SEQ_SCAN((x))` is a syntax error | [pgpa_parser.y#simple](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_parser.y#L104-L120) [syntax.out#no-sublists](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/syntax.out#L134-L145) |
| generic | the six join-method tags, `FOREIGN_JOIN`, `SEMIJOIN_UNIQUE`, `SEMIJOIN_NON_UNIQUE`, `PARTITIONWISE`, `GATHER`, `GATHER_MERGE` | Identifiers and one level of ordered sublist | `FOREIGN_JOIN` targets must each be a sublist of two or more identifiers [pgpa_parser.y#generic](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_parser.y#L121-L145) [pgpa_parser.y#generic_sublist](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_parser.y#L218-L232) |

Any identifier position also accepts a tag word, so a table aliased `hash_join` can still be named [pgpa_parser.y#identifier](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_parser.y#L192-L197) [syntax.sql#tag-words-as-names](../../../../raw/postgres-19/contrib/pg_plan_advice/sql/syntax.sql#L83-L100). Parse errors report the first problem with the nearby token, and `pgpa_parse()` returns NULL plus the message [pgpa_scanner.l#pgpa_yyerror](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_scanner.l#L228-L244) [pgpa_parser.y#pgpa_parse](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_parser.y#L281-L307).

**What each tag family asks for.**

| Family | Meaning | Evidence |
|---|---|---|
| Scan | Scan this relation with this method. Index tags also name the index. `TID_SCAN` covers [TID](../../../glossary.md#tid) and TID range scans. `DO_NOT_SCAN` says the relation must not appear in the plan, which only makes sense when the planner weighs copied alternatives | [pgplanadvice.sgml#scan-method](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L272-L309) [README#Scan-Advice](../../../../raw/postgres-19/contrib/pg_plan_advice/README#L100-L115) |
| `JOIN_ORDER` | `JOIN_ORDER(a b c)`: `a` drives and is joined to `b`, then `c`; remaining tables may follow in any order. `( ... )` describes a non-outer-deep inner join product; `{ ... }` joins its members without fixing sides or order | [pgplanadvice.sgml#join-order](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L333-L386) [README#Join-Order-Advice](../../../../raw/postgres-19/contrib/pg_plan_advice/README#L120-L147) |
| Join method | Each target is the relation, or set of relations, on the *inner* side of a join using that method; `HASH_JOIN(a b)` asks for two hash joins, `HASH_JOIN((a b))` for one with `a` and `b` together on the inner side | [pgplanadvice.sgml#join-method](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L404-L431) |
| `FOREIGN_JOIN` | Push the join of the listed foreign tables to the remote server as one Foreign Scan; it names both sides, not just the inner one | [pgplanadvice.sgml#FOREIGN_JOIN](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L289-L298) [pgpa_planner.c#opaque-join](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1458-L1470) |
| Semijoin | `SEMIJOIN_UNIQUE` asks for "make the nullable side unique, then inner join"; `SEMIJOIN_NON_UNIQUE` asks for a direct [semijoin](../../../glossary.md#semi-join-and-anti-join). The target is the nullable side, which is not always the inner side; the README says "inner side" (see Open Questions) | [pgplanadvice.sgml#semijoin](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L468-L476) [pgpa_planner.c#semijoin-sides](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1523-L1535) [README#Semijoin-Uniqueness](../../../../raw/postgres-19/contrib/pg_plan_advice/README#L205-L210) |
| `PARTITIONWISE` | A single target must not take part in any partitionwise join; a sublist must be joined partitionwise as exactly that set | [pgplanadvice.sgml#partitionwise](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L445-L453) [README#Partitionwise](../../../../raw/postgres-19/contrib/pg_plan_advice/README#L212-L224) |
| Parallel | `GATHER` or `GATHER_MERGE` puts that node over exactly the target relation or set; `NO_GATHER` keeps a relation out from under any Gather within its own subquery level | [pgplanadvice.sgml#parallel](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L492-L543) |

Two design rules shape the language. Nothing may be inferred from missing advice, so deleting any piece of generated advice can only give the planner more freedom [README#Advice-Completeness](../../../../raw/postgres-19/contrib/pg_plan_advice/README#L189-L200). And join-method advice implies join-order constraints, because a relation named on the inner side cannot be the driving table and a named set must be joined internally before anything else joins it [README#method-implies-order](../../../../raw/postgres-19/contrib/pg_plan_advice/README#L174-L177) [README#Implicit-Join-Order-Constraints](../../../../raw/postgres-19/contrib/pg_plan_advice/README#L235-L246). Keeping order and method in separate tags lets a user delete the `JOIN_ORDER` item and still force the methods [README#separate-tags](../../../../raw/postgres-19/contrib/pg_plan_advice/README#L179-L187).

### Step 5: relation identifiers

**Input:** a [range table](../../../glossary.md#range-table) entry. **Output:** a five-field `pgpa_identifier` and its text form [pgpa_identifier.h#pgpa_identifier](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_identifier.h#L19-L26).

The text form is `alias_name#occurrence_number/partition_schema.partition_name@plan_name`. Every component except the alias is omitted when not needed, together with its punctuation [README#Relation-Identifiers](../../../../raw/postgres-19/contrib/pg_plan_advice/README#L66-L77) [pgpa_identifier.c#pgpa_identifier_string](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_identifier.c#L78-L100). Each component answers one source of ambiguity:

| Component | Why it is needed | How it is computed |
|---|---|---|
| Alias | Starting point; for a partition it is the alias of the topmost parent that is still a table | `eref->aliasname` of the top parent found through `AppendRelInfo` [pgpa_identifier.c#top-parent](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_identifier.c#L119-L146) |
| `#occurrence` | The same alias twice in one subquery | Counts earlier entries with the same alias in that subquery's range table, skipping join entries and partition children; printed only when greater than 1 [pgpa_identifier.c#occurrence](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_identifier.c#L148-L184) [pgpa_identifier.c#print-occurrence](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_identifier.c#L86-L88) |
| `/schema.partition` | Which child of a partitioned table | The child's own schema and name, always both [pgpa_identifier.c#partition](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_identifier.c#L186-L191) [pgpa_parser.y#opt_partition](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_parser.y#L199-L209) |
| `@plan_name` | The same alias in different subqueries | The `PlannerInfo` plan name; omitted at the top level [pgpa_identifier.c:198](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_identifier.c#L198) [pathnodes.h#plan_name](../../../../raw/postgres-19/src/include/nodes/pathnodes.h#L320-L333). Core picks it with `choose_plan_name()` before it calls `subquery_planner()`, so it is known while the subquery is planned [subselect.c#make_subplan-name](../../../../raw/postgres-19/src/backend/optimizer/plan/subselect.c#L225-L228) [allpaths.c#subquery-plan-name](../../../../raw/postgres-19/src/backend/optimizer/path/allpaths.c#L2827-L2830) |

Occurrence numbers are counted per subquery, not over the final flattened range table, because the identifier must be computable while that subquery is planned [pgpa_identifier.c#reconstructible](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_identifier.c#L34-L42). The code also uses `rt_fetch()` rather than `planner_rt_fetch()`, because join removal and self-join elimination delete entries from the planner's arrays and would shift the numbering [pgpa_identifier.c#rt_fetch-note](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_identifier.c#L44-L47). Join entries never get identifiers; advice names a join by its members [pgpa_identifier.c#no-join-identifiers](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_identifier.c#L6-L13).

The module computes identifiers twice per cycle. During planning, `pgpa_compute_identifier_by_rti()` works from the current subquery's range table and caches the result per base relation [pgpa_identifier.c#pgpa_compute_identifier_by_rti](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_identifier.c#L108-L199) [pgpa_planner.c#pgpa_compute_rt_identifier](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L2055-L2080). After planning, `pgpa_create_identifiers_for_planned_stmt()` rebuilds them from the flattened range table, using `PlannedStmt.subrtinfos` to know which subquery each slice came from [pgpa_identifier.c#pgpa_create_identifiers_for_planned_stmt](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_identifier.c#L237-L338) [plannodes.h#SubPlanRTInfo](../../../../raw/postgres-19/src/include/nodes/plannodes.h#L1843-L1855). In assertion-enabled builds the shutdown hook checks that both methods agree [pgpa_planner.c#pgpa_validate_rt_identifiers](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L2140-L2180).

**Matching rules.** A target matches an identifier when alias and occurrence number are equal and the partition schema, partition name, and plan name are equal or absent on both sides [pgpa_ast.c#pgpa_identifier_matches_target](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_ast.c#L234-L277). An omitted occurrence number means 1 [pgpa_parser.y#opt_ri_occurrence](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_parser.y#L177-L190). So `SEQ_SCAN(s)` does not match an `s` inside subquery `x`; only `SEQ_SCAN(s@x)` does [scan.out#subquery-names](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/scan.out#L687-L742). When the hooks compare a set of identifiers with a target, `pgpa_identifiers_match_target()` classifies the relation between the two sets as equal, keys-are-subset, targets-are-subset, intersecting, or disjoint, and the enforcement rules in Steps 6 to 8 branch on that result [pgpa_ast.h#pgpa_itm_type](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_ast.h#L118-L148) [pgpa_ast.c#pgpa_identifiers_match_target](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_ast.c#L279-L328).

**Which plan name a relation gets depends on what the planner does to the query, not only on how it is written.** A subquery that the planner pulls up into its parent becomes part of the parent level and takes the parent's plan name, or none at the top level [pgplanadvice.sgml#plan-names](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L232-L243). This is why the module's tests write `OFFSET 0` inside `(SELECT ... OFFSET 0) x`: pull-up refuses a subquery with an `OFFSET` [prepjointree.c#is_simple_subquery-limits](../../../../raw/postgres-19/src/backend/optimizer/prep/prepjointree.c#L1983-L2005). The subquery is then planned separately under a plan name chosen from its alias, `x` [allpaths.c#subquery-plan-name](../../../../raw/postgres-19/src/backend/optimizer/path/allpaths.c#L2827-L2830). An unaliased subquery in `FROM` has the parser-assigned alias `unnamed_subquery`, so its relations are named `@unnamed_subquery` [parse_relation.c:1697](../../../../raw/postgres-19/src/backend/parser/parse_relation.c#L1697) [scan.out#unnamed-subquery](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/scan.out#L703-L714). Set-operation branches get generated names with the `setop` prefix [prepunion.c:251](../../../../raw/postgres-19/src/backend/optimizer/prep/prepunion.c#L251). Generated advice is built from the plan names the planner actually chose [pgpa_identifier.c#pgpa_create_identifiers_for_planned_stmt](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_identifier.c#L237-L338), while hand-written advice has to anticipate them.

### Step 6: scan advice on base relations

**Input:** a new base relation and its scan and rel advice. **Calculation:** the bits to keep. **Output:** a narrower `rel->pgs_mask`, and possibly disabled indexes.

`build_simple_rel()` calls `build_simple_rel_hook` after filling in the relation's catalog information and default mask [relnode.c#build_simple_rel_hook](../../../../raw/postgres-19/src/backend/optimizer/util/relnode.c#L400-L410). `pgpa_build_simple_rel()` records the identifier, looks up scan and rel advice for it, and applies whatever it finds [pgpa_planner.c#pgpa_build_simple_rel](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L404-L446).

`pgpa_planner_apply_scan_advice()` works on a fixed set of bits, `all_scan_mask` = the five scan bits + `PGS_APPEND` + `PGS_MERGE_APPEND` + `PGS_CONSIDER_INDEXONLY`. It turns the advice into the subset to keep and clears the rest with `rel->pgs_mask &= ~(all_scan_mask & ~scan_type)` [pgpa_planner.c#all_scan_mask](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1633-L1634) [pgpa_planner.c#scan-enforcement](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1850-L1856):

| Advice | Bits kept from `all_scan_mask` | Why | Evidence |
|---|---|---|---|
| `SEQ_SCAN` | `PGS_SEQSCAN` | | [pgpa_planner.c#tag-map](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1678-L1679) |
| `INDEX_SCAN` | `PGS_INDEXSCAN` | Clearing `PGS_CONSIDER_INDEXONLY` downgrades would-be index-only scans to index scans | [pgpa_planner.c#tag-map](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1676-L1677) |
| `INDEX_ONLY_SCAN` | `PGS_INDEXONLYSCAN` + `PGS_CONSIDER_INDEXONLY` | Index-only paths are not even considered without the second bit | [pgpa_planner.c#tag-map](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1674-L1675) |
| `BITMAP_HEAP_SCAN` | `PGS_BITMAPSCAN` + `PGS_CONSIDER_INDEXONLY` | Clearing the second bit can suppress [bitmap scans](../../../glossary.md#bitmap-scan). `build_index_paths()` builds an index path when an index-only scan is possible, even with no useful clause or ordering, and `get_index_paths()` also hands such paths to bitmap planning when the index supports bitmap scans. The module's comment explains this, but names `build_index_scankeys()`, a foreign-key trigger function, instead (see Open Questions) | [indxpath.c#index-path-reasons](../../../../raw/postgres-19/src/backend/optimizer/path/indxpath.c#L959-L966) [indxpath.c#get_index_paths-bitmap](../../../../raw/postgres-19/src/backend/optimizer/path/indxpath.c#L740-L756) [pgpa_planner.c#bitmap-comment](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1658-L1673) [ri_triggers.c#build_index_scankeys](../../../../raw/postgres-19/src/backend/utils/adt/ri_triggers.c#L3266-L3276) |
| `TID_SCAN` | `PGS_TIDSCAN` | | [pgpa_planner.c#tag-map](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1680-L1681) |
| `DO_NOT_SCAN` | nothing | Every scan of the relation becomes disabled | [pgpa_planner.c#tag-map](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1656-L1657) |
| `PARTITIONWISE` with a single target | `PGS_APPEND` + `PGS_MERGE_APPEND` | For a partitioned table, "scan it as an Append of its partitions" is the scan type | [pgpa_planner.c#partitionwise-single](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1722-L1740) |

`all_scan_mask` includes `PGS_APPEND` and `PGS_MERGE_APPEND`, and `cost_append()` disables an Append path whose relation lacks `PGS_APPEND`. Scan-method advice that named a partitioned parent itself would therefore disable the parent's Append paths; no regression test shows that case [pgpa_planner.c#all_scan_mask](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1633-L1634) [costsize.c#cost_append-disabled](../../../../raw/postgres-19/src/backend/optimizer/path/costsize.c#L2315-L2321). Generated advice instead names each partition (`pt1/public.pt1a`) for its scan method [partitionwise.out#generated](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/partitionwise.out#L109-L121). When a partitioned table is scanned as an Append of its partitions, generated advice also lists the parent in a single-target `PARTITIONWISE` item, the one scan-level tag that keeps those bits [partitionwise.out#single-target-partitionwise](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/partitionwise.out#L465-L471) [partitionwise.out#single-target-partitionwise-2](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/partitionwise.out#L486-L489). For a partitionwise join it emits the sublist form instead, such as `PARTITIONWISE((pt1 pt2 pt3))`, which this scan-level code skips because the target names more than one relation [partitionwise.out#generated](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/partitionwise.out#L109-L121) [pgpa_planner.c#partitionwise-single](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1722-L1740).

Gather advice on a single relation uses a second, independent set of bits: `PGS_GATHER` + `PGS_GATHER_MERGE` + `PGS_CONSIDER_NONPARTIAL`. `GATHER` keeps `PGS_GATHER`; `GATHER_MERGE` keeps `PGS_GATHER_MERGE`; `NO_GATHER`, or `GATHER` naming a set that includes this relation, keeps `PGS_CONSIDER_NONPARTIAL`, meaning "no Gather at this level" [pgpa_planner.c#rel-gather](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1742-L1766) [pgpa_planner.c#gather-enforcement](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1857-L1864).

**Index advice.** If the surviving advice is `INDEX_SCAN` or `INDEX_ONLY_SCAN`, the module searches the relation's index list for the named index; a schema in the advice must match, but a missing schema matches any [pgpa_planner.c#index-match](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1785-L1806). Two outcomes follow:

- **Found:** every other index on the relation gets `disabled = true`, so only the named index can produce an enabled index path [pgpa_planner.c#index-disable](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1817-L1825).
- **Not found:** the module does not force the scan type at all and marks the advice `inapplicable` [pgpa_planner.c#index-not-found](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1808-L1816). The `scan` test shows this for a nonexistent index and for the wrong schema: the plan keeps its default index scan and the feedback reads `matched, inapplicable, failed` [scan.out#wrong-schema](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/scan.out#L454-L466) [scan.out#bogus-index](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/scan.out#L527-L538).

**Conflicts.** If two pieces of scan advice for the relation ask for different scan types, or the same type with index targets that are not textually identical, all are marked `conflicting` and none is enforced; repeating identical advice is fine [pgpa_planner.c#scan-conflict](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1683-L1706) [scan.out#repeat-and-conflict](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/scan.out#L468-L496). Gather advice has its own conflict flag and is skipped independently [pgpa_planner.c#scan-flags](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1828-L1864).

With `trace_mask` on, a changed mask is reported as `strategy mask for RTI n changed from 0x... to 0x...`, with the subquery name when there is one [pgpa_planner.c#trace-base](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L448-L461).

### Step 7: Gather and partitionwise advice on join relations

**Input:** a new join relation and its rel advice. **Output:** a narrower `joinrel->pgs_mask`, which applies to every way of building this join.

`build_join_rel()` calls `joinrel_setup_hook` after deciding parallel safety and before setting up partitioning [relnode.c#joinrel_setup_hook](../../../../raw/postgres-19/src/backend/optimizer/util/relnode.c#L985-L996). `pgpa_joinrel_setup()` reads only the rel slice, because the outer and inner relations passed to it are just whichever pair happened to create the join relation [pgpa_planner.c#pgpa_joinrel_setup](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L470-L497). The per-join lookup is cached on the join relation, and an empty result is cached too, as a negative entry [pgpa_planner.c#pgpa_get_join_state](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L644-L739).

For each `GATHER`, `GATHER_MERGE`, or `PARTITIONWISE` entry, the decision depends on how the join's members compare with the target set [pgpa_planner.c#joinrel-decisions](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L760-L881):

```text
target set vs. this join relation's members
 |
 |-- NO_GATHER (always a single relation inside this join)
 |      -> keep only PGS_CONSIDER_NONPARTIAL: no Gather at this level
 |-- equal
 |      PARTITIONWISE -> outcome = do partitionwise here
 |      GATHER        -> keep only PGS_GATHER
 |      GATHER_MERGE  -> keep only PGS_GATHER_MERGE
 |-- not equal (subset, superset, or overlap)
        PARTITIONWISE -> outcome = no partitionwise here;
                         also no Gather here unless the target is a strict subset
        GATHER / GATHER_MERGE -> no Gather here;
                         also no partitionwise here unless this join is a strict subset
```

The cross-rules encode logical incompatibility: `PARTITIONWISE((a b c))` cannot coexist with a Gather over only `{a, b}`, but can with a Gather over `{a, b, c, d}` [pgpa_planner.c#cross-rules](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L806-L839).

Enforcement then clears bits, and skips a topic whose advice conflicted [pgpa_planner.c#joinrel-enforcement](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L903-L935):

- **Gather:** clear the members of `PGS_GATHER` + `PGS_GATHER_MERGE` + `PGS_CONSIDER_NONPARTIAL` that the advice did not keep.
- **Induce partitionwise:** clear `PGS_JOIN_ANY`, so every ordinary join path is disabled or skipped. The source comment says an Append or Merge Append of per-partition joins will then "hopefully" be chosen [pgpa_planner.c#partitionwise-comment](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L917-L922). Such a path exists only if the planner can set up a partitionwise join for this relation: `enable_partitionwise_join` must be on, both inputs must be partitioned with the same partition scheme, and the join must have an equi-join on the partition keys [relnode.c#build_joinrel_partition_info-gate](../../../../raw/postgres-19/src/backend/optimizer/util/relnode.c#L2211-L2216) [relnode.c#partitionwise-conditions](../../../../raw/postgres-19/src/backend/optimizer/util/relnode.c#L2218-L2235). Otherwise only disabled paths remain.
- **Prevent partitionwise:** clear only `PGS_APPEND` and `PGS_MERGE_APPEND`.

`PGS_CONSIDER_PARTITIONWISE` is the one bit the module never touches. Clearing it would stop a *higher* join relation from building partitionwise paths out of this level's child paths, even when the advice wants partitionwise there; disabling Append at this level suppresses only this level [pgpa_planner.c#partitionwise-comment](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L917-L928) [pathnodes.h#partitionwise-bits](../../../../raw/postgres-19/src/include/nodes/pathnodes.h#L52-L58).

### Step 8: join order, join method, and semijoin advice on join paths

**Input:** one proposed (outer, inner, join type) for a join relation, and the join slice plus `PARTITIONWISE` entries. **Decisions:** permit or deny this pair; restrict the method or not. **Output:** a narrower `extra->pgs_mask` for this attempt only.

`add_paths_to_joinrel()` calls `join_path_setup_hook` once per input pair and join type, before any join path is generated [joinpath.c#extra-mask-and-hook](../../../../raw/postgres-19/src/backend/optimizer/path/joinpath.c#L153-L179). `pgpa_join_path_setup()` first notes semijoin make-unique candidates: when the join type is `JOIN_UNIQUE_OUTER` or `JOIN_UNIQUE_INNER` and advice or feedback is being generated, it records the unique side's relids, minus join RTEs, in the long-lived context [pgpa_planner.c#sj_unique_rels](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L537-L579). The walker later needs this list to tell whether the planner had a semijoin choice to make [pgpa_planner.h#sj_unique_rels](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.h#L55-L69).

Then `pgpa_planner_apply_join_path_advice()` classifies every relevant entry [pgpa_planner.c#pgpa_planner_apply_join_path_advice](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L941-L1103):

```text
for this (outer, inner, jointype):
 |
 |-- PARTITIONWISE((set)): set fully inside outer or inner?  no -> deny order
 |-- JOIN_ORDER(list):
 |     find the innermost ordered sublist containing all of this join's members;
 |     an unordered sublist there -> indifferent
 |     shortest list prefix == outer?
 |       prefix is the whole list -> permit at top level; deny inside a sublist
 |       otherwise, next item == inner -> permit, else deny
 |     outer is not built from a prefix -> deny
 |-- join method (inner-side semantics):
 |     inner == target            -> permit + restrict to that method
 |     inner or outer superset    -> permit (that join already happened)
 |     outer == target            -> deny (sides reversed)
 |     whole join inside target   -> permit (still building toward it)
 |     otherwise                  -> deny (target split with outsiders mixed in)
 |-- FOREIGN_JOIN (both sides named):
 |     join == target -> permit + restrict; subset or superset -> permit; else deny
 |-- SEMIJOIN_*: nullable side == target?
 |     yes and join type is unique-ified or semi -> permit + check tag vs join type
 |     yes but join type is neither -> inapplicable
 |     tag disagrees with join type -> deny (semijoin choice)
 |     otherwise as join method -> permit or deny
 v
enforce (clear-only, per topic, skipped on conflict):
  order denied by any branch above,
    and no JOIN_ORDER entry permits it -> clear PGS_JOIN_ANY
  restricted method and no conflict    -> clear PGS_JOIN_ANY except that method
  semijoin denied and no permit        -> clear PGS_JOIN_ANY
```

Key: [pgpa_planner.c#partitionwise-recheck](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L956-L997), [pgpa_planner.c#pgpa_join_order_permits_join](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1184-L1348), [pgpa_planner.c#pgpa_join_method_permits_join](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1350-L1456), [pgpa_planner.c#pgpa_opaque_join_permits_join](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1458-L1521), [pgpa_planner.c#pgpa_semijoin_permits_join](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1523-L1621), [pgpa_planner.c#semijoin-classification](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1053-L1102), [pgpa_planner.c#join-path-enforcement](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1138-L1150).

The walkthrough of each branch:

**JOIN_ORDER.** The check runs in four stages, each of which can end it:

1. **Zoom in.** The module first finds the innermost ordered sublist that contains every member of the proposed join. For `JOIN_ORDER(t1 t2 (t3 t4 t5))`, a join of `t3` and `t4` is judged against `(t3 t4 t5)` [pgpa_planner.c#innermost-sublist](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1214-L1256).
2. **Unordered sublists.** Reaching an unordered sublist returns "indifferent", so braces place no constraint on joins among their members [pgpa_planner.c#indifferent](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1249-L1253).
3. **Prefix search.** Next it grows a prefix of the list until the prefix equals the outer input. If the prefix ever contains something not in the outer input, the order is denied [pgpa_planner.c#prefix-search](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1258-L1290).
4. **Next item or whole list.** If the prefix stops short of the whole list, the next item must equal the inner input exactly [pgpa_planner.c#next-item](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1292-L1323). If the outer input already contains the whole list, a top-level list permits the join. That is why a short `JOIN_ORDER(d2)` merely fixes the driving table and lets the planner order the rest. A sublist denies it instead, so no extra table may be added inside parentheses [pgpa_planner.c#whole-list](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1325-L1347) [join_order.out#prefix-advice](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/join_order.out#L399-L419).

Every evaluated entry is at least partially matched. It becomes fully matched when the final join of the top-level list is seen [pgpa_planner.c#jo-flags](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1211-L1212) [pgpa_planner.c#jo-full-match](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1312-L1320).

**Join method.** The target names the inner side. An exact inner match permits the join and restricts it to the advised method; a reversed match, with the target on the outer side, is denied because its paths might otherwise win on cost [pgpa_planner.c#pgpa_join_method_permits_join](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1350-L1415). A join that splits a multi-relation target across both sides while also mixing in an outside relation is denied, because it could never put exactly the target on the inner side [pgpa_planner.c#split-target](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1424-L1455). The tag maps to exactly one mask bit, such as `HASH_JOIN` to `PGS_HASHJOIN` or `NESTED_LOOP_MEMOIZE` to `PGS_NESTLOOP_MEMOIZE` [pgpa_planner.c#pgpa_join_strategy_mask_from_advice_tag](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1153-L1182).

**FOREIGN_JOIN.** Foreign joins are opaque: PostgreSQL cannot see the remote join order or method, so the target is the whole join. Subsets must stay permitted, because a foreign join path for `{x, y, z}` is built from foreign paths for its sub-joins [pgpa_planner.c#pgpa_opaque_join_permits_join](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1458-L1521).

**Semijoin.** The planner's options for a semijoin are a direct implementation, or making one side unique and then performing an inner join [README#Semijoin-Uniqueness](../../../../raw/postgres-19/contrib/pg_plan_advice/README#L205-L207). The join-path hook sees these as the join types `JOIN_SEMI` or `JOIN_RIGHT_SEMI`, and `JOIN_UNIQUE_OUTER` or `JOIN_UNIQUE_INNER` [pgpa_planner.c#semijoin-classification](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1080-L1086). The advice target is the nullable side, which is the outer input for `JOIN_UNIQUE_OUTER` and `JOIN_RIGHT_SEMI` and the inner input otherwise [pgpa_planner.c#nullable-side](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1060-L1062) [pgpa_planner.c#semijoin-sides](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1523-L1591). When the target matches, the tag must agree with the join type, or this attempt is denied; advice applied to a join that is neither kind is flagged `inapplicable` [pgpa_planner.c#semijoin-classification](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1071-L1100) [semijoin.out#non-semijoin](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/semijoin.out#L355-L369).

**Conflicts and enforcement.** Three situations mark the entries involved `conflicting`, and that topic is then not enforced [pgpa_planner.c#join-path-conflicts](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1105-L1136):

- A `JOIN_ORDER` entry permits the attempt while some advice denies its order. The denial can come from `JOIN_ORDER` itself, from a `PARTITIONWISE` set, or from the order that join-method, `FOREIGN_JOIN`, or semijoin advice implies, because all of these feed the same deny set [pgpa_planner.c#implied-order-denials](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1041-L1070). The documentation describes the same case [pgplanadvice.sgml#conflicting](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L642-L652).
- Two join-method entries restrict the attempt to different methods.
- Semijoin advice says both yes and no.

Enforcement is again clear-only, per topic [pgpa_planner.c#join-path-enforcement](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1138-L1150). Clearing `PGS_JOIN_ANY` does not remove the pair from consideration; it disables or skips all of its join paths, so they lose to any enabled path for the same join relation [joinpath.c#hook-comment](../../../../raw/postgres-19/src/backend/optimizer/path/joinpath.c#L163-L167).

### Step 9: path selection and impossible advice

**Input:** each relation's paths, now carrying disabled-node counts. **Output:** the cheapest path with the fewest disabled nodes.

The planner itself chooses; the module only changed the counts. `add_path()` keeps a path with fewer disabled nodes over any path with more, then compares cost [pathnode.c#add_path-disabled-first](../../../../raw/postgres-19/src/backend/optimizer/util/pathnode.c#L396-L406). Because planning never fails for lack of an enabled path, advice the planner cannot satisfy still yields a plan: the best of the disabled candidates [pgplanadvice.sgml#never-fails](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L157-L194).

Two common causes of unsatisfiable advice are documented. The plan may be semantically invalid, such as a join order that a `FULL JOIN` forbids, or the planner may have rejected it before costing, such as an index on a query with no usable condition or ordering [pgplanadvice.sgml#how-it-works](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L140-L155). The second case is visible in core: an index path is generated only when there are index clauses, useful sort order, a useful partial-index predicate, or a possible index-only scan [indxpath.c#index-path-conditions](../../../../raw/postgres-19/src/backend/optimizer/path/indxpath.c#L959-L966). The `join_order` test shows the first case: `JOIN_ORDER(f d1 d2)` cannot be honored because `f` must join `d2` first, so two nodes come out disabled [join_order.out#illegal-order](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/join_order.out#L546-L578).

**Join advice under GEQO is probabilistic.** When the number of `FROM` items reaches `geqo_threshold` (boot value 12, with `geqo` on by default), the planner uses the [genetic optimizer](../../../glossary.md#geqo) instead of the exhaustive [join search](../../../glossary.md#join-order-search) [allpaths.c#geqo-call](../../../../raw/postgres-19/src/backend/optimizer/path/allpaths.c#L3907-L3910) [guc_parameters.dat#geqo](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L1123-L1128) [guc_parameters.dat#geqo_threshold](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L1178-L1182).

GEQO evaluates only a random pool of join orders, so an advice-compatible order may never be tried. The result is then a non-compliant plan with disabled parts [pgplanadvice.sgml#GEQO](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L815-L829). For join advice that constrains the plan strongly, the documentation therefore suggests turning GEQO off (same lines). `geqo` has `user` context, so `SET geqo = off` changes it for the session and `SET LOCAL` for the transaction, with no reload or restart [guc_parameters.dat#geqo](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L1123-L1128).

At the pin, GEQO at least ranks join orders the same way `add_path()` ranks paths: fewer disabled nodes first, then cost [geqo_gene.h#Fitness](../../../../raw/postgres-19/src/include/optimizer/geqo_gene.h#L38-L70) [geqo_eval.c#fitness](../../../../raw/postgres-19/src/backend/optimizer/geqo/geqo_eval.c#L111-L122) [geqo_pool.c#compare](../../../../raw/postgres-19/src/backend/optimizer/geqo/geqo_pool.c#L138-L149). Scan advice is unaffected, because it does not constrain join order [pgplanadvice.sgml#GEQO](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L827-L828).

### Step 10: the shutdown hook generates advice and feedback

**Input:** the finished `PlannedStmt`. **Output:** a `pg_plan_advice` entry in `PlannedStmt.extension_state` holding `advice_string`, `feedback`, or both.

After `create_plan()` and [`set_plan_references()`](../../../glossary.md#set_plan_references) finish, `standard_planner()` calls `planner_shutdown_hook` [planner.c#create_plan-and-setrefs](../../../../raw/postgres-19/src/backend/optimizer/plan/planner.c#L550-L663) [planner.c#shutdown-hook-call](../../../../raw/postgres-19/src/backend/optimizer/plan/planner.c#L734-L736). By then setrefs has flattened all range tables into one, removed trivial nodes, and renumbered relation indexes, so the module cannot simply read the plan tree. Core therefore keeps three records that let code outside the planner, this module included, map the final plan back to planning [plannodes.h#subrtinfos](../../../../raw/postgres-19/src/include/nodes/plannodes.h#L131-L132) [plannodes.h#elidedNodes](../../../../raw/postgres-19/src/include/nodes/plannodes.h#L155-L156):

| Record | What it preserves | Evidence |
|---|---|---|
| `SubPlanRTInfo` list | Which slice of the flat range table came from which subquery, or that a subquery was only partly copied (`dummy`) | [plannodes.h#SubPlanRTInfo](../../../../raw/postgres-19/src/include/nodes/plannodes.h#L1843-L1855) |
| [`ElidedNode`](../../../glossary.md#elidednode) list | The type and relation set of each trivial `SubqueryScan`, `Append`, or `MergeAppend` removed by setrefs, keyed by the surviving child's plan node ID, and for an Append the `child_append_relid_sets` it carried | [plannodes.h#ElidedNode](../../../../raw/postgres-19/src/include/nodes/plannodes.h#L1857-L1876) [setrefs.c#elided-append](../../../../raw/postgres-19/src/backend/optimizer/plan/setrefs.c#L1908-L1926) |
| `child_append_relid_sets` on Append and Merge Append | The relation sets of child Appends that were pulled up into this one, so a partitionwise child scan is not lost; setrefs offsets them like other RTIs | [plannodes.h#Append-child-sets](../../../../raw/postgres-19/src/include/nodes/plannodes.h#L400-L404) [setrefs.c#offset-child-sets](../../../../raw/postgres-19/src/backend/optimizer/plan/setrefs.c#L1935-L1937) [setrefs.c#offset_relid_set_list](../../../../raw/postgres-19/src/backend/optimizer/plan/setrefs.c#L2088-L2104) |

`pgpa_planner_shutdown()` proceeds in four parts [pgpa_planner.c#pgpa_planner_shutdown](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L300-L399):

1. **Align subqueries.** It looks up each planned subquery's offset in the flat range table. A subquery with no offset loses its semijoin candidate list, because those relids cannot be mapped [pgpa_planner.c#pgpa_compute_rt_offsets](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L2082-L2138).
2. **Walk the plan.** `pgpa_plan_walker()` traverses the main tree and every subplan [pgpa_walker.c#main-walk](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_walker.c#L92-L102). It collects:
   - **Scans**, classified by strategy. Subquery, VALUES, single-table foreign, and proven-empty scans are "ordinary" and produce no advice, because no planner choice is involved [pgpa_scan.h#strategies](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_scan.h#L26-L68). An Append over table partitions is a partitionwise scan, and each pulled-up child Append set is classified separately [pgpa_scan.c#append](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_scan.c#L155-L183) [pgpa_scan.c#child-sets](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_scan.c#L194-L213). A [Materialize node](../../../glossary.md#materialize-node) protecting a non-repeatable `TABLESAMPLE` scan counts as part of the scan [pgpa_walker.c#pgpa_is_scan_level_materialize](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_walker.c#L615-L641).
   - **Unrolled joins.** An outer-deep tree `((A⋈B)⋈C)⋈D` becomes outer `A`, inners `B C D`; other shapes nest [pgpa_join.h#pgpa_unrolled_join](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_join.h#L64-L84). The decomposer looks through Hash, Sort and Incremental Sort, Materialize, Memoize, Gather and Gather Merge, Unique, Agg, and Result nodes that have a child, recording Materialize and Memoize as part of the method [pgpa_join.c#pgpa_decompose_join](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_join.c#L338-L478) [pgpa_join.c#descend-helpers](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_join.c#L528-L633) [pgpa_join.h#pgpa_join_strategy](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_join.h#L21-L38). It descends through any Agg, but only a simple (`AGGSPLIT_SIMPLE`) one is taken to make that side unique; other Agg nodes are assumed to finish an eager or partitionwise aggregation [pgpa_join.c#agg-uniqueness](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_join.c#L595-L613).
   - **Query features.** Gather and Gather Merge nodes (ignoring the single-copy Gather that `debug_parallel_query` adds), and semijoin outcomes: a Unique or simple Agg below one side means "made unique", and a `JOIN_SEMI`/`JOIN_RIGHT_SEMI` join means "direct" [pgpa_walker.c#gather-features](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_walker.c#L341-L365) [pgpa_join.c#semijoin-features](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_join.c#L480-L504). A direct-semijoin feature is kept only if planning recorded the unique-ify alternative, so `SEMIJOIN_NON_UNIQUE` appears only where a choice existed [pgpa_walker.c#filter-nonunique](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_walker.c#L129-L139).
   - **No-Gather scans:** every scan not beneath a Gather or Gather Merge [pgpa_scan.c#no_gather](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_scan.c#L227-L240).
   - **Discarded alternatives.** When two planning roots share an `alternative_plan_name` (a `MinMaxAggPath` or a hashed [SubPlan](../../../glossary.md#subplan) alternative), the one whose relations never appear in the final scans is "discarded", and its relations become `DO_NOT_SCAN` advice, provided another alternative was chosen [pgpa_walker.c#alternatives](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_walker.c#L187-L221) [pgpa_walker.c#pgpa_classify_alternative_subplans](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_walker.c#L1289-L1344) [pathnodes.h#alternative_plan_name](../../../../raw/postgres-19/src/include/nodes/pathnodes.h#L323-L333).
3. **Render the advice string**, if requested. `pgpa_output_advice()` emits, in this order: one `JOIN_ORDER` per top-level unrolled join, join-method advice (the inner members of each join), scan advice except ordinary scans, Gather and semijoin features, `NO_GATHER`, and `DO_NOT_SCAN` [pgpa_output.c#pgpa_output_advice](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_output.c#L79-L164). `JOIN_ORDER` items are never merged, because merging would change their meaning [pgpa_output.c#no-merge](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_output.c#L116-L124). Index names are always schema-qualified, a multi-relation scan target such as a partitionwise join is a sublist, and lines wrap after column 76 so `EXPLAIN` in an 80-column `psql` window does not wrap [pgpa_output.c#index-names](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_output.c#L257-L292) [pgpa_output.c#wrap](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_output.c#L102-L114).
4. **Compute feedback**, if requested. For each trove entry, the flags set during planning are kept, and `PGPA_FB_FAILED` is added when the entry was fully matched but generating advice from this plan would not produce it [pgpa_planner.c#pgpa_planner_append_feedback](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1867-L1908).
   - That check, `pgpa_walker_would_advise()`, maps the target to RTIs and looks for a matching relation set among the walker's scans, join inners, or features [pgpa_walker.c#pgpa_walker_would_advise](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_walker.c#L725-L907).
   - For `NO_GATHER`, the target only has to be a subset of the no-Gather scans (same lines).
   - For `JOIN_ORDER`, a match of any prefix of a top-level unrolled join is enough, because the advice need not name every member [pgpa_walker.c#join-order-matching](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_walker.c#L943-L1183).
   - With `feedback_warnings` on, every entry whose flags are not exactly "partially and fully matched" is reported in one `WARNING: supplied plan advice was not enforced` [pgpa_planner.c#pgpa_planner_feedback_warning](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1910-L1963).

Feedback flags map to words in this order [pgpa_trove.c#pgpa_trove_append_flags](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_trove.c#L335-L357) [pgplanadvice.sgml#feedback-meanings](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L599-L675):

| Flag | Shown as | Meaning |
|---|---|---|
| `PGPA_FB_MATCH_FULL` (always with partial) | `matched` | All targets were seen together at a point where the advice could be enforced |
| `PGPA_FB_MATCH_PARTIAL` alone | `partially matched` | Some targets were seen, or all but never together |
| neither | `not matched` | No target was seen; the advice does not fit the query, or that part of the query was never planned |
| `PGPA_FB_INAPPLICABLE` | `, inapplicable` | The tag cannot apply, such as a missing index or semijoin advice on a non-semijoin |
| `PGPA_FB_CONFLICTING` | `, conflicting` | Other advice asked for an incompatible behavior; the topic was not enforced |
| `PGPA_FB_FAILED` | `, failed` | Only on fully matched entries: the plan does not conform |

The last row has a consequence the flag names hide: `failed` is checked only for fully matched entries, so a `partially matched` entry never shows `failed`, even when the plan ignored it [pgpa_planner.c#failed-only-if-full](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1892-L1900) [join_order.out#partial-no-failed](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/join_order.out#L555-L571).

Finally the hook appends `DefElem("pg_plan_advice", list of DefElem("advice_string"), DefElem("feedback"))` to `PlannedStmt.extension_state`, a field core provides for exactly this [pgpa_planner.c#stash](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L339-L394) [plannodes.h#extension_state](../../../../raw/postgres-19/src/include/nodes/plannodes.h#L158-L165).

### Step 11: EXPLAIN output

**Input:** the stored entry and the `EXPLAIN` options. **Output:** two optional blocks after the plan.

`ExplainOnePlan()` calls `explain_per_plan_hook` after printing the plan, so the advice blocks come after the plan nodes and planning statistics [explain.c#explain_per_plan_hook-call](../../../../raw/postgres-19/src/backend/commands/explain.c#L656-L659). The module's hook prints [pg_plan_advice.c#explain-hook](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L346-L410):

- **Supplied Plan Advice**: each feedback entry as the advice item plus `/* flags */`, when feedback exists and either `always_explain_supplied_advice` is on (the default) or `PLAN_ADVICE` was given [pg_plan_advice.c#supplied-block](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L370-L390) [pg_plan_advice.c#pg_plan_advice_explain_feedback](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L321-L341). Advice like `HASH_JOIN(f g)` appears as separate entries `HASH_JOIN(f)` and `HASH_JOIN(g)`, because the trove holds one entry per target, while `JOIN_ORDER(f g)` stays one entry [pgplanadvice.sgml#feedback-example](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L583-L596).
- **Generated Plan Advice**: the stored advice string, only when `PLAN_ADVICE` was given and not set to false [pg_plan_advice.c#generated-block](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L392-L409).

In text format each block is printed only when non-empty, one item per line [pg_plan_advice.c#multiline](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L276-L319). Other formats emit the property whenever the block is shown and the plan carries its data, even as an empty string: the supplied block when feedback was stored, and the generated block when an advice string was stored [pg_plan_advice.c#explain-hook](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L370-L409). So JSON `EXPLAIN` with `NESTED_LOOP_PLAIN()`, an item with no targets, prints `"Supplied Plan Advice": ""` [syntax.out#json-empty](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/syntax.out#L19-L34). With no supplied advice there is no trove, so no feedback is stored and no such property appears [pgpa_planner.c#feedback-decision](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L259-L265) [pg_plan_advice.c#supplied-block](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L370-L390).

### Advisors and generation requests

Other modules use two exported functions [pg_plan_advice.h#exports](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.h#L47-L72):

- `pg_plan_advice_add_advisor()` registers a callback that receives the `PlannerGlobal`, `Query`, query string, cursor options, and `ExplainState`, and returns an advice string or NULL; `pg_plan_advice_remove_advisor()` removes it [pg_plan_advice.c#advisors](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L199-L228). The sibling `pg_stash_advice` module uses this to apply advice stored in [dynamic shared memory](../../../glossary.md#dynamic-shared-memory) per query ID. It calls `EnableQueryId()` when loaded, so [query jumbling](../../../glossary.md#query-jumbling) runs under `compute_query_id = auto`, and its advisor returns nothing for a query whose ID is 0 [pg_stash_advice.c#EnableQueryId](../../../../raw/postgres-19/contrib/pg_stash_advice/pg_stash_advice.c#L93-L94) [pg_stash_advice.h#purpose](../../../../raw/postgres-19/contrib/pg_stash_advice/pg_stash_advice.h#L6-L11) [pg_stash_advice.c#advisor-registration](../../../../raw/postgres-19/contrib/pg_stash_advice/pg_stash_advice.c#L141-L145) [pg_stash_advice.c#pgsa_advisor](../../../../raw/postgres-19/contrib/pg_stash_advice/pg_stash_advice.c#L152-L166).
- `pg_plan_advice_request_advice_generation(true)` increments a counter that turns generation on for all later planning; `false` decrements it. It can only add generation, never suppress it [pg_plan_advice.c#request_advice_generation](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L230-L254).

Registering an advisor does not by itself request generated advice or feedback [pgpa_planner.c#generate-decision](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L212-L222) [pgpa_planner.c#feedback-decision](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L259-L265). The header is installed for such modules under the server include directory, in `contrib/pg_plan_advice/` [Makefile:18](../../../../raw/postgres-19/contrib/pg_plan_advice/Makefile#L18) [meson.build#install_headers](../../../../raw/postgres-19/contrib/pg_plan_advice/meson.build#L45-L48).

### Worked examples from the regression suite

All examples below are expected output from the pinned checkout's regression files, not new measurements. The scripts set some planner GUCs away from their defaults to make plans stable; each example states which settings it depends on.

**Example 1: generate, then enforce.** `join_strategy.sql` sets `max_parallel_workers_per_gather = 0` (boot value 2), which rules out parallel plans because `standard_planner()` allows parallel mode only when that setting is above zero [join_strategy.sql:2](../../../../raw/postgres-19/contrib/pg_plan_advice/sql/join_strategy.sql#L2) [guc_parameters.dat#max_parallel_workers_per_gather](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L2063-L2067) [planner.c#parallel-ok](../../../../raw/postgres-19/src/backend/optimizer/plan/planner.c#L424-L434). With no advice, `EXPLAIN (COSTS OFF, PLAN_ADVICE)` of `join_fact f JOIN join_dim d` produces [join_strategy.out#default](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/join_strategy.out#L16-L30):

```text
 Hash Join
   Hash Cond: (f.dim_id = d.id)
   ->  Seq Scan on join_fact f
   ->  Hash
         ->  Seq Scan on join_dim d
 Generated Plan Advice:
   JOIN_ORDER(f d)
   HASH_JOIN(d)
   SEQ_SCAN(f d)
   NO_GATHER(f d)
```

Reading it with Step 10: `JOIN_ORDER(f d)` is the single unrolled join, `HASH_JOIN(d)` names its inner member, `SEQ_SCAN(f d)` lists both scans, and `NO_GATHER(f d)` lists every scan not under a Gather, which here is all of them because parallelism is off. Supplying `HASH_JOIN(d)` alone reproduces the plan, and the feedback is `/* matched */` [join_strategy.out#hash-join-advice](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/join_strategy.out#L37-L54). Supplying `NESTED_LOOP_MEMOIZE(d)` instead produces a Nested Loop over a Memoize node, again `matched` [join_strategy.out#memoize](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/join_strategy.out#L112-L132).

**Example 2: impossible scan advice, as a worked mask calculation.** `scan.sql` leaves every `enable_*` setting at its default. It changes `max_parallel_workers_per_gather` to 0, as in Example 1, and four cost settings: `seq_page_cost` and `random_page_cost` to 0.1 (defaults 1.0 and 4.0), and `cpu_tuple_cost` and `cpu_index_tuple_cost` to 0 (defaults 0.01 and 0.005) [scan.sql#setup](../../../../raw/postgres-19/contrib/pg_plan_advice/sql/scan.sql#L1-L6) [cost.h#defaults](../../../../raw/postgres-19/src/include/optimizer/cost.h#L24-L27) [guc_parameters.dat#seq_page_cost](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L2639-L2643) [guc_parameters.dat#random_page_cost](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L2421-L2425) [guc_parameters.dat#cpu_tuple_cost](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L553-L557) [guc_parameters.dat#cpu_index_tuple_cost](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L535-L539). The script does not say why it sets the cost settings. None of them enters the mask [planner.c#default_pgs_mask](../../../../raw/postgres-19/src/backend/optimizer/plan/planner.c#L490-L535), so the calculation below does not depend on them. It then supplies `INDEX_SCAN(scan_table scan_table_pkey)` for `SELECT * FROM scan_table` [scan.sql#index-on-full-scan](../../../../raw/postgres-19/contrib/pg_plan_advice/sql/scan.sql#L57-L59).

Inputs, all from source: the bit values [pathnodes.h#PGS-constants](../../../../raw/postgres-19/src/include/nodes/pathnodes.h#L66-L84); the default-mask code [planner.c#default_pgs_mask](../../../../raw/postgres-19/src/backend/optimizer/plan/planner.c#L504-L535); boot value `true` for the eleven `enable_*` GUCs that code reads besides `enable_partitionwise_join`, which is `false` [guc_parameters.dat#enable_bitmapscan](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L871-L875) [guc_parameters.dat#enable_gathermerge](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L892-L896) [guc_parameters.dat#enable_hashjoin](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L913-L917) [guc_parameters.dat#enable_indexonlyscan](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L927-L931) [guc_parameters.dat#enable_indexscan](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L934-L938) [guc_parameters.dat#enable_material](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L941-L945) [guc_parameters.dat#enable_memoize](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L948-L952) [guc_parameters.dat#enable_mergejoin](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L955-L959) [guc_parameters.dat#enable_nestloop](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L962-L966) [guc_parameters.dat#enable_seqscan](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L1020-L1024) [guc_parameters.dat#enable_tidscan](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L1034-L1038) [guc_parameters.dat#enable_partitionwise_join](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L998-L1002); `all_scan_mask` and the `INDEX_SCAN` mapping [pgpa_planner.c#all_scan_mask](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1633-L1634) [pgpa_planner.c#tag-map](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1676-L1677); and the sequential-scan test [costsize.c#cost_seqscan-disabled](../../../../raw/postgres-19/src/backend/optimizer/path/costsize.c#L279-L336).

```text
all 19 PGS bits (0x00001 .. 0x40000)          = 0x7FFFF
default_pgs_mask = 0x7FFFF - CONSIDER_PARTITIONWISE (0x20000)
                                              = 0x5FFFF
all_scan_mask    = SCAN_ANY 0x0001F + APPEND 0x01000
                 + MERGE_APPEND 0x02000 + CONSIDER_INDEXONLY 0x10000
                                              = 0x1301F
scan_type (INDEX_SCAN) = INDEXSCAN            = 0x00002
cleared = all_scan_mask & ~scan_type          = 0x1301D
rel->pgs_mask = 0x5FFFF & ~0x1301D            = 0x4CFE2

seq scan path, non-partial:
  enable_mask = SEQSCAN 0x00001 + CONSIDER_NONPARTIAL 0x40000 = 0x40001
  0x4CFE2 & 0x40001 = 0x40000 != 0x40001      -> disabled_nodes = 1
index path on scan_table_pkey: never built, because the query has no
  index clause, no useful ordering, and needs column b (no index-only scan)
```

The index-path condition is in [indxpath.c#index-path-conditions](../../../../raw/postgres-19/src/backend/optimizer/path/indxpath.c#L959-L966). With `trace_mask` on, Step 6's message would therefore report a change from `0x5ffff` to `0x4cfe2`; no regression test exercises that message, so this value is derived from the constants, not observed. With `max_parallel_workers_per_gather = 0` no partial paths exist [planner.c#parallel-ok](../../../../raw/postgres-19/src/backend/optimizer/plan/planner.c#L424-L434), so the only path left is the disabled sequential scan. It wins, and the expected output matches the calculation [scan.out#impossible-index-advice](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/scan.out#L171-L182):

```text
 Seq Scan on scan_table
   Disabled: true
 Supplied Plan Advice:
   INDEX_SCAN(scan_table scan_table_pkey) /* matched, failed */
```

The advice was `matched` because `scan_table` was seen and its scan advice applied, and `failed` because the plan does not contain that index scan.

At the default `max_parallel_workers_per_gather` of 2, a parallel sequential scan could also be considered. It would be disabled the same way, because a partial scan needs `PGS_SEQSCAN` too [costsize.c#cost_seqscan-disabled](../../../../raw/postgres-19/src/backend/optimizer/path/costsize.c#L311-L336). No test runs that case, so which disabled path would then win is not established here.

**Example 3: naming the right relation.** In a query that joins `scan_table s` twice, the generated advice calls the second one `s#2`, while `EXPLAIN` calls it `s_1`; the two naming schemes differ [scan.out#two-aliases](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/scan.out#L567-L586). `SEQ_SCAN(s#2)` changes only the second scan [scan.out#second-occurrence](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/scan.out#L613-L636). Here `x` is the alias of a parenthesized join, not of a subquery, so both copies of `s` belong to one query level. They are told apart by occurrence number, not by plan name; the occurrence count skips the join's own range-table entry [scan.out#two-aliases](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/scan.out#L567-L586) [pgpa_identifier.c#occurrence](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_identifier.c#L148-L184). `scan.sql` also changes the cost settings listed in Example 2, which can change the join methods shown, but not the names.

Partitions carry schema-qualified names such as `pt2/public.pt2a`. Each branch of a partitionwise join is planned as its own join problem [README#Join-Order-Advice](../../../../raw/postgres-19/contrib/pg_plan_advice/README#L120-L124). So the three-way partitionwise join of `pt1`, `pt2`, and `pt3` gets three `JOIN_ORDER` items, one per set of matching partitions, such as `JOIN_ORDER(pt2/public.pt2a pt3/public.pt3a pt1/public.pt1a)` [partitionwise.out#generated](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/partitionwise.out#L109-L121). That output depends on two settings of `partitionwise.sql`. `enable_partitionwise_join = true` is needed because the default `false` leaves no partitionwise paths (Step 2). `max_parallel_workers_per_gather = 0` rules out parallel plans, as in Example 1, so every scan appears in `NO_GATHER` [partitionwise.sql#setup](../../../../raw/postgres-19/contrib/pg_plan_advice/sql/partitionwise.sql#L1-L3).

**Example 4: conflict still constrains order.** `NESTED_LOOP_PLAIN(f) NESTED_LOOP_MATERIALIZE(f)` gives `f` two methods. Both entries are `conflicting`, so no method is enforced when `f` is inner. When `f` is outer, both entries deny the pair, so `f` cannot be outer at all. The planner therefore picks the cheapest join with `f` inner, a Merge Join, and both entries end `failed` [join_strategy.out#conflict](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/join_strategy.out#L299-L316) [pgpa_planner.c#join-path-enforcement](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L1138-L1150). Which join is cheapest is a cost result under `join_strategy.sql`'s `max_parallel_workers_per_gather = 0` (Example 1); the conflict and the order denial do not depend on that setting.

**Example 5: choosing between alternatives.** For `EXISTS (...) OR a < 0`, the planner builds both a per-row `exists_1` subplan and a hashed `exists_to_any_1` alternative. The generated advice records the loser as `DO_NOT_SCAN(alt_t2@exists_1)`, and supplying `DO_NOT_SCAN(alt_t2@exists_to_any_1)` flips the choice to the index-only `exists_1` subplan [alternatives.out#subplans](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/alternatives.out#L12-L66). For `min(a), max(a)`, `DO_NOT_SCAN(alt_minmax@minmax_1)` disables one `MinMaxAggPath` scan and the plan falls back to a full Aggregate [alternatives.out#minmax](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/alternatives.out#L126-L139). `alternatives.sql` also sets `max_parallel_workers_per_gather = 0`, as in Example 1, which keeps Gather nodes out of these plans [alternatives.sql:2](../../../../raw/postgres-19/contrib/pg_plan_advice/sql/alternatives.sql#L2).

**Example 6: parallel advice.** `gather.sql` is the one script that wants parallel plans, so it moves four settings the other way [gather.sql#setup](../../../../raw/postgres-19/contrib/pg_plan_advice/sql/gather.sql#L1-L6):

| Setting | Script value | Default | What the default does instead |
|---|---|---|---|
| `max_parallel_workers_per_gather` | 1 | 2 [guc_parameters.dat#max_parallel_workers_per_gather](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L2063-L2067) | Allows up to two parallel processes per executor node, as the setting's description says (same lines) |
| `parallel_setup_cost` | 0 | 1000 [guc_parameters.dat#parallel_setup_cost](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L2328-L2332) [cost.h:30](../../../../raw/postgres-19/src/include/optimizer/cost.h#L30) | Charges every Gather and Gather Merge a fixed startup cost [costsize.c#cost_gather-costs](../../../../raw/postgres-19/src/backend/optimizer/path/costsize.c#L449-L451) |
| `parallel_tuple_cost` | 0 | 0.1 [guc_parameters.dat#parallel_tuple_cost](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L2337-L2341) [cost.h:29](../../../../raw/postgres-19/src/include/optimizer/cost.h#L29) | Charges for every row passed from a worker to the leader (same lines) |
| `min_parallel_table_scan_size` | 0 | 8 MB [guc_parameters.dat#min_parallel_table_scan_size](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L2237-L2242) | Gives a base table smaller than that no parallel workers [allpaths.c#compute_parallel_worker-threshold](../../../../raw/postgres-19/src/backend/optimizer/path/allpaths.c#L4988-L4991) |

It also sets `debug_parallel_query = off`, which is already the default [guc_parameters.dat#debug_parallel_query](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L693-L698). The script does not say why it changes the other four. Their effect is to remove the startup and per-row charges on Gather nodes and the minimum table size for a parallel scan, as the table shows. All the outputs below depend on them, and no test runs these queries at the defaults, so the default plans are not established here.

Under these settings the default plan for `gt_fact f JOIN gt_dim d ... ORDER BY d.id` is a Gather Merge over a sorted Parallel Hash Join. The generated advice says so in one item, `GATHER_MERGE((f d))`, and has no `NO_GATHER`, because every scan is under the Gather Merge [gather.out#default](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/gather.out#L18-L37). Supplied advice then reshapes the plan:

| Supplied advice | Plan | Feedback |
|---|---|---|

### Key interaction: prepared statements and the plan cache

`pg_plan_advice` reads advice when the planner runs, while the [plan cache](../../../glossary.md#custom-and-generic-plan) decides when the planner runs, for example for a [prepared statement](../../../glossary.md#prepared-statement). The plan cache does not know the advice GUC exists. Therefore a cached plan keeps the advice that was in effect when it was built, until the plan cache itself decides to plan again.

The plan cache has no special handling for any extension GUC. It plans a cached statement again only in these cases:

- An [invalidation message](../../../glossary.md#invalidation-message) (sinval) arrives for a relation, function, type, or one of certain catalogs that the plan depends on [plancache.c#invalidation-overview](../../../../raw/postgres-19/src/backend/utils/cache/plancache.c#L14-L42) [plancache.c#InitPlanCache](../../../../raw/postgres-19/src/backend/utils/cache/plancache.c#L153-L167).
- The `search_path` changed [plancache.c#search_path-check](../../../../raw/postgres-19/src/backend/utils/cache/plancache.c#L716-L734).
- The statement's rewrite applied [row-level security](../../../glossary.md#row-level-security), and the current user or `row_security` changed [plancache.c#rls-recheck](../../../../raw/postgres-19/src/backend/utils/cache/plancache.c#L736-L743).
- A generic plan was marked as depending on the current user, and the current user changed [plancache.c#role-dependent-generic-plan](../../../../raw/postgres-19/src/backend/utils/cache/plancache.c#L976-L981).
- A plan marked transient sees an advanced [`TransactionXmin`](../../../glossary.md#transactionxmin) [plancache.c#transient-check](../../../../raw/postgres-19/src/backend/utils/cache/plancache.c#L997-L1004).
- `DISCARD PLANS` or `DISCARD ALL` runs, or `session_replication_role` changes; all three call `ResetPlanCache()` [discard.c#DiscardCommand](../../../../raw/postgres-19/src/backend/commands/discard.c#L31-L55) [discard.c#DiscardAll](../../../../raw/postgres-19/src/backend/commands/discard.c#L57-L79) [trigger.c#assign_session_replication_role](../../../../raw/postgres-19/src/backend/commands/trigger.c#L6716-L6728) [plancache.c#ResetPlanCache](../../../../raw/postgres-19/src/backend/utils/cache/plancache.c#L2379-L2412).

Changing `pg_plan_advice.advice` is none of these, so it invalidates nothing. To make new advice reach a statement whose plan is already cached, `DISCARD PLANS` is the direct tool. It marks the session's saved plans invalid, so the next execution plans again under the advice then in effect [discard.c#DiscardCommand](../../../../raw/postgres-19/src/backend/commands/discard.c#L40-L42) [plancache.c#ResetPlanCache](../../../../raw/postgres-19/src/backend/utils/cache/plancache.c#L2379-L2412). `DISCARD ALL` does not help here, because it also drops the prepared statements and resets every setting, the advice included [discard.c#DiscardAll](../../../../raw/postgres-19/src/backend/commands/discard.c#L70-L76). No test checks that new advice reaches a cached plan after `DISCARD PLANS`, so that use is derived from the plan-cache source.

When the plan cache does plan, `choose_custom_plan()` decides between a custom and a generic plan [plancache.c#choose_custom_plan](../../../../raw/postgres-19/src/backend/utils/cache/plancache.c#L1178-L1231). [`plan_cache_mode`](../../../glossary.md#plan-cache-mode) can force either kind; it has `user` context, so `SET` changes it for the session and `SET LOCAL` for the transaction, with no reload or restart [guc_parameters.dat#plan_cache_mode](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L2363-L2368):

| Prepared statement | When the planner runs | When a changed advice GUC takes effect |
|---|---|---|
| No parameters | Once, for the generic plan; `boundParams == NULL` returns "generic" before `plan_cache_mode` is even consulted [plancache.c#no-params](../../../../raw/postgres-19/src/backend/utils/cache/plancache.c#L1192-L1197) | Only after an invalidation or `DISCARD PLANS`; `plan_cache_mode = force_custom_plan` does not help |
| Parameters, `plan_cache_mode = auto` (default) | Custom plans for the first 5 executions, then generic if its cost is below the average custom cost [plancache.c#five-custom](../../../../raw/postgres-19/src/backend/utils/cache/plancache.c#L1211-L1230) [guc_parameters.dat#plan_cache_mode](../../../../raw/postgres-19/src/backend/utils/misc/guc_parameters.dat#L2363-L2368) | At each custom plan; not while the generic plan is reused, until it is invalidated or discarded |
| Parameters, `force_custom_plan` | Every execution [plancache.c#mode-force](../../../../raw/postgres-19/src/backend/utils/cache/plancache.c#L1199-L1203) | Next execution |
| Parameters, `force_generic_plan` | Once [plancache.c#mode-force](../../../../raw/postgres-19/src/backend/utils/cache/plancache.c#L1199-L1203) | Only after an invalidation or `DISCARD PLANS` |

Role changes reach the plan cache through syscache callbacks on role membership, role attributes, and database ownership [plancache.c#role-callbacks](../../../../raw/postgres-19/src/backend/utils/cache/plancache.c#L164-L166). `PlanCacheRoleCallback()` then invalidates the whole statement when its rewrite applied row-level security, and otherwise only a generic plan marked `dependsOnRole` [plancache.c#PlanCacheRoleCallback](../../../../raw/postgres-19/src/backend/utils/cache/plancache.c#L2317-L2365). The planner sets that mark for row-level security quals found during planning, and also for a foreign join whose push-down assumed that the current user is a user named in the query [setrefs.c#rls-dependsOnRole](../../../../raw/postgres-19/src/backend/optimizer/plan/setrefs.c#L3849-L3851) [clauses.c#inlined-rls-dependsOnRole](../../../../raw/postgres-19/src/backend/optimizer/util/clauses.c#L6138-L6143) [createplan.c#foreign-join-dependsOnRole](../../../../raw/postgres-19/src/backend/optimizer/plan/createplan.c#L4036-L4042) [plancache.c#BuildCachedPlan-dependsOnRole](../../../../raw/postgres-19/src/backend/utils/cache/plancache.c#L1137-L1156).

**Why `EXPLAIN (PLAN_ADVICE) EXECUTE` shows nothing.** `PREPARE` does not plan: `PrepareQuery()` analyzes, completes the cached plan source, and stores it [prepare.c#PrepareQuery](../../../../raw/postgres-19/src/backend/commands/prepare.c#L121-L140). So the first `EXPLAIN (PLAN_ADVICE) EXECUTE` does run the planner inside the `EXPLAIN`, yet no advice is generated, because the plan cache never passes an `ExplainState` down:

1. `ExplainExecuteQuery()` calls `GetCachedPlan()`, which has no `ExplainState` parameter [prepare.c#ExplainExecuteQuery](../../../../raw/postgres-19/src/backend/commands/prepare.c#L634-L636).
2. `BuildCachedPlan()` calls `pg_plan_queries()` [plancache.c#BuildCachedPlan](../../../../raw/postgres-19/src/backend/utils/cache/plancache.c#L1097-L1101).
3. `pg_plan_queries()` passes NULL as the `ExplainState` to `pg_plan_query()` [postgres.c#pg_plan_queries](../../../../raw/postgres-19/src/backend/tcop/postgres.c#L1010-L1014).
4. `pg_plan_advice_should_explain(NULL)` is false, so the `PLAN_ADVICE` trigger cannot fire. Advice is then generated only if `always_store_advice_details` is on or another module has requested generation [pg_plan_advice.c#should_explain](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L156-L167) [pgpa_planner.c#generate-decision](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L212-L222). `es == NULL` also turns off feedback unless `feedback_warnings` or `always_store_advice_details` is on [pgpa_planner.c#feedback-decision](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L259-L265).

The module's own comment names the workaround, `always_store_advice_details = on`, which must be in effect when the cached plan is built [pg_plan_advice.c#prepared-note](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L377-L380) [pgplanadvice.sgml#always_store](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L729-L743). The `prepared` test shows both halves: `pt1` (with `PLAN_ADVICE`) and `pt3` (with supplied advice), prepared with the setting off, show no advice block at all; with it on, `pt2` shows its Generated block and `pt4` shows both blocks [prepared.out#prepared](../../../../raw/postgres-19/contrib/pg_plan_advice/expected/prepared.out#L16-L68). Core commit `c83ac02e`, which added the `ExplainState` argument to the planner, already noted it "won't help with EXPLAIN EXECUTE is used" (sic).

**`auto_explain` meets the same limitation.** Its `auto_explain.log_extension_options` setting can request extension `EXPLAIN` options, and its documentation names `pg_plan_advice` as one provider [auto-explain.sgml#log_extension_options](../../../../raw/postgres-19/doc/src/sgml/auto-explain.sgml#L268-L288). The steps are:

1. At executor end, `auto_explain` builds its own `ExplainState`, applies the extension options to it, prints the plan, and then calls `explain_per_plan_hook` [auto_explain.c:452](../../../../raw/postgres-19/contrib/auto_explain/auto_explain.c#L452) [auto_explain.c#explain_per_plan_hook-call](../../../../raw/postgres-19/contrib/auto_explain/auto_explain.c#L462-L467).
2. `pg_plan_advice`'s hook can only print what the plan already carries [pg_plan_advice.c#explain-hook](../../../../raw/postgres-19/contrib/pg_plan_advice/pg_plan_advice.c#L346-L410).
3. That plan was built by an ordinary planner call, outside `EXPLAIN`. It therefore carries generated advice only under the conditions in step 4 of the list above, and feedback only with `feedback_warnings` or `always_store_advice_details` [pgpa_planner.c#generate-decision](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L212-L222) [pgpa_planner.c#feedback-decision](../../../../raw/postgres-19/contrib/pg_plan_advice/pgpa_planner.c#L259-L265).

`auto_explain.log_extension_options` has `superuser` context, so a role allowed to change it can `SET` it for the session or the transaction [auto_explain.c#log_extension_options-guc](../../../../raw/postgres-19/contrib/auto_explain/auto_explain.c#L286-L295). No test combines the two modules, so this interaction is derived from source.

### What advice cannot control

- **Aggregation:** sort versus hash aggregation, eager aggregation, and partitionwise aggregation [pgplanadvice.sgml#limitations](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L792-L799) [README#Future-Work](../../../../raw/postgres-19/contrib/pg_plan_advice/README#L251-L257).
- **Set operations** such as `UNION` and `INTERSECT` [pgplanadvice.sgml#limitations](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L801-L805).
- **Estimates:** advice controls outcomes, not row counts or costs [README#Future-Work](../../../../raw/postgres-19/contrib/pg_plan_advice/README#L259-L263).
- **Plans the planner never considers**, by design [pgplanadvice.sgml#limitations-viable](../../../../raw/postgres-19/doc/src/sgml/pgplanadvice.sgml#L807-L813).

### Final causal summary

`enable_*` GUCs set `default_pgs_mask` → each new base or join relation copies it → `pg_plan_advice`'s hooks match supplied advice to relations by identifier and *clear* the bits for everything the advice forbids, never setting any → core either skips the forbidden strategies or builds them as disabled paths → `add_path()` keeps the fewest-disabled, then cheapest, path → so the advised plan wins when the planner generated it and all alternatives were disabled, and otherwise a disabled plan wins without error → the shutdown hook walks the final plan, renders advice that would reproduce it, and flags each supplied entry as matched, partial, unmatched, inapplicable, conflicting, or failed → those results live inside the `PlannedStmt`, so `EXPLAIN` shows them for freshly planned queries, while cached plans keep the advice and feedback of the cycle that built them until the plan cache replans.

Conditions that decide the outcome:

- Advice cannot re-enable what an `enable_*` setting disabled.
- A requested partitionwise join can only be satisfied with `enable_partitionwise_join = on`; with the default `off`, the request still disables the ordinary joins.
- Join advice under GEQO is probabilistic.
- Conflicting advice on a topic is not enforced.
- `failed` is reported only for fully matched advice.
- A plan-cache plan carries generated advice only if `always_store_advice_details` was on, or another module had requested generation, when it was built. It carries feedback only if `always_store_advice_details` or `feedback_warnings` was on. `DISCARD PLANS` makes cached statements plan again under the current advice.
