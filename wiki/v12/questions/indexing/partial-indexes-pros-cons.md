## Question

## Answer

A PostgreSQL 12 [partial index](../../../glossary.md#partial-index) is an index with a `WHERE` predicate. It stores entries only for the table rows that satisfy that predicate. It can therefore be smaller than a full index, and rows outside the predicate add no entries to it.[indices.sgml#Partial-Indexes](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L765-L784) [create_index.sgml#partial-index-description](../../../../raw/postgres-12/doc/src/sgml/ref/create_index.sgml#L65-L84)

The main cost is that the [planner](../../../glossary.md#planner) may use the index only when it can prove, at planning time, that the query's conditions imply the predicate. The proof engine in `predtest.c` handles several common forms but is not a general theorem prover. So a query that is logically covered can still miss the index, and a generic plan for a prepared statement usually cannot prove anything about a parameter.[predtest.c#predicate_implied_by](../../../../raw/postgres-12/src/backend/optimizer/util/predtest.c#L113-L150) [indxpath.c#check_index_predicates](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L3430-L3532)

### Short answer

| Area | Benefit | Cost or caveat |
| --- | --- | --- |
| Size and write cost | Excluding common or uninteresting values makes the index smaller. A row outside the predicate gets no entry in this index.[indices.sgml#exclude-common-values](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L774-L784) [execIndexing.c#ExecInsertIndexTuples](../../../../raw/postgres-12/src/backend/executor/execIndexing.c#L313-L357) | The predicate is still evaluated for every row at build time and on every insert or non-HOT update.[heapam_handler.c#heapam_index_build_range_scan](../../../../raw/postgres-12/src/backend/access/heap/heapam_handler.c#L1604-L1626) Columns in the predicate block [HOT](../../../glossary.md#hot) updates for every row, including rows outside the predicate; see [Cons and restrictions](#cons-and-restrictions). |
| Read performance | A query whose `WHERE` clause implies the predicate can use the smaller index. The indexed column need not be the predicate column, and the key can be an expression such as `lower(col1)`.[indices.sgml#exclude-uninteresting-values](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L845-L897) [indices.sgml#indexes-expressional](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L687-L753) | A query that the proof engine cannot match never uses the index. A generic plan cannot prove the predicate from a parameter such as `order_nr < $1`; custom plans can. Expression keys must also match the stored expression; see [Planner matching and plan shape](#planner-matching-and-plan-shape) and [Prepared statements and parameters](#prepared-statements-and-parameters). |
| Conditional uniqueness | A unique partial index enforces uniqueness only among rows that satisfy the predicate.[indices.sgml#partial-unique-index](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L927-L968) | It cannot become a primary-key or unique constraint through `USING INDEX`, and it cannot be the referenced key of a foreign key.[parse_utilcmd.c#partial-index-constraint-reject](../../../../raw/postgres-12/src/backend/parser/parse_utilcmd.c#L2088-L2093) [tablecmds.c#transformFkeyCheckAttrs](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L9568-L9577) |
| Planner control | A partial index can hide an index from queries the planner would otherwise misplan.[indices.sgml#override-plan-choices](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L970-L981) | The documentation warns that this requires knowing at least as much as the planner, and that the gain over a regular index is usually minimal.[indices.sgml#partial-index-warning](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L983-L989) |
| Statistics | A standalone `ANALYZE` sets the index's `pg_class.reltuples` to an estimate of the predicate-satisfying rows, and stores [pg_statistic](../../../glossary.md#pg_statistic) rows for expression columns of the index.[analyze.c#index-relstats-update](../../../../raw/postgres-12/src/backend/commands/analyze.c#L607-L631) [analyze.c#compute_index_stats](../../../../raw/postgres-12/src/backend/commands/analyze.c#L694-L843) | `ANALYZE` skips that `reltuples` update under `VACUUM ANALYZE` and for inherited statistics. With no statistics hook loaded, general expression [selectivity](../../../glossary.md#selectivity) ignores partial expression-index statistics, but B-tree and BRIN costing still read their [correlation](../../../glossary.md#correlation). Adding the predicate to the index selectivity can underestimate it.[analyze.c#index-relstats-update](../../../../raw/postgres-12/src/backend/commands/analyze.c#L607-L612) [selfuncs.c#examine_variable-expression-index-stats](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L4527-L4602) [selfuncs.c#btcostestimate-correlation](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L6158-L6212) [selfuncs.c#add_predicate_to_index_quals](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L5878-L5890) |

### Mental model

Three objects carry a partial index through its life. The catalog row stores the predicate. The executor evaluates it on writes. The planner tries to prove it for each query, and costs the index with its own row estimate.

| Value | Meaning | Source | Live or stored | Later use |
| --- | --- | --- | --- | --- |
| `pg_index.indpred` | The predicate as a `pg_node_tree`; null for a non-partial index | [`pg_index`](../../../glossary.md#pg_index) catalog row[catalogs.sgml#pg-index-indpred](../../../../raw/postgres-12/doc/src/sgml/catalogs.sgml#L3938-L3951) | Stored; changes only when the index is recreated | Loaded through the [relcache](../../../glossary.md#relcache) into `IndexInfo.ii_Predicate` and `IndexOptInfo.indpred`[relcache.c#RelationGetIndexPredicate](../../../../raw/postgres-12/src/backend/utils/cache/relcache.c#L4713-L4778) |
| `IndexOptInfo.predOK` | Whether this query's clauses imply the predicate | `check_index_predicates()`[indxpath.c#check_index_predicates](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L3506-L3516) | Live; recomputed for every planning cycle, starting from `false`[plancat.c#get_relation_info-index-predicate](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L381-L382) | Gates plain index paths and `has_unique_index()`[indxpath.c#create_index_paths](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L258-L264) [plancat.c#has_unique_index](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L2039-L2051) |

| `IndexOptInfo.tuples` | The planner's entry count for the index | Non-partial: the table's estimate. Partial: stored density × current pages, capped at the table's estimate[plancat.c#get_relation_info-size](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L387-L407) [plancat.c#estimate_rel_size-index](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L985-L1026) | Mixed: stored density, live page count | Caps the visited-tuple estimate[selfuncs.c#genericcostestimate](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L5760-L5763) |
| Expression-column `pg_statistic` row | MCV, histogram, and correlation of an index expression column, computed only from predicate-passing sample rows | `compute_index_stats()` and `update_attstats()`, with `starelid` = the index[analyze.c#compute_index_stats](../../../../raw/postgres-12/src/backend/commands/analyze.c#L694-L843) [catalogs.sgml#pg-statistic-index-expressions](../../../../raw/postgres-12/doc/src/sgml/catalogs.sgml#L6346-L6404) | Stored until the next `ANALYZE` | Correlation in B-tree and BRIN costing; not general selectivity for a partial index[selfuncs.c#btcostestimate-correlation](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L6158-L6212) [selfuncs.c#examine_variable-expression-index-stats](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L4583-L4602) |

Two row counts are easy to confuse. The table row estimate (`rel->tuples`) counts every heap row. The partial index's `IndexOptInfo.tuples` counts only the rows the planner thinks the index holds. For a non-partial index the planner simply copies the first into the second, so the index's own `reltuples` never matters there. For a partial index the planner derives the second from the index's own stored `reltuples` and `relpages`, so an out-of-date `ANALYZE` result changes its costing.[plancat.c#get_relation_info-size](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L387-L407)

### Logic map

```text
WRITE PATH (CREATE INDEX, INSERT, non-HOT UPDATE)
  heap row ──► ExecQual(ii_Predicate)
                 ├─ false ─► no entry in this index (other indexes unaffected)
                 └─ true  ─► FormIndexDatum (evaluates expression keys) ─► index insert
  UPDATE first asks: did any column in ANY index's keys, expressions or
  predicate change, or did the new row leave the page?
                 ├─ no  ─► HOT update: no index gets an entry
                 └─ yes ─► non-HOT: every index runs the path above

PLANNING PATH (each query, each planning cycle)
  get_relation_info: indpred loaded, predOK = false
        │
  check_index_predicates: clauses = restrictions + movable join clauses
        │                          + equivalence-derived equalities
        ├─ predicate_implied_by(indpred, clauses) true  ─► predOK = true
        │      └─ not an UPDATE/DELETE/FOR UPDATE target?
        │             yes ─► drop implied quals from indrestrictinfo
        │             no  ─► keep them for EvalPlanQual recheck
        └─ false ─► predOK = false
                     ├─ plain index paths: index skipped
                     └─ bitmap OR arms: may still prove it per arm
  usable index ─► match clauses to keys (expression keys: equal())
               ─► genericcostestimate: selectivity of (quals AND
                  predicate clauses not implied by the quals)

STATISTICS PATH (standalone ANALYZE of one table)
  sample rows ─► per partial index: count rows passing predicate
              ─► tupleFract = passing / sampled
              ─► expression-column stats from passing rows only
              ─► index reltuples = ceil(tupleFract × table rows)
```

### How PostgreSQL stores and maintains a partial index

The SQL surface is ordinary `CREATE INDEX` with an optional trailing `WHERE predicate`. The same statement also accepts `UNIQUE`, `CONCURRENTLY`, an access method, expression keys, `INCLUDE` columns, storage parameters, and a tablespace.[create_index.sgml#synopsis](../../../../raw/postgres-12/doc/src/sgml/ref/create_index.sgml#L24-L30)

`transformIndexStmt()` transforms the predicate as `EXPR_KIND_INDEX_PREDICATE`.[parse_utilcmd.c#transformIndexStmt](../../../../raw/postgres-12/src/backend/parser/parse_utilcmd.c#L2584-L2641) The documentation says the predicate may refer only to columns of the indexed table, may not contain subqueries or aggregates, and must use only immutable functions and operators.[create_index.sgml#partial-index-description](../../../../raw/postgres-12/doc/src/sgml/ref/create_index.sgml#L65-L94) `CheckPredicate()` enforces the immutability rule in the source. Its comment says the parser has already rejected subqueries, aggregates, and window functions.[indexcmds.c#CheckPredicate](../../../../raw/postgres-12/src/backend/commands/indexcmds.c#L1503-L1530) Immutability matters later, because the planner's proof assumes the predicate gives the same answer at plan time and at run time.[predtest.c#predicate_implied_by](../../../../raw/postgres-12/src/backend/optimizer/util/predtest.c#L141-L147)

The catalog stores the predicate in `pg_index.indpred`, which is null for a non-partial index.[catalogs.sgml#pg-index-indpred](../../../../raw/postgres-12/doc/src/sgml/catalogs.sgml#L3938-L3951) In memory, the executor's `IndexInfo` keeps the executable predicate in `ii_Predicate`. The planner's [IndexOptInfo](../../../glossary.md#indexoptinfo) keeps it in `indpred`, together with the per-query `predOK` flag.[execnodes.h#IndexInfo](../../../../raw/postgres-12/src/include/nodes/execnodes.h#L153-L177) [pathnodes.h#IndexOptInfo](../../../../raw/postgres-12/src/include/nodes/pathnodes.h#L746-L821)

During an index build, the heap access method prepares the predicate with `ExecPrepareQual()`. It then discards each heap tuple for which `ExecQual()` is false, before it forms the index datum.[heapam_handler.c#partial-index-build-filter](../../../../raw/postgres-12/src/backend/access/heap/heapam_handler.c#L1198-L1211) [heapam_handler.c#heapam_index_build_range_scan](../../../../raw/postgres-12/src/backend/access/heap/heapam_handler.c#L1604-L1626)

During DML, `ExecInsertIndexTuples()` loops over the table's indexes. For each partial index it evaluates `ii_Predicate` and skips that index when the row fails it.[execIndexing.c#ExecInsertIndexTuples](../../../../raw/postgres-12/src/backend/executor/execIndexing.c#L313-L357) The skip is per index: the row still goes into every other index whose predicate it passes.

### Planner matching and plan shape

`RelationGetIndexPredicate()` reads `pg_index.indpred`, simplifies and canonicalizes it, converts it to an implicit-AND list, and caches the result in the relcache.[relcache.c#RelationGetIndexPredicate](../../../../raw/postgres-12/src/backend/utils/cache/relcache.c#L4713-L4778) `get_relation_info()` copies the expressions and predicate into `IndexOptInfo`, renumbers their variables for the relation being planned, and sets `predOK = false`.[plancat.c#get_relation_info-index-predicate](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L365-L382)

`check_index_predicates()` then collects the clauses it may assume true. These are the relation's restriction clauses, join clauses movable to the relation, and [equivalence class](../../../glossary.md#equivalence-class) equalities. It sets `predOK` when `predicate_implied_by(index->indpred, clauselist, false)` succeeds.[indxpath.c#check_index_predicates](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L3442-L3516)

The proof engine does more than the documentation suggests. The documentation says that apart from simple inequalities such as `x < 1` implying `x < 2`, the predicate must "exactly match part of the query's `WHERE` condition".[indices.sgml#partial-index-matching](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L899-L925) The pinned source also proves these cases:

| Proof the source attempts | Example with the docs' `orders` table | Source |
| --- | --- | --- |
| The predicate is identical to a query clause | `WHERE billed is not true` proves `billed is not true` | [predtest.c#predicate_implied_by_simple_clause](../../../../raw/postgres-12/src/backend/optimizer/util/predtest.c#L1113-L1121) |
| A strict clause on a value proves `value IS NOT NULL` | `order_nr = 3501` proves `order_nr IS NOT NULL` | [predtest.c#predicate_implied_by_simple_clause](../../../../raw/postgres-12/src/backend/optimizer/util/predtest.c#L1123-L1137) |
| AND and OR structure on either side is proved part by part; for example, an OR clause implies an OR predicate when each clause arm implies some predicate arm | `order_nr < 10 OR order_nr > 990` proves `order_nr < 50 OR order_nr > 800` | [predtest.c#predicate_implied_by_recurse](../../../../raw/postgres-12/src/backend/optimizer/util/predtest.c#L255-L300) |
| `IN (...)` and `= ANY (array)` lists of up to 100 elements are treated as OR (or AND) lists | `order_nr IN (1, 2, 3)` proves `order_nr < 10` | [predtest.c#MAX_SAOP_ARRAY_SIZE](../../../../raw/postgres-12/src/backend/optimizer/util/predtest.c#L39) [predtest.c#predicate_classify](../../../../raw/postgres-12/src/backend/optimizer/util/predtest.c#L816-L892) |
| Comparisons are proved through B-tree operator families, including immutable cross-type operators | `order_nr < 1` proves `order_nr < 2` | [predtest.c#operator_predicate_proof](../../../../raw/postgres-12/src/backend/optimizer/util/predtest.c#L1630-L1645) |

The proof still fails for many logically equivalent forms, so writing the query's condition in the same form as the predicate remains the safe practice. Because the documentation and the source disagree here, the difference is filed under [Open Questions](#open-questions).

Index-path generation then splits on `predOK`:

| Condition | Behavior | Consequence |
| --- | --- | --- |
| Non-partial index | No proof is needed | Normal key matching only |
| Partial index, `predOK = true` | Plain index and bitmap paths are built | The index competes on cost[indxpath.c#create_index_paths](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L258-L264) |
| Partial index, `predOK = false` | Plain paths skip the index | The index is unusable for this query, except as below |
| Partial index, `predOK = false`, query has an `OR` | `generate_bitmap_or_paths()` retries the proof using one OR arm plus the other clauses | One arm of a [bitmap scan](../../../glossary.md#bitmap-scan) OR can use the index[indxpath.c#generate_bitmap_or_paths-partial](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L1188-L1216) |

Plan shape also depends on the relation's role. For an ordinary relation, `check_index_predicates()` removes restriction clauses that the predicate already implies from `indrestrictinfo`, so an index scan does not test them again. For the target of `UPDATE`, `DELETE`, or `SELECT FOR UPDATE`, it keeps them. They must stay in the plan because [EvalPlanQual](../../../glossary.md#evalplanqual) rechecks a concurrently updated row against them.[indxpath.c#check_index_predicates](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L3484-L3532) [execMain.c#EvalPlanQual](../../../../raw/postgres-12/src/backend/executor/execMain.c#L2418-L2435)

Bitmap heap scans differ again. `create_bitmap_subplan()` adds the index predicate to the bitmap recheck conditions, because a [lossy bitmap](../../../glossary.md#lossy-bitmap) page must be rechecked row by row.[createplan.c#create_bitmap_scan_plan](../../../../raw/postgres-12/src/backend/optimizer/plan/createplan.c#L2968-L2987) [createplan.c#create_bitmap_subplan](../../../../raw/postgres-12/src/backend/optimizer/plan/createplan.c#L3228-L3253)

### Prepared statements and parameters

The documentation says parameterized clauses "do not work" with a partial index, because `x < ?` never implies `x < 2` for every value.[indices.sgml#partial-index-matching](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L914-L924) In the source that is true of a generic plan only.

A [prepared statement](../../../glossary.md#prepared-statement) runs with either a custom plan or a generic plan; see [Custom and generic plan](../../../glossary.md#custom-and-generic-plan).

1. **Parameter values are marked constant.** The extended-protocol Bind path, SQL `EXECUTE`, SPI, and PL/pgSQL mark bound parameters `PARAM_FLAG_CONST`.[postgres.c:1846-1850](../../../../raw/postgres-12/src/backend/tcop/postgres.c#L1846-L1850) [prepare.c:405](../../../../raw/postgres-12/src/backend/commands/prepare.c#L405) [spi.c:2459](../../../../raw/postgres-12/src/backend/executor/spi.c#L2459) [pl_exec.c:6380](../../../../raw/postgres-12/src/pl/plpgsql/src/pl_exec.c#L6380)
2. **A custom plan receives the values.** The plan cache builds a custom plan by passing the values as `boundParams`.[plancache.c#BuildCachedPlan](../../../../raw/postgres-12/src/backend/utils/cache/plancache.c#L863-L878)
3. **The planner turns them into constants.** `eval_const_expressions()` reads `root->glob->boundParams` and replaces a `PARAM_FLAG_CONST` parameter with a `Const`.[clauses.c#eval_const_expressions](../../../../raw/postgres-12/src/backend/optimizer/util/clauses.c#L2254-L2260) [clauses.c#eval_const_expressions_mutator-param](../../../../raw/postgres-12/src/backend/optimizer/util/clauses.c#L2340-L2385)
4. **The proof then sees a constant.** `order_nr < 5` can prove `order_nr < 10`, so the custom plan can use the partial index.[predtest.c#operator_predicate_proof](../../../../raw/postgres-12/src/backend/optimizer/util/predtest.c#L1630-L1645) [indxpath.c#check_index_predicates](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L3513-L3515)
5. **A generic plan gets no values.** The clause keeps its `Param`, so the proof fails and the partial index is ignored.[indices.sgml#partial-index-matching](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L920-L924) [indxpath.c#create_index_paths](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L258-L264)

Which plan runs depends on `plan_cache_mode`:

| `plan_cache_mode` | Plan chosen | Effect on a partial index |
| --- | --- | --- |
| `auto` (the boot default)[guc.c#plan_cache_mode](../../../../raw/postgres-12/src/backend/utils/misc/guc.c#L4504-L4514) | Custom plans for the first five executions, then the generic plan if its cost is below the average custom-plan cost including planning[plancache.c#choose_custom_plan](../../../../raw/postgres-12/src/backend/utils/cache/plancache.c#L1016-L1063) | Usable in custom plans. Once the generic plan wins, unusable. |
| `force_custom_plan` | Always custom[plancache.c#choose_custom_plan](../../../../raw/postgres-12/src/backend/utils/cache/plancache.c#L1032-L1035) | Usable on every execution, at the price of planning every time |
| `force_generic_plan` | Always generic | Never usable from a parameter |

`plan_cache_mode` is a `PGC_USERSET` setting, so it changes with `SET` for a session or transaction and needs no reload or restart; see [GUC context](../../../glossary.md#guc-context).[guc.c#plan_cache_mode](../../../../raw/postgres-12/src/backend/utils/misc/guc.c#L4504-L4514) Because the documentation states the parameter limitation without this condition, the discrepancy is filed under [Open Questions](#open-questions).

### Ordinary expression indexes as the baseline

An [expression index](../../../glossary.md#expression-index) is an index whose key is a function or scalar expression over table columns. The documentation's examples are `lower(col1)` for case-insensitive lookup and `(first_name || ' ' || last_name)` for full-name lookup.[indices.sgml#indexes-expressional](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L687-L753) The `CREATE INDEX` key list accepts either a column name or a parenthesized expression, and the functions and operators must be immutable.[create_index.sgml#synopsis](../../../../raw/postgres-12/doc/src/sgml/ref/create_index.sgml#L24-L30) [create_index.sgml#partial-index-description](../../../../raw/postgres-12/doc/src/sgml/ref/create_index.sgml#L43-L94)

In the catalog, `pg_index.indkey` holds zero for each expression key, and `pg_index.indexprs` holds one expression tree per zero entry. `pg_index.indpred` stays null for a non-partial index.[catalogs.sgml#pg-index-expressions-and-predicate](../../../../raw/postgres-12/doc/src/sgml/catalogs.sgml#L3880-L3951) The planner loads the expressions into `IndexOptInfo.indexprs`. Because the index is not partial, `get_relation_info()` sets `IndexOptInfo.tuples` to the table's estimate.[plancat.c#get_relation_info-size](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L387-L398)

Writes pay for the expression. `FormIndexDatum()` evaluates each expression key with `ExecEvalExprSwitchContext()` for every row that gets an entry.[index.c#FormIndexDatum](../../../../raw/postgres-12/src/backend/catalog/index.c#L2578-L2648) Searches do not recompute it, because the value is already stored in the index.[indices.sgml#index-expression-maintenance](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L736-L753)

Planning needs no predicate proof. The query clause only has to match the key and the operator family. `match_clause_to_indexcol()` accepts operator, function, scalar-array, row-comparison, boolean, and supported `IS NULL`/`IS NOT NULL` clauses. `match_index_to_operand()` compares the query operand to the stored `indexprs` tree with `equal()`, after stripping a relabel node.[indxpath.c#match_clause_to_indexcol](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L2317-L2425) [indxpath.c#match_index_to_operand](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L3811-L3887)

`ANALYZE` treats a non-partial expression index as a source of whole-table expression statistics. It sets `tupleFract = 1.0` and creates `VacAttrStats` only for expression columns.[analyze.c#do_analyze_rel-indexdata](../../../../raw/postgres-12/src/backend/commands/analyze.c#L427-L468) With no predicate, `ExecPrepareQual()` returns null for the empty list, so `compute_index_stats()` evaluates the expression for every sampled row.[execExpr.c#ExecInitQual](../../../../raw/postgres-12/src/backend/executor/execExpr.c#L188-L215) [analyze.c#compute_index_stats-expression-values](../../../../raw/postgres-12/src/backend/commands/analyze.c#L730-L825) `examine_variable()` then reads that index's `pg_statistic` row for any query expression that matches the key, as long as the index has no predicate. A loaded `get_index_stats_hook` can override that test; see [How the planner uses those statistics](#how-the-planner-uses-those-statistics).[selfuncs.c#examine_variable-expression-index-stats](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L4583-L4602)

Expression indexes share two restrictions with partial indexes. Neither can back a primary-key or unique constraint through `USING INDEX`, and neither can serve as a [replica identity](../../../glossary.md#replica-identity) index.[parse_utilcmd.c#expression-index-constraint-reject](../../../../raw/postgres-12/src/backend/parser/parse_utilcmd.c#L2081-L2086) [tablecmds.c#ATExecReplicaIdentity](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L13964-L13975) Neither can be the referenced key of a foreign key either.[tablecmds.c#transformFkeyCheckAttrs](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L9568-L9577)

The regression suite covers ordinary expression indexes directly. `create_index.sql` builds unique functional and expression indexes (`textcat(f1,f2)` and `(f1 || f2)`), checks duplicate-key errors, shows the index metadata, and rejects an expression of pseudo-type `record`.[create_index.sql#functional-and-expression-index-tests](../../../../raw/postgres-12/src/test/regress/sql/create_index.sql#L390-L429) [create_index.out#functional-and-expression-index-tests](../../../../raw/postgres-12/src/test/regress/expected/create_index.out#L1270-L1344)

### Partial indexes on expressions

An index can have both an expression key and a predicate. The documentation's example is a unique index on `(target IS NULL)` with `WHERE target IS NULL`, which allows only one null.[create_index.sgml#synopsis](../../../../raw/postgres-12/doc/src/sgml/ref/create_index.sgml#L24-L30) [indices.sgml#partial-expression-one-null](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L959-L967)

The catalog stores the two parts independently: `indkey` and `indexprs` for the keys, `indpred` for the predicate.[catalogs.sgml#pg-index-expressions-and-predicate](../../../../raw/postgres-12/doc/src/sgml/catalogs.sgml#L3880-L3951) `IndexOptInfo` mirrors the split with `indexprs` and `indpred`/`predOK`.[pathnodes.h#IndexOptInfo](../../../../raw/postgres-12/src/include/nodes/pathnodes.h#L746-L821)

The combination changes each stage as follows:

| Stage | Ordinary expression index | Partial expression index |
| --- | --- | --- |
| Write | Expression evaluated for every row | Predicate evaluated first; expression evaluated only for passing rows[heapam_handler.c#heapam_index_build_range_scan](../../../../raw/postgres-12/src/backend/access/heap/heapam_handler.c#L1604-L1626) [execIndexing.c#ExecInsertIndexTuples](../../../../raw/postgres-12/src/backend/executor/execIndexing.c#L336-L357) [index.c#FormIndexDatum](../../../../raw/postgres-12/src/backend/catalog/index.c#L2578-L2648) |
| Planning | Key match only | Predicate proof (`predOK`), then key match[indxpath.c#check_index_predicates](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L3506-L3516) [indxpath.c#match_opclause_to_indexcol](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L2547-L2629) [indxpath.c#match_index_to_operand](../../../../raw/postgres-12/src/backend/optimizer/path/indxpath.c#L3811-L3887) |
| `ANALYZE` sample | Every sampled row | Only sampled rows that pass the predicate[analyze.c#compute_index_stats](../../../../raw/postgres-12/src/backend/commands/analyze.c#L769-L775) |
| General expression selectivity (no statistics hook) | Uses the index's statistics | Ignores them, because the subset "probably" does not reflect the whole table[selfuncs.c#examine_variable-expression-index-stats](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L4571-L4602) |
| B-tree or BRIN correlation | Reads the index's statistics | Also reads them; there is no predicate check in that lookup[selfuncs.c#btcostestimate-correlation](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L6158-L6212) [selfuncs.c#brincostestimate-expression-stats](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L7088-L7124) |

The partitioned-index regression test covers the combination. It creates a parent index on `((b + a)) WHERE a > 1`, then shows that `ALTER INDEX ... ATTACH PARTITION` rejects child indexes whose expression or predicate differs and accepts the matching one.[indexing.sql#partial-expression-index-attach](../../../../raw/postgres-12/src/test/regress/sql/indexing.sql#L318-L338) [indexing.out#partial-expression-index-attach](../../../../raw/postgres-12/src/test/regress/expected/indexing.out#L638-L674)

### Pros

- **Smaller index, fewer index inserts for excluded rows.** The documentation calls avoiding common values a major use. It says this shrinks the index, speeds the queries that use it, and speeds many updates because the index need not always be updated.[indices.sgml#exclude-common-values](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L774-L784) The skip is per index and per inserted row version.[execIndexing.c#ExecInsertIndexTuples](../../../../raw/postgres-12/src/backend/executor/execIndexing.c#L336-L353)
- **A focused access path for a hot subset.** The documentation's unbilled-orders index, `CREATE INDEX orders_unbilled_index ON orders (order_nr) WHERE billed is not true`, serves queries on unbilled orders even when they filter on a different column such as `amount`.[indices.sgml#exclude-uninteresting-values](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L845-L897)
- **Conditional uniqueness.** A unique partial index constrains only rows that satisfy the predicate. The documentation uses it for one successful test per subject and target, and for allowing only one null.[indices.sgml#partial-unique-index](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L927-L968)
- **Planner steering.** A partial index can be made unavailable to a query that unusual data distributions would otherwise send to it.[indices.sgml#override-plan-choices](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L970-L981)
- **`ON CONFLICT` inference works when the `WHERE` clause covers the predicate.** `infer_arbiter_indexes()` accepts a partial unique index only when the `ON CONFLICT ... WHERE` clause implies its predicate.[plancat.c#infer_arbiter_indexes](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L803-L810)
- **Uniqueness proofs when the predicate holds.** `has_unique_index()` and `examine_variable()` treat a single-column unique partial index as unique when `predOK` is true for the query.[plancat.c#has_unique_index](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L2039-L2051) [selfuncs.c#examine_variable-expression-index-stats](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L4562-L4569)

### Cons and restrictions

- **Matching is limited and happens at planning time.** The proof engine handles the forms in the [proof table](#planner-matching-and-plan-shape) and nothing more general. A condition the engine cannot match leaves the index unused.[predtest.c#predicate_implied_by](../../../../raw/postgres-12/src/backend/optimizer/util/predtest.c#L113-L150)
- **Generic plans cannot use the index from a parameter.** Under the default `plan_cache_mode = auto`, a prepared statement can switch to its generic plan after five custom plans, and the generic plan cannot prove the predicate; see [Prepared statements and parameters](#prepared-statements-and-parameters).[plancache.c#choose_custom_plan](../../../../raw/postgres-12/src/backend/utils/cache/plancache.c#L1043-L1063)
- **The predicate can go stale.** An index that excludes common values needs those values chosen in advance, suits stable distributions, and may need recreating when the distribution changes.[indices.sgml#partial-index-distribution-maintenance](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L836-L842)
- **Excluded values can never use that index**, even where an index scan would pay off.[indices.sgml#exclude-uninteresting-values](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L845-L854)
- **Every write evaluates the predicate.** An excluded row avoids the index insert but not the `ExecQual()` call.[execIndexing.c#ExecInsertIndexTuples](../../../../raw/postgres-12/src/backend/executor/execIndexing.c#L336-L353)
- **Predicate columns block HOT updates for every row.** `RelationGetIndexAttrBitmap()` adds the columns of every index predicate to the set of indexed columns.[relcache.c#RelationGetIndexAttrBitmap-predicate](../../../../raw/postgres-12/src/backend/utils/cache/relcache.c#L4956-L4960) `heap_update()` uses that set, and allows a HOT update only when none of those columns changed and the new row stays on the same page.[heapam.c#heap_update-hot-attrs](../../../../raw/postgres-12/src/backend/access/heap/heapam.c#L2963) [heapam.c#heap_update-hot-decision](../../../../raw/postgres-12/src/backend/access/heap/heapam.c#L3591-L3601) So an `UPDATE` that changes `billed` on an already-billed order, a row the partial index never held, is still not HOT. Every other index on `orders` then gets a new entry for the new row version.[heapam_handler.c:344](../../../../raw/postgres-12/src/backend/access/heap/heapam_handler.c#L344) [nodeModifyTable.c:1446](../../../../raw/postgres-12/src/backend/executor/nodeModifyTable.c#L1446) See [HOT-blocking column](../../../glossary.md#hot-blocking-column).
- **No primary-key or unique constraint through `USING INDEX`.** The parser rejects `ALTER TABLE ... ADD CONSTRAINT ... USING INDEX` when the index has a predicate.[parse_utilcmd.c#partial-index-constraint-reject](../../../../raw/postgres-12/src/backend/parser/parse_utilcmd.c#L2088-L2093)
- **No foreign-key target.** `transformFkeyCheckAttrs()` accepts a referenced unique index only when `indpred` is null, so a partial unique index cannot back a foreign key.[tablecmds.c#transformFkeyCheckAttrs](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L9568-L9577)
- **No replica identity.** `ALTER TABLE ... REPLICA IDENTITY USING INDEX` fails with `cannot use partial index ... as replica identity`.[tablecmds.c#ATExecReplicaIdentity](../../../../raw/postgres-12/src/backend/commands/tablecmds.c#L13970-L13975)
- **No [`CLUSTER`](../../../glossary.md#cluster).** `check_index_is_clusterable()` rejects an index with `indpred`, because it may not cover every row.[cluster.c#check_index_is_clusterable](../../../../raw/postgres-12/src/backend/commands/cluster.c#L469-L479)
- **Uniqueness deductions need `predOK`.** `has_unique_index()` ignores a partial unique index unless the query implies its predicate.[plancat.c#has_unique_index](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L2039-L2051)

### Statistics generated by `ANALYZE`

`ANALYZE` samples table contents into `pg_statistic`, and the planner uses those statistics to choose plans.[analyze.sgml#description](../../../../raw/postgres-12/doc/src/sgml/ref/analyze.sgml#L41-L47) A column's statistics include [most common values and a histogram](../../../glossary.md#most-common-values-and-histogram), the null fraction, average width, and a distinct-value estimate. The statistics target controls the sample size and the MCV and histogram limits.[analyze.sgml#notes-statistics](../../../../raw/postgres-12/doc/src/sgml/ref/analyze.sgml#L188-L239) [pg_statistic.h#pg_statistic-fields](../../../../raw/postgres-12/src/include/catalog/pg_statistic.h#L36-L83) The scalar analyzer asks for 300 × the target rows; `default_statistics_target` defaults to 100, giving 30,000.[analyze.c#std_typanalyze-minrows](../../../../raw/postgres-12/src/backend/commands/analyze.c#L1700) [guc.c#default_statistics_target](../../../../raw/postgres-12/src/backend/utils/misc/guc.c#L1986-L1992)

For each partial index, `compute_index_stats()` runs the predicate against each sampled heap row and counts the rows that pass. It sets `tupleFract = numindexrows / numrows`, estimates `totalindexrows = ceil(tupleFract * totalrows)`, and computes expression-column statistics from the passing rows only.[analyze.c#compute_index_stats](../../../../raw/postgres-12/src/backend/commands/analyze.c#L694-L843)

`ANALYZE` stores `pg_statistic` rows for index expression columns, with `starelid` set to the index. It stores none for plain index columns, because the table's own column statistics already cover them.[catalogs.sgml#pg-statistic-index-expressions](../../../../raw/postgres-12/doc/src/sgml/catalogs.sgml#L6346-L6404) In the source, `do_analyze_rel()` calls `examine_attribute()` only for index columns whose `ii_IndexAttrNumbers[i]` is zero, and only when no explicit column list was given.[analyze.c#do_analyze_rel-indexdata](../../../../raw/postgres-12/src/backend/commands/analyze.c#L427-L468) `examine_attribute()` takes the type, typmod, and collation from the expression tree.[analyze.c#examine_attribute](../../../../raw/postgres-12/src/backend/commands/analyze.c#L870-L953)

`update_attstats()` writes the row: `starelid`, `staattnum`, `stainherit`, `stanullfrac`, `stawidth`, `stadistinct`, and the slot kinds, operators, collations, numbers, and values.[analyze.c#update_attstats](../../../../raw/postgres-12/src/backend/commands/analyze.c#L1395-L1457) [analyze.c#update_attstats-slots](../../../../raw/postgres-12/src/backend/commands/analyze.c#L1469-L1543) Scalar statistics can fill MCV, histogram, and correlation slots. `pg_statistic.h` defines the correlation slot as one coefficient from -1 to +1.[analyze.c#std_typanalyze](../../../../raw/postgres-12/src/backend/commands/analyze.c#L1648-L1699) [analyze.c#compute_scalar_stats](../../../../raw/postgres-12/src/backend/commands/analyze.c#L2328-L2649) [pg_statistic.h#statistic-kinds](../../../../raw/postgres-12/src/include/catalog/pg_statistic.h#L168-L209)

A standalone `ANALYZE` also writes the index's whole-relation statistics ([reltuples and relpages](../../../glossary.md#reltuples-and-relpages)). It passes `RelationGetNumberOfBlocks()` and `ceil(tupleFract * totalrows)` to `vac_update_relstats()`.[analyze.c#index-relstats-update](../../../../raw/postgres-12/src/backend/commands/analyze.c#L607-L631) [vacuum.c#vac_update_relstats](../../../../raw/postgres-12/src/backend/commands/vacuum.c#L1117-L1190) The two exceptions are in the next section.

### How the planner uses those statistics

**Index size.** `get_relation_info()` fills `IndexOptInfo.pages` and `IndexOptInfo.tuples`. For a non-partial index, `tuples` is the table estimate. For a partial index it calls `estimate_rel_size()` and caps the result at the table estimate.[plancat.c#get_relation_info-size](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L387-L407) For an index, `estimate_rel_size()` reports the live block count as `pages`. It discounts one metapage from both the live and the stored page counts, takes the density `reltuples / relpages` from `pg_class`, and returns `rint(density × live pages)`.[plancat.c#estimate_rel_size-index](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L955-L1026)

**Index selectivity.** `genericcostestimate()` calls `add_predicate_to_index_quals()`, which ANDs onto the index quals every predicate clause that the quals do not already imply. It then computes `indexSelectivity` from that list against the table. It estimates visited tuples as `indexSelectivity × index->rel->tuples`, divides by the number of `ScalarArrayOpExpr` scans, caps the result at `index->tuples`, and charges a pro-rata share of `index->pages`.[selfuncs.c#genericcostestimate](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L5679-L5763) [selfuncs.c#add_predicate_to_index_quals](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L5878-L5916)

That step can underestimate. The source comment says the redundancy check catches cases such as `x = 42` against `WHERE x >= 40 AND x < 50`, but misses many others. When it misses one, `clauselist_selectivity()` counts the same restriction twice. The result is a too-low selectivity, which biases the planner toward partial indexes.[selfuncs.c#add_predicate_to_index_quals](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L5878-L5890) The estimate is therefore better informed than one that ignores the predicate, but not reliably more accurate.

**Column statistics for the table.** Selectivity for a table column reads that column's `pg_statistic` row through `SearchSysCache3(STATRELATTINH, ...)`.[selfuncs.c#examine_simple_variable](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L4708-L4737) Equality checks the MCV list and spreads the remaining non-null, non-MCV fraction over the other distinct values.[selfuncs.c#var_eq_const](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L289-L420) Inequalities combine MCV selectivity with histogram selectivity over the rest.[selfuncs.c#scalarineqsel](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L651-L686) [selfuncs.c#mcv_selectivity](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L716-L744) [selfuncs.c#histogram_selectivity](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L791-L828)

**Expression statistics for selectivity.** `examine_variable()` matches a query expression to an expression index column. It always takes uniqueness from a matching unique index whose predicate is absent or proven. It reads the index's statistics only when the index is non-partial, because a partial index "probably" does not reflect the whole table.[selfuncs.c#examine_variable-expression-index-stats](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L4562-L4602)

That rule has one override. By default `get_index_stats_hook` is null.[selfuncs.c#get_index_stats_hook](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L146-L148) An extension that sets this [hook](../../../glossary.md#hook) is called before the `indpred == NIL` test, and when it returns true the planner uses whatever statistics it supplied, including for a partial index.[selfuncs.c#examine_variable-expression-index-stats](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L4578-L4602)

**Expression statistics for correlation.** B-tree costing reads correlation for the index's first column. For an expression column, it looks up the index's own `pg_statistic` row with no predicate check, so a partial expression index's correlation feeds the cost.[selfuncs.c#btcostestimate-correlation](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L6119-L6212) BRIN costing does the same for its expression columns.[selfuncs.c#brincostestimate-expression-stats](../../../../raw/postgres-12/src/backend/utils/adt/selfuncs.c#L7088-L7124) That correlation was computed only from predicate-passing sample rows, which is the subset the index actually holds.[analyze.c#compute_index_stats](../../../../raw/postgres-12/src/backend/commands/analyze.c#L769-L843)

### Worked example: from ANALYZE sample to planner tuple count

The numbers below are hypothetical inputs chosen to show the arithmetic. They were not produced by running PostgreSQL. The table and index are the documentation's `orders` and `orders_unbilled_index ... WHERE billed is not true`.[indices.sgml#exclude-uninteresting-values](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L860-L869)

Inputs:

| Input | Value | Where it would come from |
| --- | --- | --- |
| Sample size | 30,000 rows | 300 × `default_statistics_target` (100)[analyze.c#std_typanalyze-minrows](../../../../raw/postgres-12/src/backend/commands/analyze.c#L1700) |
| Sampled rows with `billed is not true` | 1,500 | Predicate test in `compute_index_stats()` |
| Table row estimate (`totalrows`) | 2,000,000 | `ANALYZE`'s table estimate |
| Index blocks when `ANALYZE` ran | 301, including the metapage | `RelationGetNumberOfBlocks()` |
| Index blocks at a later planning time | 361 | `RelationGetNumberOfBlocks()` |

Calculation:

1. `tupleFract = 1,500 / 30,000 = 0.05`.[analyze.c#compute_index_stats](../../../../raw/postgres-12/src/backend/commands/analyze.c#L821)
2. Index `reltuples = ceil(0.05 × 2,000,000) = 100,000`; `relpages = 301`.[analyze.c#index-relstats-update](../../../../raw/postgres-12/src/backend/commands/analyze.c#L619-L626)
3. Later, `estimate_rel_size()` discounts the metapage: stored pages 300, live pages 360.[plancat.c#estimate_rel_size-index](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L985-L994)
4. Density `= 100,000 / 300 ≈ 333.3` entries per page.[plancat.c#estimate_rel_size-index](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L996-L998)
5. `IndexOptInfo.tuples = rint(333.3 × 360) = 120,000`, below the 2,000,000 cap, and `IndexOptInfo.pages = 361`.[plancat.c#estimate_rel_size-index](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L1026) [plancat.c#get_relation_info-size](../../../../raw/postgres-12/src/backend/optimizer/util/plancat.c#L399-L407)

The result shows the mix of stored and live state. The density comes from the last statistics update, but the page count is current. So the planner assumes 20% more unbilled orders as soon as the index grows by 20%, without another `ANALYZE`. If the growth were bloat rather than new entries, that assumption would be wrong.

### Regression coverage

The v12 regression suite creates B-tree partial indexes on `onek2`, with predicates on `unique1` and `stringu1`.[create_index.sql#btree-partial-indexes](../../../../raw/postgres-12/src/test/regress/sql/create_index.sql#L63-L72) The `select` test runs `ANALYZE onek2` first, because the planner probably will not choose an index scan without statistics.[select.sql#partial-btree-indexes](../../../../raw/postgres-12/src/test/regress/sql/select.sql#L59-L91) [select.out#partial-btree-indexes](../../../../raw/postgres-12/src/test/regress/expected/select.out#L206-L293)

The same file covers a usable partial index, a predicate-implied scan with no filter retest, an update target that keeps the filter, an inapplicable partial index that falls back to a sequential scan, and bitmap scans that recheck the predicate.[select.sql#partial-index-planning](../../../../raw/postgres-12/src/test/regress/sql/select.sql#L191-L234) [select.out#partial-index-plans](../../../../raw/postgres-12/src/test/regress/expected/select.out#L737-L899)

No regression test covers the parameter case: a prepared statement switching from a custom plan that uses a partial index to a generic plan that cannot. No test covers HOT updates blocked by a predicate column either. This page found neither in `create_index.sql`, `select.sql`, or `indexing.sql`.

### Final causal summary

The predicate is stored in `pg_index.indpred`. On every write, the executor evaluates it per index, so excluded rows add no entry to that index. But predicate columns count as indexed for HOT, so changing them makes every index take a new entry.

At planning time, `predicate_implied_by()` must prove the predicate from the query's clauses, with parameters visible only in custom plans. If the proof succeeds, `predOK` makes the index usable and implied quals drop out of non-target scans.

Costing then ANDs the unproven predicate clauses into the selectivity, which can come out too low. It scales the index's stored density, from the last `CREATE INDEX`, `VACUUM`, or standalone `ANALYZE`, by the index's live page count. Expression statistics of a partial index feed B-tree and BRIN correlation, but not general selectivity.

The next `ANALYZE` (without `VACUUM`) or `VACUUM` refreshes that density. Recreating the index is the only way to change the predicate.

## Open Questions

- **Documentation understates the proof engine.** `indices.sgml` says that, apart from simple inequality implications, the predicate must exactly match part of the query's `WHERE` condition.[indices.sgml#partial-index-matching](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L907-L918) The source also proves `IS NOT NULL` from strict clauses, works through AND/OR structure, and expands small `IN` lists.[predtest.c#predicate_implied_by_simple_clause](../../../../raw/postgres-12/src/backend/optimizer/util/predtest.c#L1123-L1137) [predtest.c#predicate_classify](../../../../raw/postgres-12/src/backend/optimizer/util/predtest.c#L816-L892) This page follows the source. A measured `EXPLAIN` of each form would confirm it, but this page runs no measurement.
- **Documentation states the parameter limitation without the generic-plan condition.** `indices.sgml` says parameterized clauses do not work with a partial index.[indices.sgml#partial-index-matching](../../../../raw/postgres-12/doc/src/sgml/indices.sgml#L914-L924) The source substitutes `PARAM_FLAG_CONST` values in custom plans, which the default `plan_cache_mode = auto` uses for at least the first five executions.[clauses.c#eval_const_expressions_mutator-param](../../../../raw/postgres-12/src/backend/optimizer/util/clauses.c#L2370-L2385) [plancache.c#choose_custom_plan](../../../../raw/postgres-12/src/backend/utils/cache/plancache.c#L1043-L1045) This page follows the source.
- **No common concept page.** PostgreSQL 12 has no `common-concepts/` pages. A `partial-index` concept page would hold the storage and planner mechanics that this page and other v12 indexing pages repeat; it needs its own request.
