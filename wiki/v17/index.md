Eight v17 behaviors are cited as the reason each rule exists: no single contrib function answers the question (`pgstat_relation` refuses GIN outright, `pgstatginindex` reads three metapage fields and no second page, and `contrib/amcheck` 1.4 has no GIN verifier); the entry tree never deletes a tuple, so dead keys survive every VACUUM and die only in a rebuild; a deleted page is reusable only once `GinPageIsRecyclable`'s horizon test passes, and `ginvacuumcleanup` re-reads the relation length rather than truncating, so waste is internal capacity and not returned bytes; free space means insertion capacity on an entry page (`PageGetFreeSpace` plus a line pointer) and a physical gap on a data leaf (`GinDataLeafPageGetFreeSpace` = `PageGetExactFreeSpace`); pending-list pages are deferred work whose flush drives keys through `ginEntryInsert` and can allocate through `GinNewBuffer`; the metapage's page counts are written by `ginvacuumcleanup` alone and an `analyze_only` call is a no-op outside an autovacuum worker; and `get_raw_page_internal` opens and closes the relation per call, so a multi-page census of a busy index is a sequence of instants. Also pins the three ways index cleanup silently does not run (`INDEX_CLEANUP` disabled, the wraparound failsafe, and the bypass that keeps cleanup), why `SHARE` is too weak (a plain `REINDEX INDEX` takes a self-compatible `ShareLock` on the table), the one hole no SQL lock closes (`gin_clean_pending_list` locks only the index and `LOCK TABLE` refuses an index), that the measurement lock's privilege is `MAINTAIN`/`UPDATE`/`DELETE`/`TRUNCATE` rather than `SELECT`, that a free index page reads back `MaxFSMRequestSize` rather than the `BLCKSZ - 1` the FSM was told, that the oracle is `maintenance_work_mem`-dependent and must be labelled, and that GIN has no `fillfactor` so density has no cross-opclass reference. **Extended on 2026-09-15 with the autovacuum, VACUUM, ANALYZE and auto-analyze rules ported from the sibling B-tree page, all binding**, which makes the churn phase end in a fixed order - the recipe's writes, the settle step, the maintenance step, then the census: a **maintenance assumption** in three parts (`VACUUM ANALYZE` on every table the churn touched before the decide phase; neither `autovacuum = off` nor `autovacuum_enabled = false` exempts a table; no fixture may leave churn unmaintained), the launcher's three threshold formulas recorded with their defaults, contexts and apply scopes but deliberately **not applied** on the vacuum side, and a **simulated auto-analyze census** that recomputes `relation_needs_vacanalyze`'s strictly-greater analyze test per table from the effective reloption-or-GUC values, with the negative-`reltuples` clamp, the `autovacuum_enabled` short circuit and two statistics-publication points. The port is not a copy, because a foreground `VACUUM ANALYZE` is **not** a faithful stand-in on GIN: `analyze_rel` enters ANALYZE-only index cleanup only outside a `VACUUM ANALYZE` and its comment names GIN as the only core AM that does not no-op there, so a worker's bare `ANALYZE` flushes the pending list and any other backend's returns at once. A fixture that models the auto-analyze-only state therefore runs `ANALYZE` **plus** `gin_clean_pending_list()`, and the page names the three ways that differs from the worker's path - `full_clean` true versus false, an index `RowExclusiveLock` with an ownership check versus the worker's table lock, and neither refreshing the metapage counts, so such a fixture is stale by construction, cannot claim the settle step and loses the metapage cross-check. Twelve open questions now, led by the absent corpus and including the six the port opened: the unsimulated vacuum side, the two stand-in differences that stand, the cross-check an analyze-only fixture loses, the unprovable second publication point, the `VACUUM`-written index count the mandatory `ANALYZE` now always overwrites, and the fact that no previously filed run was produced under either new rule. **2026-09-15: `The maintenance must not be defeated` added**, the same five forbidden states as the other two protocol pages, with a GIN-specific sting: with the horizon pinned `ginbulkdelete` never runs while `ginvacuumcleanup`'s `stats == NULL` branch still flushes the pending list, walks every block and rewrites the metapage counters, so **every settle-step proof passes with no dead entry removed**. The rule separates that from the expected one-`VACUUM` lag on freshly deleted pages, adds an entry-side proof obligation beside the settle proof, names three declared exceptions (the coverage-required held-snapshot fixture, the coverage-required index-cleanup-disabled fixture, and the measurement lock, which may not be held across either step), and files the one-sided proof as the 13th open question.
