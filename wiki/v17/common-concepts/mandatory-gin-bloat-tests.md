## Definition

The mandatory GIN bloat tests are this wiki's shared **measurement protocol** for any claim about how many bytes a PostgreSQL 17 [GIN](../../glossary.md#gin) index is wasting, or how many a rebuild would return. The protocol fixes eight things and nothing else: the five phases every scored fixture runs, the settle step that must be proven to have completed before a [page](../../glossary.md#page) is read, the maintenance step and census that stand in for [autovacuum](../../glossary.md#autovacuum) and auto-analyze so that no fixture is scored against unmaintained churn, the prohibition on defeating that maintenance, because on GIN a [`VACUUM`](../../glossary.md#vacuum) that removes no entry still settles the index and satisfies every settle-step proof, the [`SHARE ROW EXCLUSIVE`](../../glossary.md#lock-mode) measurement lock that makes a census comparable instead of merely describable, the single oracle - a measured [`REINDEX INDEX`](../../glossary.md#reindex) bracketed by [`pg_relation_size(index, 'main')`](../../glossary.md#relation-size-functions) - the way a published quantity must be declared as a lower bound, an upper bound or a level before it is scored, and the four cross-checks plus the reading rules that decide which numbers may be published as [bloat](../../glossary.md#bloat) at all. It deliberately does **not** define a fixture corpus: the numbered GIN fixtures, their recipes and their results stay on the question page that runs them, and this page is what that page must state it followed. Every scored fixture assumes that normal autovacuum and auto-analyze maintain every table, and stands in for both by hand: after its churn it runs `VACUUM ANALYZE` on every table the churn touched, and a fixture whose point is an auto-analyze also runs the [pending-list](../../glossary.md#pending-list) flush that only an autovacuum worker's [`ANALYZE`](../../glossary.md#statistics) performs. A GIN waste claim is not "tested" in this wiki until it has been produced under these phases, in a maintained state, against this oracle, with a declared kind per published column. Beside those eight requirements the page recommends, without requiring it, a procedure that proves from the statement's own report that the maintenance `VACUUM` did all its work and escalates when it did not; see [Recommended: proving VACUUM did all its work](#recommended-proving-vacuum-did-all-its-work).

## Why It Exists

Nine properties of the v17 engine make a plausible GIN waste reading wrong, and each is the reason one protocol rule exists.

**No single instrument answers the question, so every method is a composite.** [`pgstattuple`](../../glossary.md#pgstattuple) refuses GIN outright: `pgstat_relation` dispatches on `relam` and the GIN arm falls into the "not supported" error ([pgstattuple.c#pgstat_relation-gin](../../../raw/postgres-17/contrib/pgstattuple/pgstattuple.c#L260-L296)). `pgstatginindex` accepts a GIN index but reads three fields from [block](../../glossary.md#block) 0 and returns, never touching a second page ([pgstatindex.c#pgstatginindex_internal](../../../raw/postgres-17/contrib/pgstattuple/pgstatindex.c#L506-L577), [pgstatindex.c#GinIndexStat](../../../raw/postgres-17/contrib/pgstattuple/pgstatindex.c#L97-L108)). [`contrib/amcheck`](../../glossary.md#amcheck) 1.4 ships [B-tree](../../glossary.md#b-tree) and [heap](../../glossary.md#heap) verifiers only, so there is no structural GIN verifier to borrow page counts from ([amcheck.control:3](../../../raw/postgres-17/contrib/amcheck/amcheck.control#L3), [amcheck--1.3--1.4.sql#bt-only](../../../raw/postgres-17/contrib/amcheck/amcheck--1.3--1.4.sql#L13-L25)). A composite instrument has no single refusal to hide behind, which is why the protocol scores the number rather than the tool.

**The entry tree never deletes a [tuple](../../glossary.md#tuple).** VACUUM removes deletable [TIDs](../../glossary.md#tid) from [posting lists](../../glossary.md#posting-list) and deletes emptied [posting-tree](../../glossary.md#posting-tree) pages, but it deletes neither tuples nor pages from the entry tree, and the GIN README states that as the reason entry-tree leaves need no dedicated high key ([README#page-deletion](../../../raw/postgres-17/src/backend/access/gin/README#L389-L396), [README#concurrency-highkey](../../../raw/postgres-17/src/backend/access/gin/README#L309-L314)). An entry tuple for a key that no longer occurs therefore survives every VACUUM and dies only in a rebuild, so any quantity a method calls "payload" is not rebuild-invariant.

**A deleted page is not a reclaimable page until the horizon moves, and GIN never truncates.** `ginDeletePage` sets `GIN_DELETED` and stamps the next [transaction id](../../glossary.md#transaction-id) into `pd_prune_xid` ([ginvacuum.c#ginDeletePage-setdeleted](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L187-L192), [ginblock.h#GinPageGetDeleteXid](../../../raw/postgres-17/src/include/access/ginblock.h#L132-L138)); `GinPageIsRecyclable` accepts a page only if it is new, or deleted with an invalid delete xid, or deleted with one `GlobalVisCheckRemovableXid` has moved past ([ginvacuum.c#GinPageIsRecyclable](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L805-L829)). `ginvacuumcleanup` records the recyclable ones in the [FSM](../../glossary.md#free-space-map) and then re-reads the [relation](../../glossary.md#relation) length rather than shortening it ([ginvacuum.c#ginvacuumcleanup-census](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L752-L789), [ginvacuum.c#ginvacuumcleanup-relength](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L794-L802)), and `GinNewBuffer` hands those pages back out inside the same index before extending the file ([ginutil.c#GinNewBuffer](../../../raw/postgres-17/src/backend/access/gin/ginutil.c#L299-L335)). Dead pages are therefore internal capacity, not returned bytes, which is why the oracle has to be a measured rebuild and not a page census.

**Free space means two different things on the two live page classes.** GIN's own free-space test on a data leaf is `GinDataLeafPageGetFreeSpace`, defined as `PageGetExactFreeSpace`, which is `pd_upper - pd_lower` with no allowance for a [line pointer](../../glossary.md#line-pointer) ([ginblock.h#GinDataLeafPageGetFreeSpace](../../../raw/postgres-17/src/include/access/ginblock.h#L287), [bufpage.c#PageGetExactFreeSpace](../../../raw/postgres-17/src/backend/storage/page/bufpage.c#L952-L973)). On an entry page the comparable engine test is `entryIsEnoughSpace`, which uses `PageGetFreeSpace` and adds `sizeof(ItemIdData)` to what it needs, because a new tuple also needs a line pointer ([ginentrypage.c#entryIsEnoughSpace](../../../raw/postgres-17/src/backend/access/gin/ginentrypage.c#L458-L482), [bufpage.c#PageGetFreeSpace](../../../raw/postgres-17/src/backend/storage/page/bufpage.c#L898-L923)). The same subtraction is insertion capacity on one class and a physical gap on the other, so the protocol forbids publishing their sum as a bound.

**Pending-list pages are deferred work, and flushing them can allocate.** With `fastupdate` on, inserts land in a linked list of `GIN_LIST` pages whose head, tail and counters live in the [metapage](../../glossary.md#metapage), and the documentation names the four events that merge them into the main structure ([ginblock.h#GinMetaPageData](../../../raw/postgres-17/src/include/access/ginblock.h#L55-L101), [gin.sgml#GIN-Fast-Update](../../../raw/postgres-17/doc/src/sgml/gin.sgml#L500-L537)). The merge is `ginInsertCleanup`, which drives the accumulated keys through `ginEntryInsert` ([ginfast.c#ginInsertCleanup](../../../raw/postgres-17/src/backend/access/gin/ginfast.c#L776-L783), [ginfast.c#flush-entry-insert](../../../raw/postgres-17/src/backend/access/gin/ginfast.c#L926-L933)), and a split on that path takes a new page from `GinNewBuffer` ([ginbtree.c#split-newbuffer](../../../raw/postgres-17/src/backend/access/gin/ginbtree.c#L463-L466), [gindatapage.c#dataSplit-newbuffer](../../../raw/postgres-17/src/backend/access/gin/gindatapage.c#L1822-L1826)). Settling the index is part of the measurement, and it is not free.

**The metapage's page counts are written by one caller only.** `nTotalPages`, `nEntryPages`, `nDataPages` and `nEntries` are documented in the struct as "accurate as of last VACUUM" ([ginblock.h#planner-stats](../../../raw/postgres-17/src/include/access/ginblock.h#L77-L83)), are written by `ginvacuumcleanup` through `ginUpdateStats` ([ginvacuum.c#ginvacuumcleanup-census](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L752-L789), [ginutil.c#ginUpdateStats](../../../raw/postgres-17/src/backend/access/gin/ginutil.c#L645-L650)), and [`pageinspect`](../../glossary.md#pageinspect) republishes them with the same caveat in a comment ([ginfuncs.c#gin_metapage_info](../../../raw/postgres-17/contrib/pageinspect/ginfuncs.c#L30-L95)). An `ANALYZE`-only call into the GIN callback is a no-op except in an autovacuum worker ([ginvacuum.c#analyze_only](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L705-L729)). A census that trusts those counters without proving a cleanup ran is reading a number from an unknown earlier state.

**A census holds no relation lock between page reads.** `get_raw_page_internal` opens the relation with `AccessShareLock`, copies one page, and closes the relation with that lock before the next call ([rawpage.c#get_raw_page_internal](../../../raw/postgres-17/contrib/pageinspect/rawpage.c#L141-L199)). A multi-page census of a busy index is therefore a sequence of instants, not a snapshot, which is why the protocol has both a lock rule and a bracket rule.

**An unmaintained table is not a state the default configuration leaves behind, and on GIN an auto-analyze is not a statistics-only event.** Autovacuum is on by default, and each worker process checks every table in its database and runs `VACUUM` and/or `ANALYZE` as needed ([guc_tables.c#autovacuum](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L1450-L1457), [maintenance.sgml#autovacuum-daemon](../../../raw/postgres-17/doc/src/sgml/maintenance.sgml#L853-L885)). A fixture that churns an index and never maintains it therefore scores a method against a fault in operations rather than against the index, which is why the maintenance step is mandatory. GIN adds a second, sharper reason: `analyze_rel` enters the [index AM](../../glossary.md#access-method)'s ANALYZE-only cleanup **only when the command is not a `VACUUM ANALYZE`**, and the comment there names GIN as the only core index AM that does not treat that mode as a no-op ([analyze.c#analyze-only-cleanup](../../../raw/postgres-17/src/backend/commands/analyze.c#L694-L721)); the GIN callback then flushes the pending list when, and only when, the caller is an autovacuum worker ([ginvacuum.c#analyze_only-worker](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L709-L717)). A foreground `ANALYZE` cannot produce the state a real auto-analyze leaves on a GIN index, so the stand-in for it is an explicit flush rather than a command name.

**A `VACUUM` can remove nothing and still leave a fully settled index, which makes the settle proof reassuring and wrong.** `VACUUM` takes its [removal horizon](../../glossary.md#xmin-horizon) from `GetOldestNonRemovableTransactionId` ([vacuum.c#vacuum_get_cutoffs-OldestXmin](../../../raw/postgres-17/src/backend/commands/vacuum.c#L1109-L1122), [procarray.c#GetOldestNonRemovableTransactionId](../../../raw/postgres-17/src/backend/storage/ipc/procarray.c#L2005-L2026)), which folds in every backend's `xmin` and every [replication slot](../../glossary.md#replication-slot)'s, exempting only a vacuuming or decoding backend ([procarray.c#ComputeXidHorizons-backend-xmin](../../../raw/postgres-17/src/backend/storage/ipc/procarray.c#L1792-L1815), [procarray.c#skip-vacuum-and-decoding](../../../raw/postgres-17/src/backend/storage/ipc/procarray.c#L1817-L1832), [procarray.c#slot-horizons](../../../raw/postgres-17/src/backend/storage/ipc/procarray.c#L1896-L1902)). Under a pinned horizon the churn's rows stay [`HEAPTUPLE_RECENTLY_DEAD`](../../glossary.md#dead-tuple) and are only counted ([vacuumlazy.c#recently_dead_tuples](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L208-L212), [vacuumlazy.c#lazy_scan_noprune-recently-dead](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1770-L1776)), [index vacuuming](../../glossary.md#index-vacuuming) is entered only when dead TIDs were collected ([vacuumlazy.c#lazy_vacuum-gate](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1047-L1052)), so `ginbulkdelete` never runs - and `ginvacuumcleanup` then takes its `stats == NULL` branch, flushes the pending list, walks every block and rewrites the metapage counters anyway ([ginvacuum.c#cleanup-pending-when-no-bulkdelete](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L719-L729), [ginvacuum.c#ginvacuumcleanup-census](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L752-L789)). The index is settled, the metapage is current, and not one dead entry has left it. That is why the maintenance step carries a prohibition as well as an obligation.

## How It Works

### The five phases of a run

Every scored fixture passes through the same five phases, in order, on one isolated cluster. The phase boundaries are what make a GIN number comparable to a rebuild at all.

| Phase | What happens | Why it is a separate phase |
|---|---|---|
| build | create the table, load it, create the index that is scored, settle it | the as-built state is the only state in which the index is known to be dense |
| baseline | record `pg_relation_size(index, 'main')`, the metapage row, and the page-class census | a before-and-after claim has nothing to compare against otherwise, and the entry-page slack of a fresh build is the level every later reading is judged against |
| churn | run the recipe's own writes, then the settle step, then the maintenance step | this is the state the method is asked about, and it is a maintained state |
| decide | run the method under test, unmodified, under the measurement lock | the text that is scored must be the text that is published |
| oracle | `REINDEX INDEX`, then read the size again | the only ground truth for "how many bytes would a rebuild return" |

The settle step belongs to the build and churn phases, not to the decide phase: a method may not be handed an index whose pending list and deleted pages were never resolved, because that state is an artifact of the fixture rather than of the index.

The churn phase therefore ends in a fixed order, and a run states that it followed it: the recipe's writes, then the settle step, then the maintenance step of [The maintenance assumption](#the-maintenance-assumption), then [The simulated auto-analyze census](#the-simulated-auto-analyze-census). Nothing but the method under test runs in the decide phase.

### The settle step, and proving it ran

Settling means: the pending list has been merged, and the metapage's page counts describe the file as it now stands. A run must record evidence that it happened, because every failure mode here is silent.

1. **`VACUUM` on the table is the settle command.** GIN registers `ginbulkdelete` and `ginvacuumcleanup` as its `ambulkdelete` and `amvacuumcleanup` callbacks ([ginutil.c#ginhandler-vacuum](../../../raw/postgres-17/src/backend/access/gin/ginutil.c#L64-L72)), and `ginvacuumcleanup` is what walks every block from `GIN_ROOT_BLKNO`, records recyclable pages in the FSM and rewrites the metapage counters ([ginvacuum.c#ginvacuumcleanup-census](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L752-L789)).
2. **`gin_clean_pending_list()` settles the pending list only.** It opens the *index* with `RowExclusiveLock`, requires ownership, refuses during recovery and on another session's temporary index, and is a logged no-op on an [index that is not valid](../../glossary.md#invalid-index) ([ginfast.c#gin_clean_pending_list](../../../raw/postgres-17/src/backend/access/gin/ginfast.c#L1030-L1091)). It does not rewrite the metapage's page counts, so it is not a substitute for the `VACUUM`.
3. **A successful `VACUUM` may never have touched the index.** `do_index_cleanup` starts true and is forced false when [`INDEX_CLEANUP`](../../glossary.md#index_cleanup) is disabled ([vacuumlazy.c#do_index_cleanup-init](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L387-L397)), the cleanup call is made only when it is still set ([vacuumlazy.c#lazy_cleanup_all_indexes-gate](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1064-L1066)), and the [wraparound failsafe](../../glossary.md#vacuum-failsafe) clears it mid-run ([vacuumlazy.c#failsafe-disables-cleanup](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L2320-L2326)). The index-vacuum bypass is the one case that does *not* cost the settle step: it turns off index vacuuming and explicitly keeps index cleanup ([vacuumlazy.c#bypass-keeps-cleanup](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1899-L1949)). A run must therefore assert the settle step from the index's own state, not from the fact that a `VACUUM` returned.
4. **Expect more than one `VACUUM` before deleted pages count as free.** A page deleted by the first VACUUM carries a delete xid the cluster has not passed yet, so `GinPageIsRecyclable` refuses it and `ginvacuumcleanup` counts it as a data page instead of recording it free ([ginvacuum.c#GinPageIsRecyclable](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L805-L829), [ginvacuum.c#ginvacuumcleanup-census](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L752-L789)).
5. **On a [standby](../../glossary.md#hot-standby) the settle step cannot run at all.** `VACUUM` is classified as not strictly read-only ([utility.c#vacuum-not-read-only](../../../raw/postgres-17/src/backend/tcop/utility.c#L280-L295)) and is refused during recovery by the utility gate ([utility.c#recovery-gate](../../../raw/postgres-17/src/backend/tcop/utility.c#L570-L583), [utility.c#PreventCommandDuringRecovery](../../../raw/postgres-17/src/backend/tcop/utility.c#L440-L449)); `gin_clean_pending_list` refuses for itself ([ginfast.c#recovery-refusal](../../../raw/postgres-17/src/backend/access/gin/ginfast.c#L1037-L1041)). A standby census reads whatever state replay produced, and the protocol does not score a bound against it.

### The maintenance assumption

Every scored fixture assumes that normal autovacuum and auto-analyze maintain every table, and the run performs that maintenance itself. The assumption has three parts.

1. **After its churn, a fixture runs `VACUUM ANALYZE` on every table the churn touched, before the decide phase.** The `VACUUM` half is the settle step above, with its own proof obligations; the `ANALYZE` half is the maintenance a real server would also have run. A fixture with no churn has nothing to maintain, and the `ANALYZE` of its build phase is what it carries into the decide phase.
2. **Turning autovacuum off does not exempt a table.** The run keeps `autovacuum` off, and a fixture may additionally set `autovacuum_enabled = false` on a table ([reloptions.c#autovacuum_enabled](../../../raw/postgres-17/src/backend/access/common/reloptions.c#L105-L113)). Either setting stops the launcher's verdicts for that table, wraparound forcing aside ([autovacuum.c#AutoVacuumingActive](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3235-L3241), [autovacuum.c#av_enabled-return](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3048-L3054)); neither stops the fixture from running the maintenance the launcher would have run, because the assumption replaces the launcher rather than depending on it.
3. **No fixture may leave churn unmaintained.** A recipe that inserts, updates or deletes and then asks the method about the index with no `VACUUM ANALYZE` in between is not a fixture this protocol defines, and a number produced from one is not a scored number.

**The `ANALYZE` half cannot un-settle a settled index, which is why the settle step keeps its own rules and runs first.** `vacuum()` processes each relation by vacuuming it and then analyzing it ([vacuum.c#vacuum-then-analyze](../../../raw/postgres-17/src/backend/commands/vacuum.c#L618-L650)), and `analyze_rel` enters the index AM's ANALYZE-only cleanup only when the command is not a `VACUUM ANALYZE` ([analyze.c#analyze-only-cleanup](../../../raw/postgres-17/src/backend/commands/analyze.c#L694-L721)). Under the maintenance step the GIN callback is therefore reached by the `VACUUM` half alone, and the `ANALYZE` half touches no index page. What the `ANALYZE` half does write is statistics, and two of those writes are visible to a method: `pgstat_report_analyze` zeroes `mod_since_analyze` ([pgstat_relation.c#report_analyze-reset](../../../raw/postgres-17/src/backend/utils/activity/pgstat_relation.c#L331-L337)), and `vac_update_relstats` rewrites the measured index's own [`pg_class`](../../glossary.md#pg_class) row from a live `RelationGetNumberOfBlocks` plus a scaled row estimate ([analyze.c#index-relstats](../../../raw/postgres-17/src/backend/commands/analyze.c#L647-L663), [vacuum.c#vac_update_relstats](../../../raw/postgres-17/src/backend/commands/vacuum.c#L1409-L1416)), so [`relpages`](../../glossary.md#reltuples-and-relpages) and `reltuples` for that index are post-maintenance values rather than whatever the build left ([pg_class.h#relpages-reltuples](../../../raw/postgres-17/src/include/catalog/pg_class.h#L62-L66)). The `VACUUM` half reports its live and dead counts and zeroes the insert counter ([pgstat_relation.c#report_vacuum-reset](../../../raw/postgres-17/src/backend/utils/activity/pgstat_relation.c#L233-L246)).

A foreground `VACUUM ANALYZE` is a faithful stand-in for the worker's *command*: `autovacuum_do_vac_analyze` builds one `VacuumRelation` and calls the same `vacuum()` the SQL command reaches ([autovacuum.c#autovacuum_do_vac_analyze](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3120-L3147), [vacuum.c#ExecVacuum-vacuum](../../../raw/postgres-17/src/backend/commands/vacuum.c#L450-L451)). It is **not** a faithful stand-in for an auto-analyze on a GIN index; see [The auto-analyze stand-in on a GIN index](#the-auto-analyze-stand-in-on-a-gin-index).

**The launcher's verdicts are recorded here, not applied.** The run maintains after every churn whether or not the counters had crossed a threshold, so the protocol never reproduces the vacuum side, and a conforming run may not claim that it does. A launcher at the defaults wakes every `autovacuum_naptime` of 60 s ([guc_tables.c#autovacuum_naptime](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L3339-L3348)), and its worker asks `relation_needs_vacanalyze` for a vacuum verdict and an analyze verdict at once for every table it walks ([autovacuum.c#do_autovacuum-census](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L2021-L2033)).

| Launcher verdict | Engine test, on effective per-table values | At the defaults | Evidence |
|---|---|---|---|
| vacuum | `dead_tuples > vac_base_thresh + vac_scale_factor * reltuples` | `50 + 0.2 * reltuples` | [autovacuum.c#vacthresh-anlthresh](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3074-L3076), [autovacuum.c#verdicts](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3092-L3095), [guc_tables.c#autovacuum_vacuum_threshold](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L3349-L3357), [guc_tables.c#autovacuum_vacuum_scale_factor](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L3886-L3894) |

The counters the launcher compares are `n_dead_tup`, `n_mod_since_analyze` and `n_ins_since_vacuum` in [`pg_stat_all_tables`](../../glossary.md#pg_stat_all_tables) ([system_views.sql#launcher-counters](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L688-L690)), and the documentation states the same three formulas ([maintenance.sgml#thresholds](../../../raw/postgres-17/doc/src/sgml/maintenance.sgml#L899-L953)).

The assumption is deliberately stronger than the launcher: the maintenance step runs even where the counters sit far below every threshold, so the protocol builds no sub-threshold unmaintained GIN index and scores no method against one. What the three parts do not cover on their own is a fixture that issues the maintenance and then prevents it from working; that is [The maintenance must not be defeated](#the-maintenance-must-not-be-defeated).

### The maintenance must not be defeated

**No fixture may carry a state into the settle step or the maintenance step that would have stopped a real server's autovacuum, `VACUUM`, `ANALYZE` or auto-analyze from doing the work this protocol credits it with.** [The maintenance assumption](#the-maintenance-assumption) says the command must run; this rule says it must have been effective. On GIN the failure is worse than silent, it is reassuring: with the horizon pinned, `ginbulkdelete` never runs, and `ginvacuumcleanup` still flushes the pending list, walks every block and rewrites the metapage counters, so **every proof [The settle step, and proving it ran](#the-settle-step-and-proving-it-ran) asks for is satisfied while no dead entry has left the index** ([ginvacuum.c#cleanup-pending-when-no-bulkdelete](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L719-L729), [ginvacuum.c#ginvacuumcleanup-census](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L752-L789)).

Five states are forbidden, on every table and index a fixture touches, from its first churn statement to the end of the census.

| Forbidden state | Why it defeats the maintenance step | Evidence |
|---|---|---|
| an open transaction or held [snapshot](../../glossary.md#snapshot) anywhere in the cluster, other than a lazy `VACUUM` | `VACUUM`'s `OldestXmin` comes from `GetOldestNonRemovableTransactionId`, which folds in every backend's `xmin`, so nothing that horizon still covers is removable: the churn's rows stay `HEAPTUPLE_RECENTLY_DEAD`, no dead TIDs are collected, index vacuuming is never entered, and `ginbulkdelete` never runs. A lazy `VACUUM` is the one exemption the engine itself grants, through the `PROC_IN_VACUUM` flag the [proc-array](../../glossary.md#procarray) scan skips | [vacuum.c#vacuum_get_cutoffs-OldestXmin](../../../raw/postgres-17/src/backend/commands/vacuum.c#L1109-L1122), [procarray.c#ComputeXidHorizons-backend-xmin](../../../raw/postgres-17/src/backend/storage/ipc/procarray.c#L1792-L1815), [vacuumlazy.c#lazy_vacuum-gate](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1047-L1052), [vacuum.c#PROC_IN_VACUUM](../../../raw/postgres-17/src/backend/commands/vacuum.c#L2006-L2029), [procarray.c#skip-vacuum-and-decoding](../../../raw/postgres-17/src/backend/storage/ipc/procarray.c#L1817-L1832) |

**This is not the one-`VACUUM` lag.** Point 4 of the settle step is engine behavior with nobody holding anything: a page deleted by *this* `VACUUM` carries a delete xid the cluster has not passed, so `GinPageIsRecyclable` refuses it and the page is counted as a data page until a later `VACUUM` ([ginvacuum.c#GinPageIsRecyclable](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L805-L829)). That lag is expected and a fixture reports it. A pinned horizon is different in kind: nothing is deleted for the lag to apply to.

**A disabled launcher is not a defeat either.** `autovacuum = off` and a per-table `autovacuum_enabled = false` stop the launcher's verdicts, and part 2 of the assumption already accounts for them: the fixture runs the maintenance the launcher would have run ([autovacuum.c#AutoVacuumingActive](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3235-L3241), [autovacuum.c#av_enabled-return](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3048-L3054)). The five states above are different in kind: the maintenance statement runs and cannot do its work.

What a run records, per fixture:

| Proof | What it establishes |
|---|---|
| the maintenance statement completed, and no `skipping vacuum of ... --- lock not available` or `skipping analyze of ...` line names the fixture's relation | the command was neither skipped for want of the lock nor cut short |
| `VACUUM (VERBOSE)`'s `tuples: ... are dead but not yet removable` count for every churned table ([vacuumlazy.c#verbose-tuples-line](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L657-L663)) | a nonzero count on a fixture whose churn deleted or updated rows is a pinned horizon; the fixture is repaired and re-run, not scored |
| the horizon holders at that moment: [`pg_stat_activity`](../../glossary.md#pg_stat_activity)'s `xact_start` and `backend_xmin`, and `pg_replication_slots`' `xmin` ([system_views.sql#pg_stat_activity-xmin](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L878-L885), [system_views.sql#pg_replication_slots-xmin](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L1006-L1017)) | which session or slot pinned it, when one did. These four proofs stay the binding minimum. They do not catch a [cleanup-lock miss](../../glossary.md#missed-dead-tuple) or an index-vacuum bypass, because both leave the `dead but not yet removable` count at 0 while the settle proof still passes ([vacuumlazy.c#verbose-tuples-line](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L657-L663), [vacuumlazy.c#verbose-missed-line](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L664-L668), [vacuumlazy.c#verbose-index-scan-line](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L695-L717)). [Recommended: proving VACUUM did all its work](#recommended-proving-vacuum-did-all-its-work) adds the checks that do.

**Two exceptions are declared rather than forbidden**, because the protocol requires one of them and owns the other.

| Exception | What the run does instead |
|---|---|
| the fixture that holds a snapshot across the settling `VACUUM`, required by [Coverage the protocol requires](#coverage-the-protocol-requires) | the snapshot is the point: declare it, report it beside the stuck pages as [The reading rules](#the-reading-rules) already demands, and publish the reading as a held-horizon reading, never as a maintained-state one ([ginvacuum.c#GinPageIsRecyclable](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L805-L829)) |
| the measurement lock, which excludes `VACUUM` and `ANALYZE` by design ([lock.c#LockConflicts](../../../raw/postgres-17/src/backend/storage/lmgr/lock.c#L64-L104)) | take it in the decide phase only, after the settle step, the maintenance step and the census, and release it before any later maintenance; it may not be held across either step |

The held-snapshot fixture is outside [Recommended: proving VACUUM did all its work](#recommended-proving-vacuum-did-all-its-work): its first gate query fails by design, and its report is read as the held-horizon reading it declares.

Nothing in this rule asks a run to switch the launcher on. `autovacuum` stays off for isolation, as [What the run fixes, and the apply scope of each setting](#what-the-run-fixes-and-the-apply-scope-of-each-setting) states; the rule binds what a fixture may do while it is off.

### Recommended: proving VACUUM did all its work

**This procedure is recommended, not required.** [The maintenance must not be defeated](#the-maintenance-must-not-be-defeated) stays the binding rule, and its proofs stay the minimum a conforming run records. This section adds a way for a tester to show, for one maintenance statement, that every part of [`VACUUM`](../../glossary.md#vacuum)'s work actually happened, and what to do when a part did not.

The behavior it guards against is easy to miss: a `VACUUM` that returns success can still leave work undone, and most of the ways it does so raise no error. It can skip the table before it starts. It can keep [dead rows](../../glossary.md#dead-tuple) that an old [snapshot](../../glossary.md#snapshot) can still see, or leave dead rows on a page it could not lock for cleanup. It can decline [index vacuuming](../../glossary.md#index-vacuuming), give up [truncation](../../glossary.md#truncation), or never reach the [TOAST](../../glossary.md#toast) table. Each of those leaves a trace, either in the [report `VERBOSE` prints](../../glossary.md#vacuum-verbose) or in the statistics the statement writes. So the procedure removes every cause it can before the statement runs, and then proves completion from those traces rather than from the exit status.

#### Where VACUUM can leave work undone

The map follows one tier-0 statement, `VACUUM (VERBOSE, ANALYZE, PARALLEL 0)`, on one table, in execution order. Each branch on the left is a way part of the work is not done; the right column is the trace that branch leaves. The numbered nodes are keyed to their evidence in the table below the map.


#### Stage A: remove the causes before the statement

Run these checks immediately before the maintenance statement, in the session that will run it, so that "no other session" in check 2 means exactly that. Each check removes a branch of the map, so the statement can no longer take it.

1. **No horizon holder.** The first query below must return no row. A backend with an xid or xmin, a prepared transaction or a slot with an `xmin` moves the cutoff of node [2] back, and rows deleted after it then stay as dead but not yet removable. The engine counts only same-database backends for an ordinary table ([procarray.c#data-horizon-same-database](../../../raw/postgres-17/src/backend/storage/ipc/procarray.c#L1838-L1864)); the query looks at the whole cluster anyway, because the stricter check costs nothing and also covers the shared catalogs. A prepared transaction can exist only when `max_prepared_transactions` is above its default of 0, because `PREPARE TRANSACTION` fails outright at 0; the setting has `postmaster` context, so changing it needs a restart ([guc_tables.c#max_prepared_transactions](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L2579-L2585), [twophase.c#prepared-disabled](../../../raw/postgres-17/src/backend/access/transam/twophase.c#L371-L376)).
2. **No other session on the database, and no lock on the table.** The second query must list no other client backend, and the third no lock held or awaited by anyone else on the table, its TOAST table or any of their indexes. No core view shows buffer pins, and `pg_buffercache`'s `pinning_backends` counts them per buffer without naming the backend ([pg_buffercache--1.2.sql#pinning_backends](../../../raw/postgres-17/contrib/pg_buffercache/pg_buffercache--1.2.sql#L17), [pgbuffercache.sgml#pinning_backends](../../../raw/postgres-17/doc/src/sgml/pgbuffercache.sgml#L166-L172)). A session that is not connected holds no pin, though, so ruling out the session rules out its pins at node [3]. Any lock at all blocks truncation's [`AccessExclusiveLock`](../../glossary.md#accessexclusivelock) at node [6], and a lock that conflicts with `ShareUpdateExclusiveLock` makes the statement itself wait at node [1]. A prepared transaction's locks show in `pg_locks` with no `pid` ([pg_proc.dat#pg_lock_status](../../../raw/postgres-17/src/include/catalog/pg_proc.dat#L6308-L6313), [system_views.sql#pg_locks](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L401-L402)), which is why the query compares with `IS DISTINCT FROM`.
3. **No dirty buffers left by the churn.** Run `CHECKPOINT`. The [checkpointer](../../glossary.md#checkpointer) and the [background writer](../../glossary.md#background-writer) pin and share-lock a dirty buffer while they write it ([bufmgr.c#SyncOneBuffer-pin](../../../raw/postgres-17/src/backend/storage/buffer/bufmgr.c#L3546-L3567)), and a pin held at that moment is enough to refuse the cleanup lock of node [3] ([bufmgr.c#ConditionalLockBufferForCleanup](../../../raw/postgres-17/src/backend/storage/buffer/bufmgr.c#L5456-L5508)). After the checkpoint the churned pages are clean, so neither process has a reason to write them while `VACUUM` reads them. `CHECKPOINT` requires the privileges of `pg_checkpoint` ([utility.c#checkpoint-privilege](../../../raw/postgres-17/src/backend/tcop/utility.c#L942-L950)). It reduces the risk rather than removing it, which is why Stage C still checks for missed tuples.
4. **No phase switched off by a storage parameter.** The fourth query must show no `vacuum_index_cleanup` of `off` and no `vacuum_truncate` of `false` on the table or its TOAST table. Their defaults are `auto` and `true` ([reloptions.c#vacuum_index_cleanup](../../../raw/postgres-17/src/backend/access/common/reloptions.c#L510-L520), [reloptions.c#vacuum_truncate](../../../raw/postgres-17/src/backend/access/common/reloptions.c#L151-L158)), and a command that gives neither option takes them from the parameters ([vacuum.c#index_cleanup-reloption](../../../raw/postgres-17/src/backend/commands/vacuum.c#L2155-L2179), [vacuum.c#truncate-reloption](../../../raw/postgres-17/src/backend/commands/vacuum.c#L2190-L2201)).
5. **Far from the failsafe.** The same query must show `age(relfrozenxid)` below the larger of `vacuum_failsafe_age` and 1.05 times `autovacuum_freeze_max_age`, and `mxid_age(relminmxid)` below the MultiXact equivalent, which is the test `vacuum_xid_failsafe_check` applies ([vacuum.c#vacuum_xid_failsafe_check](../../../raw/postgres-17/src/backend/commands/vacuum.c#L1252-L1298)). The defaults are 1.6 billion and 200 million; the failsafe ages have `user` context and the `autovacuum_*` ages `postmaster` context ([guc_tables.c#vacuum_failsafe_age](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L2707-L2723), [guc_tables.c#autovacuum_freeze_max_age](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L3378-L3398)). A fresh fixture is nowhere near either.
6. **The churn's statistics are published.** Every churn session has exited or run `SELECT pg_stat_force_next_flush();`, as [The simulated auto-analyze census](#the-simulated-auto-analyze-census) requires. Otherwise a flush that lands after the statement adds to `n_dead_tup` and Stage D reads a count the statement never left.
7. **The maintenance session cannot be cut short.** Set its four timeouts to 0. That is each one's boot value ([guc_tables.c#statement_timeout](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L2611-L2620), [guc_tables.c#lock_timeout](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L2622-L2631), [guc_tables.c#idle_in_transaction_session_timeout](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L2633-L2642), [guc_tables.c#transaction_timeout](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L2644-L2653)), so the `SET` only undoes a role, database or configuration-file value. All four have `user` context, so the `SET` applies to the session.
8. **Record the counters.** Keep `vacuum_count` and `analyze_count` for the table and its TOAST table, so that Stage D can check that each moved by exactly one.

The probe queries carry their own `statement_timeout` and `lock_timeout`, so a probe that blocks fails instead of stalling the run. `public.t` stands for the table being maintained.

```sql
SET statement_timeout = '30s';
SET lock_timeout = '5s';

-- 1. Horizon holders anywhere in the cluster: expect no row.
SELECT /* wiki_vacuum_gate_horizon */
       'backend' AS holder, pid::text AS id, datname::text AS db,
       backend_type AS detail, backend_xid::text AS xid, backend_xmin::text AS xmin
  FROM pg_stat_activity
 WHERE pid <> pg_backend_pid()
   AND (backend_xid IS NOT NULL OR backend_xmin IS NOT NULL)
UNION ALL
SELECT 'prepared', gid, database::text, owner::text, transaction::text, NULL
  FROM pg_prepared_xacts
UNION ALL
SELECT 'slot', slot_name::text, database::text, slot_type, NULL,
       coalesce(xmin::text, '-') || ' / ' || coalesce(catalog_xmin::text, '-')
  FROM pg_replication_slots
 WHERE xmin IS NOT NULL OR catalog_xmin IS NOT NULL;

-- 2. Other sessions on this database: expect no row.
SELECT /* wiki_vacuum_gate_sessions */ pid, usename, application_name, state, backend_type
  FROM pg_stat_activity
 WHERE pid <> pg_backend_pid()
   AND datname = current_database()
   AND backend_type IN ('client backend', 'autovacuum worker');

-- 3. Locks held or awaited by anyone else on the table, its TOAST table and their indexes: expect no row.
WITH /* wiki_vacuum_gate_locks */ heap AS (
       SELECT c.oid FROM pg_class c WHERE c.oid = 'public.t'::regclass
       UNION ALL
       SELECT c.reltoastrelid FROM pg_class c
        WHERE c.oid = 'public.t'::regclass AND c.reltoastrelid <> 0
     ), rels AS (
       SELECT oid FROM heap
       UNION ALL
       SELECT i.indexrelid FROM pg_index i JOIN heap h ON i.indrelid = h.oid
     )
SELECT l.pid, l.relation::regclass AS rel, l.mode, l.granted
  FROM pg_locks l
 WHERE l.locktype = 'relation'
   AND l.database = (SELECT oid FROM pg_database WHERE datname = current_database())
   AND l.relation IN (SELECT oid FROM rels)
   AND l.pid IS DISTINCT FROM pg_backend_pid();

-- 4 and 5. Storage parameters and distance to the failsafe, for the table and its TOAST table.
SELECT /* wiki_vacuum_gate_options */ c.oid::regclass AS rel, c.reloptions,
       age(c.relfrozenxid) AS xid_age,
       greatest(current_setting('vacuum_failsafe_age')::numeric,
                current_setting('autovacuum_freeze_max_age')::numeric * 1.05) AS xid_failsafe_age,
       mxid_age(c.relminmxid) AS mxid_age,
       greatest(current_setting('vacuum_multixact_failsafe_age')::numeric,
                current_setting('autovacuum_multixact_freeze_max_age')::numeric * 1.05) AS mxid_failsafe_age
  FROM pg_class c
 WHERE c.oid IN ('public.t'::regclass::oid,
                 (SELECT reltoastrelid FROM pg_class WHERE oid = 'public.t'::regclass));

-- 8. Counters before the statement.
SELECT /* wiki_vacuum_gate_counters */ relid::regclass AS rel, vacuum_count, analyze_count
  FROM pg_stat_all_tables
 WHERE relid IN ('public.t'::regclass::oid,
                 (SELECT reltoastrelid FROM pg_class WHERE oid = 'public.t'::regclass));

CHECKPOINT;
```

Every column these queries read is defined at the pin: `pg_stat_activity` ([system_views.sql#pg_stat_activity](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L865-L891)), `pg_prepared_xacts` ([system_views.sql#pg_prepared_xacts](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L421-L426)), `pg_replication_slots` ([system_views.sql#pg_replication_slots](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L1006-L1029)), `pg_locks` ([pg_proc.dat#pg_lock_status](../../../raw/postgres-17/src/include/catalog/pg_proc.dat#L6308-L6313)) and `pg_stat_all_tables` ([system_views.sql#pg_stat_all_tables](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L670-L703)); the two `backend_type` names are the engine's own ([miscinit.c#backend-type-names](../../../raw/postgres-17/src/backend/utils/init/miscinit.c#L277-L283)).

#### Stage B: run the statement and keep its report

Run one statement per table, so each report belongs to one table and its TOAST table:

```sql
SET statement_timeout = 0;
SET lock_timeout = 0;
SET idle_in_transaction_session_timeout = 0;
SET transaction_timeout = 0;
VACUUM /* wiki_vacuum_maintenance */ (VERBOSE, ANALYZE, PARALLEL 0) public.t;
```

The options stay at their defaults except `VERBOSE`, `ANALYZE` and `PARALLEL 0`, which together are tier 0 of the escalation in Stage E. `PARALLEL 0` is there because an autovacuum worker never vacuums indexes in parallel, while the SQL command does by default whenever at least two of the table's indexes support [parallel vacuum](../../glossary.md#parallel-vacuum) and reach `min_parallel_index_scan_size`; the option sets the worker count to -1, so `dead_items_alloc` never starts a parallel context ([autovacuum.c#no-parallel](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L2839-L2840), [vacuum.c#parallel-default](../../../raw/postgres-17/src/backend/commands/vacuum.c#L171-L172), [vacuum.c#PARALLEL-zero](../../../raw/postgres-17/src/backend/commands/vacuum.c#L277-L282), [vacuumlazy.c#parallel-gate](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L2830-L2857), [vacuumparallel.c#parallel_vacuum_compute_workers](../../../raw/postgres-17/src/backend/commands/vacuumparallel.c#L547-L601)). A parallel run would skip no index, because the leader processes every index no worker took ([vacuumparallel.c#leader-participates](../../../raw/postgres-17/src/backend/commands/vacuumparallel.c#L719-L726)), so the option changes which process does the work, not how much of it is done. Setting `max_parallel_maintenance_workers` to 0 has the same effect for every statement in the session: the setting has `user` context and a default of 2, and the worker computation returns 0 when it is 0 ([guc_tables.c#max_parallel_maintenance_workers](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L3409-L3417), [vacuumparallel.c#parallelism-disabled](../../../raw/postgres-17/src/backend/commands/vacuumparallel.c#L555-L560)). Six options are never used, because each one creates a branch of the map on purpose: `SKIP_LOCKED` turns the wait of node [1] into a skip, `INDEX_CLEANUP OFF` and `TRUNCATE false` switch off nodes [4] to [6], `PROCESS_TOAST false` and `PROCESS_MAIN false` drop node [8] or the main table, and `SKIP_DATABASE_STATS` drops node [10] ([vacuum.c#ExecVacuum-defaults](../../../raw/postgres-17/src/backend/commands/vacuum.c#L153-L169), [ref/vacuum.sgml#options](../../../raw/postgres-17/doc/src/sgml/ref/vacuum.sgml#L112-L323)).

The report is made of server notices. `INFO` always reaches the client, whatever `client_min_messages` says ([elog.c#should_output_to_client](../../../raw/postgres-17/src/backend/utils/error/elog.c#L248-L264)), and `psql` writes every notice to standard error, prefixed with the script name and line number when it reads a file ([common.c#NoticeProcessor](../../../raw/postgres-17/src/bin/psql/common.c#L269-L273), [startup.c#log_locus_callback](../../../raw/postgres-17/src/bin/psql/startup.c#L99-L111), [logging.c#locus-prefix](../../../raw/postgres-17/src/common/logging.c#L244-L261)). So capture standard error to one file per table, for example `psql -X -v ON_ERROR_STOP=1 -f vacuum_t.sql 2> vacuum_t.log`. Each report's first line carries the prefix; its other lines start at column 0, because the server sends the report as one multi-line message ([vacuumlazy.c#report-ereport](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L762-L763)).

A second session may watch the statement through [progress reporting](../../glossary.md#progress-reporting) in `pg_stat_progress_vacuum` and the [wait event](../../glossary.md#wait-event) columns of `pg_stat_activity` ([system_views.sql#pg_stat_progress_vacuum](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L1209-L1227)). A wait of type `Lock` is node [1], type `BufferPin` is the aggressive wait of node [3], and type `Timeout` with event `VacuumTruncate` is the retry loop of node [6] ([wait_event.c#wait-event-types](../../../raw/postgres-17/src/backend/utils/activity/wait_event.c#L391-L409), [wait_event_names.txt#VACUUM_TRUNCATE](../../../raw/postgres-17/src/backend/utils/activity/wait_event_names.txt#L181), [wait_event_names.txt#BUFFER_PIN](../../../raw/postgres-17/src/backend/utils/activity/wait_event_names.txt#L278-L280), [generate-wait_event_types.pl#camel-case](../../../raw/postgres-17/src/backend/utils/activity/generate-wait_event_types.pl#L112-L128)). The watcher must send single statements and never hold a transaction open: a snapshot taken after the churn committed cannot protect the churn's rows, but one taken before it is itself a horizon holder.

The last line is the strongest single check, for two reasons. `ANALYZE` counts every `LP_DEAD` stub and every dead or recently dead row it reads ([heapam_handler.c#analyze-dead-rows](../../../raw/postgres-17/src/backend/access/heap/heapam_handler.c#L1054-L1085)), so it catches a horizon holder, a missed page and a bypass alike. And it reads every block when the table has no more blocks than its sample target, `300` times the statistics target ([analyze.c#two-stage-sample](../../../raw/postgres-17/src/backend/commands/analyze.c#L1136-L1137), [analyze.c#std_typanalyze-minrows](../../../raw/postgres-17/src/backend/commands/analyze.c#L1888-L1895)); above that size `K` is an estimate.

A pin does not always show up as missed tuples. A backend that reads a nearly full page prunes it on the spot when it can take the cleanup lock, before it keeps its pin ([pruneheap.c#heap_page_prune_opt-minfree](../../../raw/postgres-17/src/backend/access/heap/pruneheap.c#L226-L264)). `VACUUM`'s no-prune path then finds dead item identifiers instead of dead rows and collects them ([vacuumlazy.c#noprune-lpdead](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1799-L1829)), and the second heap pass can free them despite the pin, because it needs only an exclusive lock ([vacuumlazy.c#heap-pass-exclusive-lock](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L2148-L2153)). The same pin can therefore leave no trace at all, or a bypass line when those few pages fall under the bypass test.

These checks need nothing but a POSIX shell. They print the failing lines and nothing else when the report is clean:

```sh
log=vacuum_t.log
grep -c 'INFO:  finished vacuuming "' "$log"                  # one per relation: t, and its TOAST table
grep '^tuples: ' "$log" | grep -v ', 0 are dead but not yet removable$'
grep -E '^tuples missed: |^index scan bypassed|WARNING:  (skipping|permission denied|bypassing nonessential|cutoff for)|(stopping|suspending) truncate' "$log"
grep -E '": scanned [0-9]+ of [0-9]+ pages, containing [0-9]+ live rows and [0-9]+ dead rows' "$log" | grep -v ' and 0 dead rows;'
```

#### Stage D: cross-check the statistics and the catalog

```sql
SET statement_timeout = '30s';
SET lock_timeout = '5s';
SELECT /* wiki_vacuum_post_check */ s.relid::regclass AS rel,
       s.vacuum_count, s.analyze_count, s.n_dead_tup,
       c.relpages, c.relallvisible,
       pg_relation_size(c.oid) / current_setting('block_size')::int AS blocks_now
  FROM pg_stat_all_tables s
  JOIN pg_class c ON c.oid = s.relid
 WHERE s.relid IN ('public.t'::regclass::oid,
                   (SELECT reltoastrelid FROM pg_class WHERE oid = 'public.t'::regclass));
```

|---|---|---|---|
| `vacuum_count` | one more than in Stage A, for the table and for its TOAST table | the relation was skipped at node [1], or the statement died before node [7] | [vacuumlazy.c#report-vacuum](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L577-L591), [pgstat_relation.c#pgstat_report_vacuum](../../../raw/postgres-17/src/backend/utils/activity/pgstat_relation.c#L227-L257) |
| `analyze_count` | one more for the table; unchanged for the TOAST table, which `VACUUM` never analyzes | the `ANALYZE` half was skipped | [pgstat_relation.c#analyze-count](../../../raw/postgres-17/src/backend/utils/activity/pgstat_relation.c#L339-L348), [vacuum.c#toast-recursion](../../../raw/postgres-17/src/backend/commands/vacuum.c#L2282-L2300) |
| `n_dead_tup` | 0 for both | the table: `ANALYZE` saw dead rows. The TOAST table: its `VACUUM` left dead-but-not-removable or missed rows | [pgstat_relation.c#report_analyze-dead](../../../raw/postgres-17/src/backend/utils/activity/pgstat_relation.c#L328-L329), [vacuumlazy.c#report-vacuum](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L577-L591) |
| `relpages` against `blocks_now` | equal | the table grew or shrank after the statement | [analyze.c#relpages](../../../raw/postgres-17/src/backend/commands/analyze.c#L190-L197) |
| `relallvisible` against `relpages` | equal, apart from all-zero pages | a page `VACUUM` could not set all-visible: a dead or not-yet-visible row, a dead item identifier a bypass left, or a page it could not lock for cleanup | [vacuumlazy.c#prune-sets-vm](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1523-L1556), [vacuumlazy.c#heap-pass-sets-vm](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L2260-L2281), [vacuumlazy.c#new-page-not-in-vm](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1290-L1321) |

The visibility-map check works because each path that finishes a page also sets its bit. Pruning sets it when every remaining row is visible to all and no `LP_DEAD` item is left, the second heap pass sets it after it frees the dead items, and an empty page is set all-visible and all-frozen ([vacuumlazy.c#prune-sets-vm](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1523-L1556), [vacuumlazy.c#heap-pass-sets-vm](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L2260-L2281), [vacuumlazy.c#empty-page-sets-vm](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1323-L1381)). The no-prune path sets nothing, and an all-zero page is deliberately left out of the map ([vacuumlazy.c#new-page-not-in-vm](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1290-L1321)). A shortfall therefore points at a page that kept work, unless it is an all-zero page. A superuser can count those with [`pageinspect`](../../glossary.md#pageinspect), where an all-zero page reads `upper = 0` ([pageinspect--1.5.sql#page_header](../../../raw/postgres-17/contrib/pageinspect/pageinspect--1.5.sql#L22-L33), [rawpage.c#superuser](../../../raw/postgres-17/contrib/pageinspect/rawpage.c#L150-L153)):

```sql
SELECT /* wiki_vacuum_zero_pages */ count(*) AS all_zero_pages
  FROM generate_series(0, pg_relation_size('public.t') / current_setting('block_size')::int - 1) AS b
 WHERE (page_header(get_raw_page('public.t', b::int))).upper = 0;
```

#### The index half on a GIN index

The heap lines above decide whether the dead entries were handed to the index. On GIN the index line cannot decide it, because `ginvacuumcleanup` walks every block and rewrites the metapage counts whenever it runs, whether or not `ginbulkdelete` removed anything ([ginvacuum.c#ginvacuumcleanup-census](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L752-L789)). This table says what to read instead.

| What to read | Pass | What is by design | Evidence |
|---|---|---|---|
| the [pending list](../../glossary.md#pending-list) | `pgstatginindex(index)` reports `pending_pages = 0` and `pending_tuples = 0` after the statement | the flush runs on the first `ginbulkdelete` call, or in `ginvacuumcleanup` when bulk delete did not run. It waits for any concurrent cleaner, and a foreground `VACUUM` empties the whole list where a worker stops at the tail it saw first | [ginvacuum.c#bulkdelete-flush](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L591-L602), [ginvacuum.c#cleanup-pending-when-no-bulkdelete](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L719-L729), [ginfast.c#forceCleanup-wait](../../../raw/postgres-17/src/backend/access/gin/ginfast.c#L800-L817), [ginfast.c#full_clean-tail](../../../raw/postgres-17/src/backend/access/gin/ginfast.c#L879-L888), [pgstattuple--1.4.sql#pgstatginindex](../../../raw/postgres-17/contrib/pgstattuple/pgstattuple--1.4.sql#L40-L45) |
| that `ginbulkdelete` ran | the heap's `index scan` label is `needed` | the `index "i"` line appears after every `VACUUM` that reaches index cleanup, so its presence proves the census ran, not that entries left | [vacuumlazy.c#verbose-index-scan-line](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L695-L717), [ginvacuum.c#ginvacuumcleanup-census](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L752-L789) |
| pins on posting trees | nothing to check | the posting-tree pass waits for a cleanup lock on each posting-tree root, so a pin delays it and never skips it | [ginvacuum.c#posting-tree-cleanup-lock](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L430-L436) |

So on GIN a pinned horizon looks like this: the settle proof passes, the index line is present, and the pending list is empty, while the heap's `tuples:` line reports dead rows not yet removable and the `ANALYZE` line reports dead rows.

#### Stage E: verdict, re-run and escalation

The escalation is tiered. Tier 0 is the autovacuum-equivalent statement of Stage B. A failure is first classified: a structural cause is repaired and tier 0 is run again, and a transient cause gets one more tier-0 run once its cause is removed. Only a transient failure that survives that re-run moves to tier 1, which changes one option and is declared.

| Failure seen | Cause class | What to do at tier 0 | Tier 1, only if the tier-0 re-run fails the same way |
|---|---|---|---|
| `D` above 0 on the `tuples:` line, or `K` above 0 with neither a `tuples missed:` nor an `index scan bypassed` line | structural: a horizon holder at node [2] | find it with the first gate query, end it, and run Stages A to D again | none. No option moves the cutoff; the holder has to go |
| `tuples missed:` | transient: a pin at node [3] | run `CHECKPOINT`, confirm the second gate query is still empty, and run the statement again. The missed pages are not all-visible, so the next `VACUUM` scans them again | `VACUUM (VERBOSE, ANALYZE, PARALLEL 0, FREEZE) public.t`; see [The FREEZE escalation](#the-freeze-escalation) |
| `index scan bypassed:` | transient by design: the bypass test at node [4] | record it. A re-run on the same pages makes the same choice, so a fixture that needs the entries gone goes straight to tier 1 | `VACUUM (VERBOSE, ANALYZE, PARALLEL 0, INDEX_CLEANUP ON) public.t`; see [The INDEX_CLEANUP ON escalation](#the-index_cleanup-on-escalation) |
| `bypassed by failsafe`, or the `bypassing nonessential maintenance` warning | structural: the table's freeze horizon is too old | the fixture is not usable; rebuild it. `INDEX_CLEANUP ON` does not help, because the failsafe can still bypass it ([vacuumlazy.c#phase-switches](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L370-L407)) | none |
| a skip warning, or no `vacuuming` line | structural: privilege, relation kind or `SKIP_LOCKED` | fix the cause, then run Stages A to D again | none |
| `stopping truncate`, `suspending truncate`, or no `truncated` line when truncation was due | transient: some lock on the table at node [6], or growth | remove the lock holder, then run the statement again | none. The `TRUNCATE` option can prevent truncation but cannot force it past the size threshold or the lock ([vacuumlazy.c#phase-switches](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L370-L407), [vacuumlazy.c#should_attempt_truncation](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L2529-L2544)) |
| no `finished vacuuming` line, or an `ERROR` | structural: the statement was cancelled or failed | find what cancelled it, make sure the four timeouts are 0, and run again | none |
| no TOAST block although the table has a TOAST table | structural: `PROCESS_TOAST false` was given | run without it | none |
| `relallvisible` below `relpages` with every report check passing | none, when the gap equals the all-zero pages | count the all-zero pages; any page beyond them is a failure to explain | none |

`DISABLE_PAGE_SKIPPING` is not a remedy for a missed page. It makes the run aggressive and turns off visibility-map skipping ([vacuumlazy.c#aggressive-and-skipwithvm](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L449-L467)), but the freeze cutoff stays `vacuum_freeze_min_age`, 50 million XIDs by default, behind the next XID ([vacuum.c#FreezeLimit](../../../raw/postgres-17/src/backend/commands/vacuum.c#L1160-L1177), [guc_tables.c#vacuum_freeze_min_age](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L2667-L2674)). On a young fixture no tuple is that old, so a pinned page still takes the no-prune path ([vacuumlazy.c#noprune-aggressive-wait](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1713-L1733)). Its only use here is the case the documentation names, a visibility map that is itself suspect.

##### The FREEZE escalation

- **Default.** A tier-0 statement is not aggressive on a young table, and a non-aggressive `VACUUM` never waits for a cleanup lock: the no-prune path always returns true for it ([vacuumlazy.c#noprune-contract](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1633-L1651), [vacuum.c#aggressive-decision](../../../raw/postgres-17/src/backend/commands/vacuum.c#L1199-L1241)).
- **Cause.** The `FREEZE` option sets all four freeze ages to 0 for this statement ([vacuum.c#FREEZE-ages](../../../raw/postgres-17/src/backend/commands/vacuum.c#L385-L402)).
- **Mechanism.** A freeze table age of 0 makes the run aggressive, and a freeze minimum age of 0 puts `FreezeLimit` at the next XID, clamped to the removal cutoff ([vacuum.c#FreezeLimit](../../../raw/postgres-17/src/backend/commands/vacuum.c#L1160-L1177), [vacuum.c#aggressive-decision](../../../raw/postgres-17/src/backend/commands/vacuum.c#L1199-L1241)). A row is only dead when its deleting XID precedes the cutoff ([heapam_visibility.c#HeapTupleSatisfiesVacuum](../../../raw/postgres-17/src/backend/access/heap/heapam_visibility.c#L1162-L1181)), and `heap_tuple_should_freeze` answers true for any tuple whose plain xmin or xmax precedes `FreezeLimit` ([heapam.c#heap_tuple_should_freeze](../../../raw/postgres-17/src/backend/access/heap/heapam.c#L8247-L8284)). So on a page that holds a dead row with a plain deleting XID, or any unfrozen row older than the cutoff, the no-prune path returns false and the scan waits for the cleanup lock before pruning ([vacuumlazy.c#noprune-aggressive-wait](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1713-L1733), [vacuumlazy.c#cleanup-lock-or-noprune](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L950-L961)). A dead row whose deleter is a MultiXact is decided by the MultiXact cutoff and its members instead ([heapam.c#heap_tuple_should_freeze](../../../raw/postgres-17/src/backend/access/heap/heapam.c#L8247-L8284)).
- **What it costs.** The wait has no timeout of its own, so a pin that is never released stalls the statement in a `BufferPin` wait instead of skipping the page; Stage A's session check is what makes that wait short. `FREEZE` also freezes every eligible row, which an autovacuum worker at the defaults would not do, so the run declares that the maintained state is a frozen one.

##### The INDEX_CLEANUP ON escalation

- **Default.** `INDEX_CLEANUP` is `AUTO`, and under `AUTO` index vacuuming is bypassed when fewer than 2 % of the heap's pages hold dead items and their TIDs take under 32 MB ([vacuumlazy.c#phase-switches](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L370-L407), [vacuumlazy.c#bypass-conditions](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1899-L1934)).
- **Cause.** `INDEX_CLEANUP ON` given in the command ([vacuum.c#INDEX_CLEANUP-option](../../../raw/postgres-17/src/backend/commands/vacuum.c#L233-L248)).
- **Mechanism.** The option sets `consider_bypass_optimization` to false before the scan, so `lazy_vacuum` never applies the bypass, and index vacuuming runs whenever dead item identifiers were collected; only the failsafe can still turn it off ([vacuumlazy.c#phase-switches](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L370-L407), [vacuumlazy.c#bypass-conditions](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1899-L1934)).
- **What it costs.** The documentation calls `ON` the conservative choice that removes all dead tuples from indexes ([ref/vacuum.sgml#INDEX_CLEANUP](../../../raw/postgres-17/doc/src/sgml/ref/vacuum.sgml#L186-L231)). An autovacuum worker takes `vacuum_index_cleanup` instead, `auto` by default ([autovacuum.c#unspecified-options](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L2832-L2840), [vacuum.c#index_cleanup-reloption](../../../raw/postgres-17/src/backend/commands/vacuum.c#L2155-L2179)), so the run declares the departure.

#### Behavior that looks like a skip but is by design

These leave a trace that resembles undone work. None of them is a failure of the procedure, and a run reports them rather than repairing them.

| Behavior | Why it is by design | Evidence |
|---|---|---|
| `pages: ... scanned` below 100 % | an all-visible page has nothing to remove, so a non-aggressive run skips runs of 32 or more of them | [vacuumlazy.c#skip-range](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1138-L1143), [vacuumlazy.c#find_next_unskippable_block](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1203-L1245) |
| no `new relfrozenxid` line | a non-aggressive run that skipped an all-visible page keeps the old horizon, because it did not see that page's XIDs; and the horizon never moves backward | [vacuumlazy.c#keep-relfrozenxid](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L544-L554), [vacuum.c#relfrozenxid-advance-only](../../../raw/postgres-17/src/backend/commands/vacuum.c#L1489-L1519) |
| no `truncated` line on a heap whose end is empty | fewer than 1000 pages, and fewer than one sixteenth of the table, could be freed | [vacuumlazy.c#should_attempt_truncation](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L2529-L2544) |
| `index scans: 2` or more | the dead-item store filled, so `VACUUM` emptied it with an extra round; nothing was skipped | [vacuumlazy.c#dead-items-full](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L872-L910) |
| fewer parallel workers than planned, in a run that drops `PARALLEL 0` | the leader processes the remaining indexes | [vacuumparallel.c#leader-participates](../../../raw/postgres-17/src/backend/commands/vacuumparallel.c#L719-L726) |
| `VacuumDelay` waits | cost-based delay slows the run and skips nothing; its default is 0 for a command | [guc_tables.c#vacuum_cost_delay](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L3865-L3873) |
| an index without a `VERBOSE` line | the access method returned no result for this run; see the index half above | [vacuumlazy.c#verbose-index-line](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L718-L732) |
| an index left out entirely | `VACUUM` opens only indexes marked `indisready`, so one left unready by a failed concurrent build is not vacuumed | [vacuum.c#vac_open_indexes-indisready](../../../raw/postgres-17/src/backend/commands/vacuum.c#L2345-L2357) |
| `datfrozenxid` unchanged | it moves only when every relation's horizon allows, and is skipped outright when a relation's horizon looks newer than the next XID | [vacuum.c#datfrozenxid-bogus](../../../raw/postgres-17/src/backend/commands/vacuum.c#L1663-L1715) |

#### State changes that move the evidence

The proof reads stored values, so it has to read them after the right event and before the wrong one.

| Event | State before | State after | Effect on the proof |
|---|---|---|---|
| a churn session commits but has not flushed its counts | `n_dead_tup` lower than the truth | unchanged until the flush | a flush after the statement adds dead tuples that the statement already removed; Stage A item 6 prevents it ([pgstat.c#pgstat_report_stat](../../../raw/postgres-17/src/backend/utils/activity/pgstat.c#L583-L600)) |
| `CHECKPOINT` | churned pages dirty | clean | background writes no longer pin the pages `VACUUM` is about to read ([bufmgr.c#SyncOneBuffer-pin](../../../raw/postgres-17/src/backend/storage/buffer/bufmgr.c#L3546-L3567)) |
| the `VACUUM` half ends | old counters | `vacuum_count` + 1, `n_dead_tup` = dead-but-not-removable plus missed, `n_ins_since_vacuum` = 0; `relpages`, `relallvisible` and the freeze horizons in `pg_class` | the completion check reads `vacuum_count` from here on ([pgstat_relation.c#pgstat_report_vacuum](../../../raw/postgres-17/src/backend/utils/activity/pgstat_relation.c#L227-L257), [vacuumlazy.c#relallvisible](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L556-L575)) |
| the `ANALYZE` half ends | `n_dead_tup` from `VACUUM` | `n_dead_tup` from the sample, `analyze_count` + 1, `n_mod_since_analyze` = 0; `relpages` and `relallvisible` rewritten | `n_dead_tup` now says what `ANALYZE` saw, including stubs a bypass left ([pgstat_relation.c#report_analyze-dead](../../../raw/postgres-17/src/backend/utils/activity/pgstat_relation.c#L328-L329), [analyze.c#analyze-relstats](../../../raw/postgres-17/src/backend/commands/analyze.c#L623-L645)) |
| any statement that consumes an XID, then another `VACUUM` | deleted index pages not yet reusable | reusable, where the access method's cleanup scans the index | closes the recycling lag the index half describes |
| new writes to the table | pages all-visible | the touched pages lose their visibility-map bit | the proof applies to one statement; new churn needs the whole procedure again |

#### The two dead-row counters disagree on purpose

`VACUUM` and `ANALYZE` both publish a dead-row count, and they count different things. `VACUUM`'s `tuples:` line and its `n_dead_tup` write leave out the dead item identifiers a bypass or the failsafe kept: the code says so where it reports to the statistics system, and the bypass decision says so again ([vacuumlazy.c#report-vacuum](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L577-L591), [vacuumlazy.c#bypass-conditions](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1899-L1934)). `ANALYZE` counts every `LP_DEAD` stub as a dead row ([heapam_handler.c#analyze-dead-rows](../../../raw/postgres-17/src/backend/access/heap/heapam_handler.c#L1054-L1085)). So after a bypass the `VACUUM` half reads clean and the `ANALYZE` half does not. A proof that read only the `VACUUM` half would pass a bypassed run; a proof that read only `ANALYZE` could not tell a bypass from a horizon holder. That is why Stage C reads both, together with the `index scan` label that names the bypass.

#### Summary of the causal chain

A quiet cluster - no horizon holder, no other session, clean buffers, no phase switched off, far from the failsafe, timeouts at 0 - runs one `VACUUM (VERBOSE, ANALYZE, PARALLEL 0)` per table. Its removal cutoff is then newer than every churn transaction, so every deleted row is dead rather than recently dead. With no other pins every scanned page takes the cleanup lock and is pruned, and the dead item identifiers go through index vacuuming and the second heap pass unless the bypass declines them. Index cleanup and, when due, truncation follow, and the statistics are written. The report then shows 0 dead-but-not-removable rows, no missed or bypassed line, no warning, a finished block for the table and its TOAST table, and an `ANALYZE` line with 0 dead rows. The counters move by one and `relallvisible` meets `relpages`. Any failed check names its node of the map and its tier: a holder is removed, a pin is retried and then waited out with `FREEZE`, and a bypass is overridden with `INDEX_CLEANUP ON`, both declared.

### The auto-analyze stand-in on a GIN index

On a GIN index an auto-analyze is not a statistics-only event, so a fixture whose point is the auto-analyze-only maintained state cannot be built with `ANALYZE`.

- A worker's bare `ANALYZE` reaches `ginvacuumcleanup` with `analyze_only` set and, because the caller is an autovacuum worker, flushes the pending list through `ginInsertCleanup` with `full_clean` false and `fill_fsm` true, then returns before the page census ([ginvacuum.c#analyze_only-worker](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L709-L717), [ginfast.c#ginInsertCleanup](../../../raw/postgres-17/src/backend/access/gin/ginfast.c#L776-L783)).
- The same call from any other backend returns immediately - "Otherwise, an ANALYZE-only call is a no-op" - and `analyze_rel` reaches it at all only outside a `VACUUM ANALYZE` ([ginvacuum.c#analyze_only-worker](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L709-L717), [analyze.c#analyze-only-cleanup](../../../raw/postgres-17/src/backend/commands/analyze.c#L694-L721)).

**The rule.** A fixture that models a table maintained by auto-analyze alone - insert-heavy, past the analyze threshold, under both vacuum thresholds - runs `ANALYZE` **and** `gin_clean_pending_list()` on the measured index, and declares that pair as its maintenance. The `ANALYZE` is the part that writes the statistics; the flush is the part a foreground `ANALYZE` cannot do.

Three differences a run must state, because the stand-in is not the worker's path:

| Difference | What it costs the fixture |
|---|---|
| `gin_clean_pending_list` passes `full_clean` true where the worker's analyze passes false ([ginfast.c#gin_clean_pending_list](../../../raw/postgres-17/src/backend/access/gin/ginfast.c#L1030-L1091)), and that flag is what makes the cleanup ignore the tail it remembered at its start and work until the list is empty ([ginfast.c#full_clean-tail](../../../raw/postgres-17/src/backend/access/gin/ginfast.c#L879-L888)) | only a concurrent inserter can expose the difference, because with no writer there is no page past the remembered tail; a fixture that keeps a writer running across its maintenance may not use the stand-in |
| the flush runs as the index's owner under `RowExclusiveLock` on the index, and refuses during recovery, on another session's temporary index, and as a `DEBUG1` no-op on an index that is not valid ([ginfast.c#gin_clean_pending_list](../../../raw/postgres-17/src/backend/access/gin/ginfast.c#L1030-L1091)), where the worker's analyze holds `ShareUpdateExclusiveLock` on the table ([analyze.c#analyze-lockmode](../../../raw/postgres-17/src/backend/commands/analyze.c#L135-L145)) | a run records which lock its maintenance took, and the index-only form is the same writer no table lock can exclude ([The measurement lock](#the-measurement-lock)) |
| neither path rewrites the metapage's page counts, because `ginUpdateStats` is reached only from the census inside `ginvacuumcleanup` ([ginvacuum.c#analyze_only-worker](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L709-L717), [ginvacuum.c#ginvacuumcleanup-census](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L752-L789), [ginutil.c#ginUpdateStats](../../../raw/postgres-17/src/backend/access/gin/ginutil.c#L645-L650)) | an auto-analyze-maintained fixture carries stale `nTotalPages`, `nEntryPages`, `nDataPages` and `nEntries` **by construction**. It may not claim the settle step, its metapage cross-check does not apply, and every metapage-derived quantity on it is declared a `level` or withheld ([The settle step, and proving it ran](#the-settle-step-and-proving-it-ran), [How a published quantity is declared and scored](#how-a-published-quantity-is-declared-and-scored)) |

What the flush does leave as evidence, which a run records rather than assuming: `shiftList` decrements `nPendingPages` and `nPendingHeapTuples` and zeroes both once the list drains completely ([ginfast.c#shiftList-metapage](../../../raw/postgres-17/src/backend/access/gin/ginfast.c#L603-L616)), records each freed page in the FSM when `fill_fsm` is set ([ginfast.c#shiftList-fill_fsm](../../../raw/postgres-17/src/backend/access/gin/ginfast.c#L667-L668)) - which both the worker's path and the stand-in ask for, so the FSM cross-check behaves the same under either - `ginInsertCleanup` vacuums the index FSM once it has freed anything ([ginfast.c#insertcleanup-fsm-vacuum](../../../raw/postgres-17/src/backend/access/gin/ginfast.c#L1014-L1020)), and the function returns its own count of deleted pending pages ([ginfast.c#gin_clean_pending_list](../../../raw/postgres-17/src/backend/access/gin/ginfast.c#L1030-L1091)).

The same `full_clean` distinction appears on the settle path: when `ginbulkdelete` did not run, `ginvacuumcleanup` flushes the pending list itself and passes `full_clean` as the negation of "am I an autovacuum worker", so a foreground `VACUUM` cleans the whole list where a worker's `VACUUM` stops at the remembered tail ([ginvacuum.c#cleanup-pending-when-no-bulkdelete](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L719-L729)).

### The simulated auto-analyze census

After the maintenance step and before the decide phase, the run recomputes the launcher's **analyze** verdict for every table in the fixture database and analyzes the tables it names. The maintenance step has already analyzed every churned table, so what the census decides are the tables no churn touched: one whose build phase left it past the threshold is analyzed here, and one whose build-phase `ANALYZE` still describes it is left alone. The census is also the recheck that the counters were published in the right order.

The rule is the engine's own test rather than a per-fixture annotation: `relation_needs_vacanalyze` sets `doanalyze` when the table's `mod_since_analyze` is **strictly greater** than `anl_base_thresh + anl_scale_factor * reltuples` ([autovacuum.c#vacthresh-anlthresh](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3074-L3076), [autovacuum.c#verdicts](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3092-L3095)).

| Input | Effective value the census must use | Evidence |
|---|---|---|
| base threshold | `relopts->analyze_threshold` when `>= 0`, else `autovacuum_anl_thresh` | [autovacuum.c#anl-effective-values](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3011-L3017) |
| scale factor | `relopts->analyze_scale_factor` when `>= 0`, else `autovacuum_anl_scale` | [autovacuum.c#anl-effective-values](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3011-L3017) |
| row count | `pg_class.reltuples`, taken as 0 when it is negative | [autovacuum.c#census-inputs](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3063-L3072) |
| counter | `mod_since_analyze` from the table's shared statistics entry | [autovacuum.c#census-inputs](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3063-L3072) |
| comparison | strictly greater than, so a table landing exactly on its threshold is left alone | [autovacuum.c#verdicts](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3092-L3095) |
| short circuit | `autovacuum_enabled = false` makes `doanalyze` false outright, wraparound forcing aside | [autovacuum.c#av_enabled-return](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L3048-L3054) |

The reloptions arrive as the `AutoVacOpts` member of the table's `StdRdOptions`, decoded by `extract_autovac_opts`, and an unset member reads back below zero, which is exactly what makes the `>= 0` test the precedence rule ([autovacuum.c#extract_autovac_opts](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L2704-L2723), [rel.h#AutoVacOpts](../../../raw/postgres-17/src/include/utils/rel.h#L308-L326)). A census that reads `current_setting('autovacuum_analyze_threshold')` for every table computes the wrong threshold for any table that carries the reloption. At the shipped defaults of 50 and 0.1 the effective threshold is 50 rows plus a tenth of the estimated row count ([guc_tables.c#autovacuum_analyze_threshold](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L3367-L3375), [guc_tables.c#autovacuum_analyze_scale_factor](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L3906-L3914)); both GUCs are `PGC_SIGHUP`, so a cluster-wide change is a reload, and either reloption is an `ALTER TABLE` taking `ShareUpdateExclusiveLock` ([reloptions.c#autovacuum_analyze_threshold](../../../raw/postgres-17/src/backend/access/common/reloptions.c#L243-L251), [reloptions.c#autovacuum_analyze_scale_factor](../../../raw/postgres-17/src/backend/access/common/reloptions.c#L417-L425)).

**Two publication points, not one.** Running the phases in order does not put the churn into `mod_since_analyze`. A backend accumulates its table counts locally, and they reach the shared entry only when `pgstat_report_stat` flushes them, which it does between transactions and, unforced, at most once per `PGSTAT_MIN_INTERVAL` of 1000 ms ([pgstat.c#PGSTAT_MIN_INTERVAL](../../../raw/postgres-17/src/backend/utils/activity/pgstat.c#L117-L122), [pgstat.c#pgstat_report_stat](../../../raw/postgres-17/src/backend/utils/activity/pgstat.c#L583-L600), [pgstat.c#flush-intervals](../../../raw/postgres-17/src/backend/utils/activity/pgstat.c#L636-L655), [postgres.c#pgstat_report_stat-idle](../../../raw/postgres-17/src/backend/tcop/postgres.c#L4662-L4681)); only such a flush adds to the counter ([pgstat_relation.c#mod_since_analyze](../../../raw/postgres-17/src/backend/utils/activity/pgstat_relation.c#L857-L860)). Meanwhile the `ANALYZE` half of the maintenance step zeroes that counter and forgets what was committed while it ran ([pgstat_relation.c#report_analyze-reset](../../../raw/postgres-17/src/backend/utils/activity/pgstat_relation.c#L331-L337)).

| When | What must hold | How to get it |
|---|---|---|
| after the churn, before the maintenance `VACUUM ANALYZE` and before the census reads the counter | every churn session's table counts are in the shared entry | `SELECT pg_stat_force_next_flush();` in each churn session ([pg_proc.dat#pg_stat_force_next_flush](../../../raw/postgres-17/src/include/catalog/pg_proc.dat#L5916-L5920), [pgstat.c#pgstat_report_stat](../../../raw/postgres-17/src/backend/utils/activity/pgstat.c#L583-L600)); or let each churn session exit; or wait out `PGSTAT_MIN_INTERVAL` |
| after the maintenance `ANALYZE`, before any recheck | nothing published after the reset is read as new churn | publish first, analyze second, then re-read; a recheck that still disagrees is recorded as a disagreement, not analyzed again |

The read side is a third hazard. The census reads `n_mod_since_analyze` from `pg_stat_all_tables` ([system_views.sql#launcher-counters](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L688-L690)), and `stats_fetch_consistency` - `PGC_USERSET`, so session or transaction scope, default `cache` ([guc_tables.c#stats_fetch_consistency](../../../raw/postgres-17/src/backend/utils/misc/guc_tables.c#L4966-L4974)) - decides whether a second read of the same entry returns the first answer again, so a census that reads, analyzes and re-reads inside one transaction discards the cached statistics with `pg_stat_clear_snapshot()` ([pg_proc.dat#pg_stat_clear_snapshot](../../../raw/postgres-17/src/include/catalog/pg_proc.dat#L5911-L5915)). The engine's own statistics test uses exactly this force-flush-then-read sequence under an explicit `stats_fetch_consistency = snapshot` ([stats.sql#force-flush](../../../raw/postgres-17/src/test/regress/sql/stats.sql#L101-L110)).

**What the census costs a GIN fixture.** Every churned table is analyzed by the maintenance step and every unchurned table past its threshold by the census, so a fixture whose point was a stale row count is scored against fresh statistics instead. On this protocol that cost is narrower than it looks, because the quantities scored here are bytes and pages, and the metapage counts are the one census the `ANALYZE` cannot refresh at all ([The auto-analyze stand-in on a GIN index](#the-auto-analyze-stand-in-on-a-gin-index)). What does move is the catalog: a method that reads the index's `relpages` or `reltuples` is reading a value the maintenance step or the census has just rewritten, and it says so.

### The measurement lock

When a census has to be compared with anything - an earlier census, a later rebuild, another index - it runs inside one transaction holding `SHARE ROW EXCLUSIVE` on the index's **table**. That mode conflicts with `ROW EXCLUSIVE`, `SHARE UPDATE EXCLUSIVE`, `SHARE`, itself, `EXCLUSIVE` and `ACCESS EXCLUSIVE`, and is compatible with `ACCESS SHARE` and `ROW SHARE` only ([lock.c#LockConflicts](../../../raw/postgres-17/src/backend/storage/lmgr/lock.c#L64-L104), [mvcc.sgml#SHARE-ROW-EXCLUSIVE](../../../raw/postgres-17/doc/src/sgml/mvcc.sgml#L1023-L1043)). So it excludes writers, `VACUUM` and `ANALYZE` - both of which take `ShareUpdateExclusiveLock` ([vacuum.c#vacuum-lockmode](../../../raw/postgres-17/src/backend/commands/vacuum.c#L2049-L2056), [analyze.c#analyze-lockmode](../../../raw/postgres-17/src/backend/commands/analyze.c#L135-L145)), [`VACUUM FULL`](../../glossary.md#vacuum-full)'s `AccessExclusiveLock` ([vacuum.c#vacuum-lockmode](../../../raw/postgres-17/src/backend/commands/vacuum.c#L2049-L2056)), and both `REINDEX` forms - while leaving ordinary readers alone.

Three rules follow from the source, and a run may not weaken them:

- **`SHARE` is one step weaker and not enough.** A plain `REINDEX INDEX` takes `ShareLock` on the table, which is self-compatible, so it would proceed and swap the index's storage under a running census ([indexcmds.c#RangeVarCallbackForReindexIndex](../../../raw/postgres-17/src/backend/commands/indexcmds.c#L2857-L2872), [indexcmds.c#ReindexIndex-locks-and-dispatch](../../../raw/postgres-17/src/backend/commands/indexcmds.c#L2824-L2849)).
- **The lock cannot be taken on the index, and one writer escapes it.** `LOCK TABLE` refuses anything but a plain table, a partitioned table or a view ([lockcmds.c#RangeVarCallbackForLockTable](../../../raw/postgres-17/src/backend/commands/lockcmds.c#L70-L107)), while `gin_clean_pending_list` locks only the index ([ginfast.c#gin_clean_pending_list](../../../raw/postgres-17/src/backend/access/gin/ginfast.c#L1030-L1091)). The protocol closes that hole operationally - the index's owner does not flush the pending list during a measurement - and a run states that it did so.
- **The privilege is not `SELECT`.** `LockTableAclCheck` accepts `MAINTAIN`, `UPDATE`, `DELETE` or `TRUNCATE` for every mode above `ROW EXCLUSIVE`, and adds `SELECT` only at `ACCESS SHARE` ([lockcmds.c#LockTableAclCheck](../../../raw/postgres-17/src/backend/commands/lockcmds.c#L279-L299)). A raw-page census already needs superuser ([rawpage.c#get_raw_page_internal](../../../raw/postgres-17/contrib/pageinspect/rawpage.c#L141-L199)), so this binds only a method built on `pgstatginindex`, whose execute privilege is granted to `pg_stat_scan_tables` ([pgstattuple--1.4--1.5.sql#pgstatginindex-grant](../../../raw/postgres-17/contrib/pgstattuple/pgstattuple--1.4--1.5.sql#L49-L57)).

The lock is a cost, not a default: it blocks every writer on the table for the duration of the census, so a run reports the interval it held and pairs it with `lock_timeout`.

### The oracle

The oracle is a measured `REINDEX INDEX` on the settled fixture, with `pg_relation_size(index, 'main')` read immediately before and after. `reindex_index` suppresses the target index, gives it a new [relfilenode](../../glossary.md#relfilenumber) and calls `index_build`, so the after-reading is a new physical file rather than a compacted old one ([index.c#reindex_index-rebuild](../../../raw/postgres-17/src/backend/catalog/index.c#L3781-L3789)). `pg_relation_size` with an explicit [fork](../../glossary.md#fork) sums the segments of that one fork ([dbsize.c#pg_relation_size](../../../raw/postgres-17/src/backend/utils/adt/dbsize.c#L345-L371), [dbsize.c#calculate_relation_size](../../../raw/postgres-17/src/backend/utils/adt/dbsize.c#L302-L343), [func.sgml#pg_relation_size](../../../raw/postgres-17/doc/src/sgml/func.sgml#L29627-L29643)), which is the right denominator because a page census counts main-fork blocks and nothing else.

Two constraints on using it:

- **The oracle measures returned filesystem bytes, not waste.** The engine reclaims a GIN page into the index's own FSM and never truncates the relation, so a page census and the oracle answer different questions by construction ([ginvacuum.c#ginvacuumcleanup-relength](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L794-L802), [ginutil.c#GinNewBuffer](../../../raw/postgres-17/src/backend/access/gin/ginutil.c#L299-L335)).
- **A run must report the `maintenance_work_mem` the rebuild ran at.** The GIN build flushes its accumulator to the index whenever allocated memory reaches `maintenance_work_mem` ([gininsert.c#build-flush](../../../raw/postgres-17/src/backend/access/gin/gininsert.c#L286-L292)), so the rebuilt size is a function of the budget as well as of the data. "What a rebuild would return" is not a property of the index alone, and an unlabelled oracle number is not reproducible.

### How a published quantity is declared and scored

Before the run, every column the method publishes is declared as exactly one of three kinds. The declaration is filed with the fixture plan and may not be rewritten afterwards.

| Declared kind | What it claims against the oracle | Verdicts |
|---|---|---|
| lower bound | the quantity never exceeds the bytes a rebuild returns | `HELD`, `VIOLATED` |
| upper bound | the quantity is never less than the bytes a rebuild returns | `HELD`, `VIOLATED` |
| level | the quantity has no relation to what a rebuild returns | `DECLARED` - never scored as a bound, and never published as reclaimable space |

Two columns are mandatory for a run to be readable: `truth_pct`, the oracle's own fraction of the churned file, computed from the two size readings and nothing else; and `declared_kind` per published quantity, filed before the run. A `VIOLATED` verdict is corrected in the method or moved to a `level`, not annotated away.

A method that also makes a **decision** - rebuild, or leave alone - declares its own threshold, because the protocol fixes the oracle and not the threshold. The decision is then scored `PASS`, `FALSE POSITIVE` (rebuilt, and the rebuild returned less than the method's own threshold) or `FALSE NEGATIVE` (not rebuilt, and a rebuild would have returned more). A run reports the threshold beside the score; a threshold chosen after the results is not a scored run.

### The four mandatory cross-checks

No GIN number is published from a single reading. All four checks run, and a run records which ones agreed.

| Check | What it compares | Direction and failure mode |
|---|---|---|

### The concurrency rules

- **Flag what the progress views can see.** A census records whether [`pg_stat_progress_vacuum`](../../glossary.md#progress-reporting), `pg_stat_progress_analyze` or `pg_stat_progress_create_index` showed work on the relation at either end of its scan ([system_views.sql#pg_stat_progress_vacuum](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L1209-L1227), [system_views.sql#pg_stat_progress_analyze](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L1188-L1207), [system_views.sql#pg_stat_progress_create_index](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L1256-L1289)). The `create_index` view names `REINDEX` and [`REINDEX CONCURRENTLY`](../../glossary.md#concurrently) explicitly, so a rebuild racing the census is visible by command.
- **The flag is not a guarantee.** A maintenance command that starts and finishes between the two progress reads leaves no trace in either, so a flagged census is unreliable and an unflagged one is only unrefuted. Where a comparison must be exact, take the lock instead of reading the flags; see [The measurement lock](#the-measurement-lock).
- **Read a busy index twice.** Two censuses that disagree on an unchanging file size are evidence of a mixed-instant reading, and that evidence exists because no relation lock is held across the page reads ([rawpage.c#get_raw_page_internal](../../../raw/postgres-17/contrib/pageinspect/rawpage.c#L141-L199)).

### The reading rules

These decide which numbers may be published, and as what.

- **Report the page classes separately.** Whole-page waste, live-page slack and pending-list bytes have three different relations to a rebuild; a single combined percentage is page accounting and must be declared a `level` unless the run scores it as a bound and it holds.
- **Entry-page slack is insertion capacity, not a defect.** The engine's own entry-page test charges a line pointer for the next tuple ([ginentrypage.c#entryIsEnoughSpace](../../../raw/postgres-17/src/backend/access/gin/ginentrypage.c#L458-L482), [bufpage.c#PageGetFreeSpace](../../../raw/postgres-17/src/backend/storage/page/bufpage.c#L898-L923)), so a freshly built index carries a large, healthy entry slack.
- **Compare an index to its own history or to a rebuilt twin, never to another [opclass](../../glossary.md#operator-class).** GIN has no `fillfactor` reloption ([ginutil.c#ginoptions](../../../raw/postgres-17/src/backend/access/gin/ginutil.c#L601-L614)), so the engine defines no target density for a GIN build, and a cross-opclass density comparison has no fixed point.
- **Pending bytes are a `fastupdate` tuning signal, not waste.** The remedies are `VACUUM`, `gin_clean_pending_list()` or `gin_pending_list_limit` ([gin.sgml#GIN-Fast-Update](../../../raw/postgres-17/doc/src/sgml/gin.sgml#L500-L537)), and the flush itself can allocate ([ginfast.c#flush-entry-insert](../../../raw/postgres-17/src/backend/access/gin/ginfast.c#L926-L933), [ginbtree.c#split-newbuffer](../../../raw/postgres-17/src/backend/access/gin/ginbtree.c#L463-L466)).
- **Dead pages that will not go away may be waiting on a transaction, not on `VACUUM`.** The horizon test is in `GinPageIsRecyclable` ([ginvacuum.c#GinPageIsRecyclable](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L805-L829)), so a run that reports stuck pages also reports whether a snapshot was held.
- **Suppress every slack-derived field when the format is not version 2.** `pd_lower` on a pre-9.4 posting-tree page cannot be trusted, and the struct says so ([ginblock.h#pd_lower-untrusted](../../../raw/postgres-17/src/include/access/ginblock.h#L302-L309), [ginblock.h#GIN_CURRENT_VERSION](../../../raw/postgres-17/src/include/access/ginblock.h#L86-L103)). Publish the page counts, withhold the slack and everything computed from it.
- **Suppress slack-derived fields when any page could not be decoded or classified.** `gin_page_opaque_info` raises on a foreign special-area size and prints unrecognized flag bits as hex rather than guessing a class ([ginfuncs.c#gin_page_opaque_info](../../../raw/postgres-17/contrib/pageinspect/ginfuncs.c#L98-L172)); `gin_leafpage_items` refuses any page whose flags are not exactly `GIN_DATA | GIN_LEAF | GIN_COMPRESSED` ([ginfuncs.c#gin_leafpage_items-flags](../../../raw/postgres-17/contrib/pageinspect/ginfuncs.c#L211-L226)); and `get_page_from_raw` raises on a page of the wrong size ([rawpage.c#get_page_from_raw](../../../raw/postgres-17/contrib/pageinspect/rawpage.c#L214-L234)). One such page can cost a multi-index statement every row it would have returned, so a statement scored here reports a per-page status instead of failing.
- **Handle the new page in both readers.** `gin_metapage_info`, `gin_page_opaque_info` and `gin_leafpage_items` return NULL for a page `PageIsNew` accepts ([ginfuncs.c#gin_metapage_info](../../../raw/postgres-17/contrib/pageinspect/ginfuncs.c#L30-L95), [ginfuncs.c#gin_page_opaque_info](../../../raw/postgres-17/contrib/pageinspect/ginfuncs.c#L98-L172), [bufpage.h#PageIsNew](../../../raw/postgres-17/src/include/storage/bufpage.h#L226-L234)), while `page_header` has no such test and reports the zeros it finds ([rawpage.c#page_header](../../../raw/postgres-17/contrib/pageinspect/rawpage.c#L245-L266)). An all-zero page is recyclable whole-page waste, not a zero-slack entry page.

### What the protocol does not cover

Named limits, so a consumer page does not claim more than the protocol gives.

- **It scores the number, not the instrument.** Whether a method reads raw pages, `pgstatginindex`, the FSM or the catalogs is out of scope; the declared kind and the oracle are what is checked. A method that cannot run on a required behavior records that it skipped it.
- **There is no structural verifier to corroborate a page census.** `contrib/amcheck` has no GIN entry point, so a census's page classification is checked only against the metapage, the FSM and `VACUUM`'s own output ([amcheck--1.3--1.4.sql#bt-only](../../../raw/postgres-17/contrib/amcheck/amcheck--1.3--1.4.sql#L13-L25)).
- **One block size and one platform.** Every page constant derives from [`BLCKSZ`](../../glossary.md#blcksz) and `MAXALIGN`; the protocol fixes no second build.
- **The pending-list hole stays open.** No lock available from SQL excludes a direct `gin_clean_pending_list()` by the index's owner ([lockcmds.c#RangeVarCallbackForLockTable](../../../raw/postgres-17/src/backend/commands/lockcmds.c#L70-L107), [ginfast.c#gin_clean_pending_list](../../../raw/postgres-17/src/backend/access/gin/ginfast.c#L1030-L1091)). The protocol handles it by operational rule only.
- **A standby is not a scored environment.** The settle step cannot run there ([utility.c#recovery-gate](../../../raw/postgres-17/src/backend/tcop/utility.c#L570-L583), [ginfast.c#recovery-refusal](../../../raw/postgres-17/src/backend/access/gin/ginfast.c#L1037-L1041)).
- **The vacuum side of the launcher is recorded, not simulated.** The dead-tuple and insert thresholds are stated under [The maintenance assumption](#the-maintenance-assumption) and never applied: the maintenance step runs after every churn. A method whose reading differs between a table the launcher would have vacuumed and one it would have left is therefore exercised on the first case only, and no fixture builds a GIN index whose dead entries were never vacuumed.
- **A `VACUUM` whose index cleanup did not run is not required coverage.** A conforming run does not have to reach one, and [The maintenance must not be defeated](#the-maintenance-must-not-be-defeated) declares no exception for one. Such a `VACUUM` still returns success: `INDEX_CLEANUP` off and the wraparound failsafe each clear `do_index_cleanup`, and `ginvacuumcleanup` is reached only while it is set ([vacuumlazy.c#do_index_cleanup-init](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L387-L397), [vacuumlazy.c#failsafe-disables-cleanup](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L2320-L2326), [vacuumlazy.c#lazy_cleanup_all_indexes-gate](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1064-L1066)). Point 3 of [The settle step, and proving it ran](#the-settle-step-and-proving-it-ran) therefore still binds every run, but no required fixture shows that proof catching such a `VACUUM`.
- **No fixture overrides the four vacuum-side reloptions.** The census applies the reloption-over-GUC precedence to the analyze parameters, and the same selection exists for the vacuum and insert-vacuum pair ([autovacuum.c#vac-effective-values](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L2993-L3009)); nothing in the protocol exercises that half of `relation_needs_vacanalyze`.
- **Only one autovacuum-worker behavior is stood in for.** The stand-in reproduces the worker's pending-list flush, because that is the one GIN-visible thing a worker does that a foreground session cannot ([analyze.c#analyze-only-cleanup](../../../raw/postgres-17/src/backend/commands/analyze.c#L694-L721)). Everything else a worker carries - its cost-delay budget, its `last_autoanalyze_time` and `autoanalyze_count` bookkeeping ([pgstat_relation.c#report_analyze-worker-fields](../../../raw/postgres-17/src/backend/utils/activity/pgstat_relation.c#L339-L343)), its naptime scheduling - is outside the protocol.
- **The engine's own test suites validate the build, not the method.** The shipped GIN and `pageinspect` tests assert function behavior on tiny fixtures; none of them reads a bloat estimate ([gin.sql#pageinspect-gin](../../../raw/postgres-17/contrib/pageinspect/sql/gin.sql#L1-L19)).

## Interactions with Other Concepts

- **VACUUM.** The protocol depends on `VACUUM` for the only state transition it cannot make itself: dead entries into recyclable pages and a refreshed metapage. It makes four boundaries explicit - it never reproduces the launcher's *vacuum* verdicts, because the maintenance step runs after every churn regardless of the counters; it does not assume a `VACUUM` that returned actually cleaned the index; it forbids a fixture from defeating the `VACUUM` it issued, and names the two cases where defeating it is the declared point ([The maintenance must not be defeated](#the-maintenance-must-not-be-defeated)); and it treats more than one `VACUUM` as normal rather than as a fixture quirk. Beside those boundaries it recommends, without requiring, a procedure that proves from the statement's own report and statistics that the `VACUUM` did all its work ([Recommended: proving VACUUM did all its work](#recommended-proving-vacuum-did-all-its-work)).
- **Autovacuum and auto-analyze.** The protocol assumes both ran and stands in for them, rather than modelling an unmaintained database: the maintenance step is the worker's command, the census is the worker's analyze verdict recomputed per table, and the launcher's vacuum-side thresholds are recorded so the gap is visible. The one place the substitution is not exact is GIN's own: an auto-analyze flushes a pending list and a foreground `ANALYZE` does not, which is why the stand-in is explicit ([The auto-analyze stand-in on a GIN index](#the-auto-analyze-stand-in-on-a-gin-index)). How to tune autovacuum for a GIN workload is not a bloat question and is not decided here.
- **[Cumulative statistics](../../glossary.md#cumulative-statistics).** The census is the only required part of the protocol that reads a statistics view rather than a page or a catalog, and the recommended completeness procedure also reads `vacuum_count`, `analyze_count` and `n_dead_tup`; both inherit that subsystem's timing: pending counts are published by a flush and not by a commit, and a view read may be served from a cached snapshot. The protocol's boundary is that it fixes the publication points and the fetch consistency and then reads; it makes no claim about the subsystem beyond the counter it uses.
- **The free space map.** The FSM is a cross-check, not a source of truth: for an index it records only free-versus-in-use, and the value read back is a category floor ([indexfsm.c#index-fsm-notes](../../../raw/postgres-17/src/backend/storage/freespace/indexfsm.c#L14-L20), [freespace.c#fsm_space_cat_to_avail](../../../raw/postgres-17/src/backend/storage/freespace/freespace.c#L427-L435)). Whether a page a rebuild would drop is in the FSM is a separate question from whether a rebuild would drop it.
- **The GIN pending list and `fastupdate`.** The protocol requires the pending list to be settled and reported separately, and treats a flush as an action with a cost. How to tune `fastupdate` is not a bloat question.
- **REINDEX.** The oracle is the blocking `REINDEX INDEX` form. Lock levels, the concurrent form's behavior and failure outcomes belong to the method or to a `REINDEX` question page, not here.
- **B-tree bloat measurement.** The B-tree suite is a different document with a different contract: it defines a fixture corpus and decision bands, where this page defines a protocol and leaves the corpus to the consumer. See [Mandatory B-Tree Bloat Tests](mandatory-btree-bloat-tests.md) for navigation; no claim on this page rests on it.
- **The measurement interface.** `pageinspect`, `pgstattuple` and `pg_freespacemap` are inputs whose refusals shape what a run can say ([pageinspect.control:3](../../../raw/postgres-17/contrib/pageinspect/pageinspect.control#L3), [pgstattuple.control:3](../../../raw/postgres-17/contrib/pgstattuple/pgstattuple.control#L3), [pg_freespacemap.control:3](../../../raw/postgres-17/contrib/pg_freespacemap/pg_freespacemap.control#L3)). The protocol scores the number a method publishes, not the extension it came from.

## Open Questions

- **The protocol fixes no fixture corpus, so coverage is self-reported.** [Coverage the protocol requires](#coverage-the-protocol-requires) lists behaviors, not fixtures, and a run says which of its own fixtures reached each one. Two consumer pages can therefore both conform while exercising very different shapes, and nothing here makes their scores comparable. Whether this page should grow a named corpus, or a second page should hold one, is undecided.
- **The pending-list hole cannot be closed from SQL.** A direct `gin_clean_pending_list()` by the index's owner is invisible to the measurement lock, and each census on either side of it is internally consistent, so no cross-check flags the pair. The protocol handles it by operational rule, which is not enforcement.
- **A maintenance command entirely between the two progress reads is undetectable.** The concurrency flag is a sampling of two instants; a `VACUUM` that starts and finishes inside the census leaves nothing for the flag, the size bracket or the metapage check to catch. Only the lock removes the case, and the lock is not always available.
- **No structural verifier corroborates the page classification.** With no GIN entry point in `contrib/amcheck`, a census's classification is checked only against three readings that share its assumptions. A misclassification consistent with the metapage would pass every cross-check here.
- **The decision threshold is the method's, not the protocol's.** Because a GIN waste reading has no engine-defined target density, this page deliberately fixes the oracle and leaves the rebuild threshold to the method. That makes a `FALSE NEGATIVE` on one page incomparable with a `FALSE NEGATIVE` on another, and there is no source basis in v17 for choosing a shared threshold.
- **The oracle is budget-dependent and the protocol only requires it to be labelled.** A run reports the `maintenance_work_mem` it rebuilt at and, where required, more than one budget; it does not define which budget the "true" reclaimable figure belongs to.
- **The vacuum side of the launcher is assumed, never simulated.** [The maintenance assumption](#the-maintenance-assumption) records the dead-tuple and insert thresholds and then runs the maintenance step regardless of them, so the protocol has no counterpart to the census on the vacuum side. Adding one would recover the sub-threshold case, at the price of re-creating GIN indexes whose dead entries were never vacuumed unless the churn `VACUUM` stayed mandatory beside it. Which of the two costs is worse is undecided.
- **Two of the stand-in's three differences from a real auto-analyze stand.** The `full_clean` difference is argued away by the protocol's own no-concurrency rule, but the lock and privilege path is genuinely different, and neither the worker's flush nor the stand-in refreshes the metapage counts ([The auto-analyze stand-in on a GIN index](#the-auto-analyze-stand-in-on-a-gin-index)). Nothing in the protocol proves that a stood-in fixture is byte-identical to one an autovacuum worker produced, because reaching the worker's path at all means letting the launcher run, which the isolation rule forbids.
- **An auto-analyze-maintained fixture cannot satisfy the settle step, so it loses a cross-check.** Its metapage page counts are stale by construction, which removes the metapage cross-check from [The four mandatory cross-checks](#the-four-mandatory-cross-checks) for that fixture and leaves three. Whether such a fixture should be restricted to metapage-free quantities, or scored at all, is the asker's call.
- **The census's second publication point has no proof.** A run can force a flush and then read, but nothing in the engine reports "every pending count for this relation is published", so a partial flush under lock contention looks identical to having had nothing pending ([pgstat.c#flush-intervals](../../../raw/postgres-17/src/backend/utils/activity/pgstat.c#L636-L655)).
- **The effectiveness proof of [The maintenance must not be defeated](#the-maintenance-must-not-be-defeated) is one-sided, and on GIN the settle proof cannot help it.** A nonzero `dead but not yet removable` count proves the horizon was pinned ([vacuumlazy.c#verbose-tuples-line](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L657-L663)), but a zero count proves only that nothing was pinned for that table at that moment, and a fixture whose churn was insert-only produces no signal at all. The settle step is no substitute, because `ginvacuumcleanup`'s `stats == NULL` branch satisfies it whether or not an entry was removed ([ginvacuum.c#cleanup-pending-when-no-bulkdelete](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L719-L729)), and nothing in the engine reports "no session or slot held the horizon for the duration of this command": `pg_stat_activity` and `pg_replication_slots` are reads taken beside the maintenance step rather than interlocks around it ([system_views.sql#pg_stat_activity-xmin](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L878-L885), [system_views.sql#pg_replication_slots-xmin](../../../raw/postgres-17/src/backend/catalog/system_views.sql#L1006-L1017)). [Recommended: proving VACUUM did all its work](#recommended-proving-vacuum-did-all-its-work) narrows the gap without closing it: its `tuples missed` line, `index scan` label and `ANALYZE` dead-row count are readings taken inside the statement rather than beside it ([vacuumlazy.c#verbose-missed-line](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L664-L668), [vacuumlazy.c#verbose-index-scan-line](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L695-L717), [analyze.c#verbose-sample-line](../../../raw/postgres-17/src/backend/commands/analyze.c#L1296-L1306)), but its horizon-holder queries are still reads, and on a fixture with no churn none of those counters has anything to count.
- **`DISABLE_PAGE_SKIPPING` does less than its documentation says.** The reference page says the option disables all page skipping, including pages skipped "to avoid waiting for other sessions to finish using them" ([ref/vacuum.sgml#DISABLE_PAGE_SKIPPING](../../../raw/postgres-17/doc/src/sgml/ref/vacuum.sgml#L147-L164)). The source makes the run aggressive and turns off visibility-map skipping, but a page whose cleanup lock is refused still takes the no-prune path unless one of its tuples is older than the freeze cutoff, which stays at `vacuum_freeze_min_age` ([vacuumlazy.c#aggressive-and-skipwithvm](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L449-L467), [vacuumlazy.c#noprune-aggressive-wait](../../../raw/postgres-17/src/backend/access/heap/vacuumlazy.c#L1713-L1733), [vacuum.c#FreezeLimit](../../../raw/postgres-17/src/backend/commands/vacuum.c#L1160-L1177)). The source wins, which is why the procedure escalates with `FREEZE` instead.
- **The recommended procedure has no consumer run yet.** No consumer page has filed a run under it, and no shipped test exercises the bypass. Its SQL and shell checks were exercised against a disposable build of this pin, but the page publishes no number from that run, so how often each branch of its map occurs on GIN fixtures is unmeasured.
- **`CHECKPOINT` lowers the risk of a background-writer pin; it does not remove it.** A checkpoint that starts while the statement runs may write a page the statement has not reached yet, and the background writer keeps running ([bufmgr.c#SyncOneBuffer-pin](../../../raw/postgres-17/src/backend/storage/buffer/bufmgr.c#L3546-L3567)). The procedure therefore keeps the missed-tuple check and its re-run rather than claiming prevention. A run that recorded which process held the pin would close this.
- **An escalation changes the state it proves.** `FREEZE` freezes every eligible row, and `INDEX_CLEANUP ON` removes entries an autovacuum worker at the defaults might have left ([vacuum.c#FREEZE-ages](../../../raw/postgres-17/src/backend/commands/vacuum.c#L385-L402), [autovacuum.c#unspecified-options](../../../raw/postgres-17/src/backend/postmaster/autovacuum.c#L2832-L2840)). Whether a fixture whose maintenance needed tier 1 still models an autovacuum-maintained table is the asker's call; the procedure only requires the departure to be declared.
- **The count `VACUUM` reports for a GIN index is now unreachable.** `ginvacuumcleanup` reports the heap tuple count as the index's tuple count and the code calls that bogus for a partial index in as many words ([ginvacuum.c#num_index_tuples-bogus](../../../raw/postgres-17/src/backend/access/gin/ginvacuum.c#L733-L739)). Because the maintenance step always analyzes after it vacuums, an `ANALYZE` estimate overwrites that value before any method reads it, so no fixture exercises a method against the number `VACUUM` alone would have left.
- **No run filed before this revision was produced under the maintenance step or the census.** The protocol now requires a maintained state and a recomputed analyze verdict, neither of which older runs performed, so their numbers describe fixtures this page no longer defines and re-running them is a task of its own.
