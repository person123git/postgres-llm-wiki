## Answer

### Summary

Row-Level Security (RLS) in PostgreSQL 14 is a **query-rewrite feature**, not a storage or access-method feature. Policies stored in the `pg_policy` catalog are loaded into each table's relcache entry, and during the rewrite phase `get_row_security_policies()` turns the policies that apply to the current command and role into two kinds of expressions: **security-barrier `USING` quals** (which silently filter which existing rows a query can see) and **`WITH CHECK` options** (which raise an error when a new or updated row would violate a policy) [rowsecurity.c overview](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L1-L34). A central helper, `check_enable_rls()`, decides per relation whether RLS applies, is bypassed, or should error [rls.c#check_enable_rls](../../../raw/postgres-14/src/backend/utils/misc/rls.c#L51-L133).

The performance picture follows directly from that design: RLS quals run inside the plan as per-row checks, they are pinned to run before less-trusted user quals unless they are *leakproof* (which can block index use), policy expressions may contain subqueries, a relation with RLS but no applicable policy gets an always-false **default-deny** qual, and cached plans must be re-planned whenever the role or the `row_security` setting changes. You do not need to restate a policy's conditions in the query for the planner to use them: policy `USING` quals are transferred into the table's `baserestrictinfo` at the lowest security level, so the planner already uses them for index scans and partition pruning, while a hand-written copy only lands at a higher security level [restrictinfo.c#restriction_is_securely_promotable](../../../raw/postgres-14/src/backend/optimizer/util/restrictinfo.c#L396-L409). Separately, wrapping an uncorrelated function call in a scalar sub-SELECT — `(SELECT auth.uid())` instead of `auth.uid()` — makes the planner turn it into an *InitPlan* that runs once per query and caches its result in a parameter, instead of re-invoking a per-row `STABLE` function filter [subselect.c#build_subplan](../../../raw/postgres-14/src/backend/optimizer/plan/subselect.c#L396-L410). For aggregate queries, there is no aggregate-specific RLS bypass switch: an `Agg` node aggregates tuples produced by its outer subplan, so the mitigation is to make the RLS-filtered input path cheaper, safer to index/prune, or intentionally pre-aggregated under a separate security design [nodeAgg.c#ExecAgg](../../../raw/postgres-14/src/backend/executor/nodeAgg.c#L2145-L2190) [pathnode.c#create_agg_path](../../../raw/postgres-14/src/backend/optimizer/util/pathnode.c#L3100-L3158). RLS policy filtering is not itself a MultiXact operation; the source-visible MultiXact implication is indirect, through referential-integrity (foreign-key) paths where RLS disables the bulk validation query and leaves per-row `FOR KEY SHARE` checks that can create or read MultiXacts on hot referenced rows [ri_triggers.c#RI_Initial_Check](../../../raw/postgres-14/src/backend/utils/adt/ri_triggers.c#L1358-L1368) [tablecmds.c#validateForeignKeyConstraint](../../../raw/postgres-14/src/backend/commands/tablecmds.c#L11367-L11415) [ri_triggers.c#RI_FKey_check](../../../raw/postgres-14/src/backend/utils/adt/ri_triggers.c#L356-L390).

The settings are: the `row_security` GUC (session-scoped), the `plan_cache_mode` GUC that controls generic-vs-custom plan selection for prepared statements, the per-table `relrowsecurity`/`relforcerowsecurity` flags set by `ALTER TABLE ... [ENABLE|DISABLE|FORCE|NO FORCE] ROW LEVEL SECURITY`, the per-role `BYPASSRLS` attribute, the per-policy options of `CREATE POLICY`/`ALTER POLICY` (permissive/restrictive, command, roles, `USING`, `WITH CHECK`), and two extension hooks.

### How RLS is implemented

#### Catalog storage and the policy data model

Each policy is a row in the `pg_policy` system catalog. The columns are the policy name (`polname`), the owning relation (`polrelid`), the command it applies to (`polcmd`, one of the `ACL_*_CHR` characters or `'*'` for `ALL`), whether it is permissive (`polpermissive`), the roles it applies to (`polroles`, where `0` means `PUBLIC`), the `USING` expression (`polqual`), and the `WITH CHECK` expression (`polwithcheck`) [pg_policy.h#FormData_pg_policy](../../../raw/postgres-14/src/include/catalog/pg_policy.h#L29-L44). A unique index on `(polrelid, polname)` enforces unique names per table and lets the relcache load policies in name order [pg_policy.h#indexes](../../../raw/postgres-14/src/include/catalog/pg_policy.h#L55-L58).

Whether a table participates in RLS at all is two booleans on `pg_class`: `relrowsecurity` (RLS enabled) and `relforcerowsecurity` (RLS also forced on the table owner), both defaulting to false [pg_class.h#relrowsecurity](../../../raw/postgres-14/src/include/catalog/pg_class.h#L107-L111). The per-role bypass right is `pg_authid.rolbypassrls` [pg_authid.h#rolbypassrls](../../../raw/postgres-14/src/include/catalog/pg_authid.h#L41).

In memory, a loaded policy is a `RowSecurityPolicy` (name, command char, role array, permissive flag, `qual`, `with_check_qual`, and a cached `hassublinks` flag), and a relation's full policy set is a `RowSecurityDesc` holding its own memory context plus a list of policies [rowsecurity.h#RowSecurityPolicy](../../../raw/postgres-14/src/include/rewrite/rowsecurity.h#L20-L35).

#### Building policies into the relcache

`RelationBuildRowSecurity()` populates `relation->rd_rsdesc` the first time a table with `relrowsecurity` is opened. It scans `pg_policy` by `polrelid` using the `(polrelid, polname)` index (so policies are visited in name order), deserializes the stored `polqual` and `polwithcheck` node trees with `stringToNode()`, caches whether either expression contains a sublink, and reparents the descriptor's memory context under `CacheMemoryContext` so it survives until a relcache flush [policy.c#RelationBuildRowSecurity](../../../raw/postgres-14/src/backend/commands/policy.c#L195-L325). Because policy expressions are stored as fully-parsed node trees, no re-parsing happens at query time — only copying.

#### The bypass decision: `check_enable_rls`

`check_enable_rls(relid, checkAsUser, noError)` is the single decision point. It returns one of three values from `enum CheckEnableRlsResult` — `RLS_NONE`, `RLS_NONE_ENV`, `RLS_ENABLED` [rls.h#CheckEnableRlsResult](../../../raw/postgres-14/src/include/utils/rls.h#L41-L46). The logic is:

1. Built-in relations (OID `< FirstNormalObjectId`) and tables without `relrowsecurity` return `RLS_NONE` — nothing to do, and the plan need not be invalidated for RLS reasons [rls.c#check_enable_rls](../../../raw/postgres-14/src/backend/utils/misc/rls.c#L61-L78).
2. Superusers and roles with `BYPASSRLS` return `RLS_NONE_ENV`: RLS is skipped now, but the answer depends on the environment (the user), so the plan must be re-checked if the role changes [rls.c#bypassrls](../../../raw/postgres-14/src/backend/utils/misc/rls.c#L80-L88).
3. The table owner returns `RLS_NONE_ENV` unless the table has `FORCE ROW LEVEL SECURITY` set *and* this is not a referential-integrity context (`InNoForceRLSOperation()`); RI checks intentionally still bypass forced RLS for the owner [rls.c#owner](../../../raw/postgres-14/src/backend/utils/misc/rls.c#L90-L118).
4. Otherwise RLS applies. As a special case, if the `row_security` GUC is off and `noError` is false, it raises a "query would be affected by row-level security policy" error instead of silently filtering [rls.c#row_security-off](../../../raw/postgres-14/src/backend/utils/misc/rls.c#L120-L132).

`has_bypassrls_privilege()` is what step 2 consults: superusers always return true, otherwise the result is `pg_authid.rolbypassrls` [aclchk.c#has_bypassrls_privilege](../../../raw/postgres-14/src/backend/catalog/aclchk.c#L5471-L5488). `InNoForceRLSOperation()` is true when the `SECURITY_NOFORCE_RLS` bit is set in the security context [miscinit.c#InNoForceRLSOperation](../../../raw/postgres-14/src/backend/utils/init/miscinit.c#L657-L661). The SQL function `row_security_active()` is just `check_enable_rls()` with `noError = true` [rls.c#row_security_active](../../../raw/postgres-14/src/backend/utils/misc/rls.c#L141-L167).

#### Rewrite-time expansion

RLS is applied during query rewrite, after view expansion, in `fireRIRrules()`. For each range-table entry that is a plain table or partitioned table, it calls `get_row_security_policies()` and then:

- prepends the returned security quals to the RTE's `securityQuals` list, so RLS conditions on the table take priority over barrier quals inherited from a security-barrier view [rewriteHandler.c#fireRIRrules-RLS](../../../raw/postgres-14/src/backend/rewrite/rewriteHandler.c#L2256-L2349);
- concatenates the returned `WITH CHECK` options into the query's `withCheckOptions`;
- if the new quals contain sublinks, locks the referenced relations and fires RIR (view) rules on them, with recursion detection that raises "infinite recursion detected in policy for relation" [rewriteHandler.c#policy-sublinks](../../../raw/postgres-14/src/backend/rewrite/rewriteHandler.c#L2285-L2336);
- marks the query `hasRowSecurity` (and `hasSubLinks` if applicable), which later drives plan-cache invalidation [rewriteHandler.c#hasRowSecurity](../../../raw/postgres-14/src/backend/rewrite/rewriteHandler.c#L2351-L2358).

`get_row_security_policies()` is the core of the feature [rowsecurity.h#prototype](../../../raw/postgres-14/src/include/rewrite/rowsecurity.h#L44-L47). It only acts on `RELKIND_RELATION` and `RELKIND_PARTITIONED_TABLE` RTEs [rowsecurity.c#relkind](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L125-L128), resolves the effective user (`rte->checkAsUser` for views, else the current user) [rowsecurity.c#user_id](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L130-L134), and short-circuits on the `check_enable_rls()` result. On `RLS_NONE_ENV` it adds no quals but still sets `hasRowSecurity = true` to force re-planning if the environment changes [rowsecurity.c#RLS_NONE_ENV](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L136-L155).

The command type drives which policies are selected. If the RTE is the result relation it uses the query's command type, otherwise it treats the RTE as a `SELECT` source (so `UPDATE t1 ... FROM t2` applies t1's UPDATE policies and t2's SELECT policies) [rowsecurity.c#commandType](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L157-L169). It then layers quals for the combinations that need them:

- `SELECT ... FOR [KEY] UPDATE/SHARE` (the SELECT requires `ACL_UPDATE`) first adds the UPDATE `USING` quals, so a locking select cannot lock rows the user couldn't update [rowsecurity.c#select-for-update](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L190-L213).
- `SELECT`/`UPDATE`/`DELETE` add the command's own `USING` quals as security quals [rowsecurity.c#using-quals](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L215-L232).
- `UPDATE`/`DELETE` that also need `ACL_SELECT` (a `RETURNING` clause or a `WHERE` referencing the table) additionally add the SELECT `USING` quals [rowsecurity.c#update-needs-select](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L234-L258).
- `INSERT`/`UPDATE` add `WITH CHECK` options for new rows; if `RETURNING` requires SELECT, SELECT policies are added as `WITH CHECK` options (not security quals) so a violation errors rather than silently dropping rows [rowsecurity.c#with-check](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L260-L303).
- `INSERT ... ON CONFLICT DO UPDATE` adds extra conflict checks: the UPDATE `USING` clauses as `WCO_RLS_CONFLICT_CHECK`, plus the UPDATE `WITH CHECK` clauses [rowsecurity.c#on-conflict](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L305-L380).

Finally it copies `checkAsUser` into the new quals (for sub-selects against other relations) and sets `hasRowSecurity = true` [rowsecurity.c#finish](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L385-L397).

#### Combining policies: permissive, restrictive, and default-deny

`get_policies_for_relation()` walks the relcache policy list and keeps the policies whose `polcmd` matches the command (or is `'*'`) and that apply to the user's role, splitting them into permissive and restrictive lists. Restrictive policies are sorted by name so their checks run in a defined order. Extension-hook policies are appended afterward [rowsecurity.c#get_policies_for_relation](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L407-L513). Sorting uses `strcmp` on the policy name [rowsecurity.c#row_security_policy_cmp](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L523-L545).

`add_security_quals()` builds the read-side filter: all **permissive** `USING` quals are OR'd into one expression, all **restrictive** `USING` quals are AND'd on top, and the combined expression is appended to `securityQuals`. Crucially, **if there is no permissive policy, it appends a single `false` constant** — the default-deny rule that makes a row-secured table with no matching policy return nothing [rowsecurity.c#add_security_quals](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L558-L637).

`add_with_check_options()` builds the write-side check the same way (permissive OR, restrictive AND), using each policy's `WITH CHECK` expression or, if absent, its `USING` expression (the `QUAL_FOR_WCO` macro). Each restrictive check becomes its own named `WithCheckOption` so violations can name the offending policy; with no permissive policy it emits a single `false` check, denying all writes [rowsecurity.c#add_with_check_options](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L654-L769).

#### Command and role matching

A policy applies to the current role when its role list is `PUBLIC` (`polroles[0] == ACL_ID_PUBLIC`) or the user is a member of one of the listed roles (`has_privs_of_role`), so normal role inheritance applies to policies [rowsecurity.c#check_role_for_policy](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L775-L792).

#### Planner: the security-barrier qual mechanism

RLS quals are placed in the RTE's `securityQuals`, the same machinery used for security-barrier views, so the planner enforces an evaluation-order rule that prevents leaking rows through cleverly-chosen user functions. Each `RestrictInfo` carries a `security_level`; a clause may not be evaluated before a clause of lower `security_level` **unless it is leakproof** [pathnodes.h#security_level](../../../raw/postgres-14/src/include/nodes/pathnodes.h#L2003-L2010). The planner computes `qual_security_level` as the maximum `securityQuals` list length across RTEs [planner.c#qual_security_level](../../../raw/postgres-14/src/backend/optimizer/plan/planner.c#L738-L747) [pathnodes.h#qual_security_level](../../../raw/postgres-14/src/include/nodes/pathnodes.h#L343-L344), and `process_security_barrier_quals()` copies each `securityQuals` sublist into the relation's `baserestrictinfo` at successively higher security levels [initsplan.c#process_security_barrier_quals](../../../raw/postgres-14/src/backend/optimizer/plan/initsplan.c#L1083-L1127).

At plan-build time, `order_qual_clauses()` sorts the quals at each node: lower security level first, and within a level by estimated cost. A leakproof clause that is also cheap (under `10 * cpu_operator_cost`) is treated as security level 0 so it can be evaluated early; everything else keeps its real level [createplan.c#order_qual_clauses](../../../raw/postgres-14/src/backend/optimizer/plan/createplan.c#L5191-L5300).

#### Executor: enforcing `WITH CHECK`

`USING` quals become ordinary scan filters (enforced as part of the plan), so they silently exclude rows. `WITH CHECK` options are enforced separately by `ExecWithCheckOptions()`, which evaluates each option of the requested kind against the new tuple and raises an error if it returns NULL or false. For RLS kinds it reports "new row violates row-level security policy [\"name\"] for table" and, unlike view checks, deliberately does **not** include the failing row's data, because the user might not be allowed to see that row [execMain.c#ExecWithCheckOptions](../../../raw/postgres-14/src/backend/executor/execMain.c#L1977-L2086). Permission checks (`ExecCheckRTPerms`) are explicitly separate from RLS; callers that return rows must also consult `check_enable_rls()` [execMain.c#ExecCheckRTPerms](../../../raw/postgres-14/src/backend/executor/execMain.c#L548-L560).

#### Plan-cache invalidation

Because the policies that apply depend on the current role and the `row_security` GUC, cached plans for RLS queries are environment-sensitive [plancache.c#overview](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L16-L20). The rewriter's `hasRowSecurity` flag is harvested into the plan source's `dependsOnRLS` field via `extract_query_dependencies()` (which reuses the `dependsOnRole` slot as a collector) [setrefs.c#extract_query_dependencies](../../../raw/postgres-14/src/backend/optimizer/plan/setrefs.c#L3142-L3167) [setrefs.c#hasRowSecurity](../../../raw/postgres-14/src/backend/optimizer/plan/setrefs.c#L3219-L3221), alongside the role and `row_security` value captured at rewrite time [plancache.c#capture](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L396-L403). `RevalidateCachedQuery()` then forces a re-analysis/re-plan if `dependsOnRLS` is set and either the user id or the `row_security` setting has changed [plancache.c#RevalidateCachedQuery](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L600-L607). The built plan is likewise marked role-dependent [plancache.c#BuildCachedPlan](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L982-L994), and the fast "simple validity" revalidation path is disabled for RLS-dependent plans [plancache.c#simple-validity](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L1343-L1345).

#### Inheritance and partitioning

RLS works on partitioned and inherited tables, but child tables do **not** contribute their own policies. When the planner expands an inheritance/partition child RTE it sets the child's `securityQuals` to empty on purpose, so only the parent's RLS conditions apply; the parent's quals are propagated to children with the other base-restriction clauses [inherit.c#expand_single_inheritance_child](../../../raw/postgres-14/src/backend/optimizer/util/inherit.c#L457-L487). The documentation states the same rule: the parent's row-security policies are applied to rows from child tables, and a child's own policies (if any) are ignored during an inherited query [ddl.sgml#inheritance](../../../raw/postgres-14/doc/src/sgml/ddl.sgml#L3458-L3460).

#### Feature boundaries (COPY, CTAS, RI, and error-message leakage)

Several subsystems special-case RLS:

- **COPY**: if RLS is enabled, `COPY TO` is internally rewritten as `COPY (SELECT ...)` so the normal query path applies the policies, while `COPY FROM` is rejected with "COPY FROM not supported with row-level security" (use `INSERT`) [copy.c#RLS](../../../raw/postgres-14/src/backend/commands/copy.c#L201-L227).
- **CREATE TABLE AS / SELECT INTO**: creating into a relation that would have RLS enabled errors with "policies not yet implemented for this command" [createas.c#RLS](../../../raw/postgres-14/src/backend/commands/createas.c#L535-L546).
- **Referential integrity**: the bulk foreign-key validation query is skipped (forcing slower per-row checks) when either table has RLS and the current role is neither the owner nor `BYPASSRLS` [ri_triggers.c#RI_Initial_Check](../../../raw/postgres-14/src/backend/utils/adt/ri_triggers.c#L1358-L1368). RI error details are also suppressed when RLS is enabled, to avoid leaking key values [ri_triggers.c#error-detail](../../../raw/postgres-14/src/backend/utils/adt/ri_triggers.c#L2444-L2455).
- **Error-message leakage**: row and partition-key value descriptions in error messages return NULL when RLS is active, so violation messages cannot leak protected data [execMain.c#ExecBuildSlotValueDescription](../../../raw/postgres-14/src/backend/executor/execMain.c#L2142-L2148) [execPartition.c#partition-key-desc](../../../raw/postgres-14/src/backend/executor/execPartition.c#L1364-L1365).

#### Extension hooks

Two global hooks let an extension inject policies at rewrite time: `row_security_policy_hook_permissive` (combined with OR, like other permissive policies) and `row_security_policy_hook_restrictive` (combined with AND, name-sorted, always checked before permissive hook policies) [rowsecurity.h#hooks](../../../raw/postgres-14/src/include/rewrite/rowsecurity.h#L37-L42) [rowsecurity.c#hook-decls](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L87-L97) [rowsecurity.c#hook-application](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L473-L512).

### Scalability and performance issues

RLS adds correctness machinery to the plan, so its costs are paid per query and per row. The main concerns, all grounded in the implementation above:

1. **Per-row evaluation.** `USING` expressions become scan-level filters and `WITH CHECK` expressions run for every inserted/updated row in `ExecWithCheckOptions()` [execMain.c#ExecWithCheckOptions](../../../raw/postgres-14/src/backend/executor/execMain.c#L1977-L2086). A policy expression that calls a function or sub-select runs that work once per candidate row.

2. **Leakproof ordering can defeat indexes.** A non-leakproof qual from the user's own `WHERE` clause cannot be evaluated before the RLS qual; only leakproof (and cheap) clauses are allowed to move ahead [pathnodes.h#security_level](../../../raw/postgres-14/src/include/nodes/pathnodes.h#L2003-L2010) [createplan.c#order_qual_clauses](../../../raw/postgres-14/src/backend/optimizer/plan/createplan.c#L5191-L5300). The documentation spells out the consequence: the policy expression is evaluated before user conditions/functions, except for leakproof functions [ddl.sgml#leakproof](../../../raw/postgres-14/doc/src/sgml/ddl.sgml#L2263-L2277). This is the classic RLS performance trap — a selective user predicate using a non-leakproof operator may not be pushed to an index ahead of the policy filter.

3. **Subqueries in policies.** A policy whose `USING`/`WITH CHECK` contains a sublink sets `hassublinks`, requiring the rewriter to lock and recursively process those subqueries [policy.c#hassublinks](../../../raw/postgres-14/src/backend/commands/policy.c#L301-L303) [rewriteHandler.c#policy-sublinks](../../../raw/postgres-14/src/backend/rewrite/rewriteHandler.c#L2285-L2336), and the subquery executes as part of every row's check. Policies that look up membership tables per row are a common scalability bottleneck of this kind.

4. **Many policies enlarge the qual tree.** Every applicable permissive policy is copied and OR'd, and every restrictive policy is copied and AND'd, into the per-RTE qual [rowsecurity.c#add_security_quals](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L558-L637). More policies mean larger expressions to evaluate per row and sort per node, and restrictive policies are name-sorted on each relcache build [rowsecurity.c#get_policies_for_relation](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L468-L471).

5. **Plan-cache churn on role/GUC change.** Prepared statements and PL/pgSQL plans for RLS queries are re-planned whenever the role or `row_security` value differs from when they were built, and they cannot use the cheap revalidation fast path [plancache.c#RevalidateCachedQuery](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L600-L607) [plancache.c#simple-validity](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L1338-L1348). Workloads that switch roles frequently (e.g. `SET ROLE` per request on a pooled connection) pay repeated planning costs. The mechanics, the cases where caching does not help, and the no-cache cost are detailed in [RLS and the plan cache](#rls-and-the-plan-cache) below.

6. **Combined `USING` sets for locking and `RETURNING`.** `SELECT ... FOR UPDATE`, and `UPDATE`/`DELETE` with `RETURNING` or table-referencing `WHERE`, layer additional `USING`/`WITH CHECK` policy sets onto the query, so these statements carry more checks than a plain read [rowsecurity.c#select-for-update](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L190-L213) [rowsecurity.c#update-needs-select](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L234-L258).

7. **Foreign-key checks lose the bulk path.** With RLS on a referenced or referencing table (for a non-owner, non-`BYPASSRLS` role), the initial bulk FK validation query is skipped, leaving slower per-row RI verification [ri_triggers.c#RI_Initial_Check](../../../raw/postgres-14/src/backend/utils/adt/ri_triggers.c#L1358-L1368) [tablecmds.c#validateForeignKeyConstraint](../../../raw/postgres-14/src/backend/commands/tablecmds.c#L11367-L11415). Those per-row checks use `FOR KEY SHARE` on the referenced row, so hot referenced rows can hit the same MultiXact creation and SLRU-read costs described in [RLS and MultiXact](#rls-and-multixact) [ri_triggers.c#RI_FKey_check](../../../raw/postgres-14/src/backend/utils/adt/ri_triggers.c#L356-L390).

8. **Default-deny is cheap; missing policies are silent.** A row-secured table with no matching permissive policy gets a single `false` constant, so it is cheap but returns no rows — easy to mistake for a data problem [rowsecurity.c#default-deny](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L626-L636).

9. **Partition fan-out.** The parent's policy quals are propagated to every scanned child partition [inherit.c#expand_single_inheritance_child](../../../raw/postgres-14/src/backend/optimizer/util/inherit.c#L457-L487), so the per-row cost is multiplied across all partitions touched by a query.

### Do RLS filter conditions need to be in the query?

**No. In PostgreSQL 14 you do not need to repeat a policy's filter conditions in your query's `WHERE` clause for the planner to use them, and repeating them does not help query planning.** A policy's `USING` expression is turned into a security-barrier qual during rewrite and *prepended* to the range-table entry's `securityQuals`, ahead of any security-barrier-view quals [rewriteHandler.c#fireRIRrules-RLS](../../../raw/postgres-14/src/backend/rewrite/rewriteHandler.c#L2338-L2349). Before planning, `process_security_barrier_quals()` copies those quals into the table's `baserestrictinfo`, giving the first security sublist `security_level` 0 and each successive sublist a higher level [initsplan.c#process_security_barrier_quals](../../../raw/postgres-14/src/backend/optimizer/plan/initsplan.c#L1083-L1127). From that point the policy predicate is an ordinary base restriction — the very `baserestrictinfo` list the planner uses to build index paths and partition-pruning steps.

#### The planner already uses the policy qual

Two planner paths consume the RLS qual directly, with no help from the query text:

- **Index scans.** `match_clause_to_index()` uses a base-restriction clause as an index qualifier unless `restriction_is_securely_promotable()` rejects it [indxpath.c#match_clause_to_index](../../../raw/postgres-14/src/backend/optimizer/path/indxpath.c#L2188-L2193). That helper returns true when the clause's `security_level` is `<=` the relation's `baserestrict_min_security`, *or* the clause is leakproof [restrictinfo.c#restriction_is_securely_promotable](../../../raw/postgres-14/src/backend/optimizer/util/restrictinfo.c#L396-L409). `baserestrict_min_security` is the minimum level over the table's base restrictions [initsplan.c#baserestrict_min_security](../../../raw/postgres-14/src/backend/optimizer/plan/initsplan.c#L2194-L2198), and the RLS filter's first sublist is at level 0, so that sublist is always securely promotable. In the common **permissive-only** case the whole combined RLS visibility filter *is* that single level-0 clause [rowsecurity.c#add_security_quals](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L558-L637), so the planner can match the policy predicate to an index by itself.
- **Partition pruning.** Plan-time pruning takes its prune quals straight from `rel->baserestrictinfo` [createplan.c#partition-pruneinfo](../../../raw/postgres-14/src/backend/optimizer/plan/createplan.c#L1314-L1340), which already contains the transferred RLS qual. A policy predicate on the partition key can therefore prune partitions without being restated.

#### Restating the predicate is redundant — and weaker

Quals that come from the query text are assigned the *maximum* security level — `root->qual_security_level`, the largest `securityQuals` list length [planner.c#qual_security_level](../../../raw/postgres-14/src/backend/optimizer/plan/planner.c#L738-L747) [initsplan.c#query-quals](../../../raw/postgres-14/src/backend/optimizer/plan/initsplan.c#L817-L838). So a hand-written copy of the policy predicate lands *above* the RLS qual and is usable for early/index evaluation only if it is leakproof [restrictinfo.c#restriction_is_securely_promotable](../../../raw/postgres-14/src/backend/optimizer/util/restrictinfo.c#L396-L409). It gives the planner nothing the level-0 policy qual did not already provide, and it adds a second clause to evaluate per row.

#### The real constraint is your *other* filters

The design rule is that a lower-`security_level` qual must be evaluated before a higher one unless the higher one is leakproof [optimizer README#security-level-rules](../../../raw/postgres-14/src/backend/optimizer/README#L910-L969) [pathnodes.h#security_level](../../../raw/postgres-14/src/include/nodes/pathnodes.h#L2003-L2010). Your own selective `WHERE` predicate therefore cannot be pushed to an index ahead of the RLS filter unless it is leakproof, and `order_qual_clauses()` enforces the same ordering at execution time (only a cheap leakproof clause is treated as level 0) [createplan.c#order_qual_clauses](../../../raw/postgres-14/src/backend/optimizer/plan/createplan.c#L5191-L5300). This is the leakproof-ordering trap from [Scalability and performance issues](#scalability-and-performance-issues) (item 2), seen from the query author's side.

So the levers that actually help planning are not about *where you write* the condition:

1. **Do not duplicate policy predicates in the query.** The planner already sees them as level-0 base restrictions; a copy only adds a higher-security-level clause and no new index/pruning ability.
2. **Make the policy predicate indexable.** Because it becomes `baserestrictinfo`, an index (or partial index, or a matching partition key) on the columns the policy tests is what lets the planner turn the RLS filter into an index scan or a partition prune — the same mechanism described in the [RLS and aggregation](#rls-and-aggregation) mitigations.
3. **Keep your own selective filters leakproof where possible.** That is the only way a query-text predicate escapes the security-level delay and can be used early (for example, as an index qual) alongside the RLS filter.

Two boundaries. First, when a table also has restrictive policies, or a statement layers extra `USING` sets (locking `SELECT`s, or `UPDATE`/`DELETE` with `RETURNING`), RLS contributes more than one security sublist, and only the level-0 sublist is unconditionally promotable; the higher sublists follow the same leakproof rule [rowsecurity.c#add_security_quals](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L558-L637) [rowsecurity.c#select-for-update](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L190-L213). Second, this is all about read-side `USING` quals used for planning; `WITH CHECK` options are enforced per row by `ExecWithCheckOptions()` [execMain.c#ExecWithCheckOptions](../../../raw/postgres-14/src/backend/executor/execMain.c#L1977-L2086), not through indexes or pruning, so restating them in a query has no planning effect either.

### Wrapping a function in a subquery to evaluate it once

**Yes, when the unwrapped call would otherwise be applied as a per-row filter. Wrapping an uncorrelated function call in a scalar sub-SELECT — writing `(SELECT auth.uid()) = user_id` instead of `auth.uid() = user_id` — makes PostgreSQL 14 evaluate that subquery once per query execution and reuse the result.** The planner turns an uncorrelated `(SELECT ...)` into an *InitPlan* whose single result is stored in an executor parameter (`PARAM_EXEC`) and reused for every row. A bare `STABLE` function left in a filter qual is re-invoked for each row the filter is applied to, although an index-qualifiable comparison may already evaluate the same function once per scan as a runtime key. This is general planner/executor behavior, and it applies to the function call whether you write it inside a policy's `USING`/`WITH CHECK` expression or in an ordinary query, because RLS policy quals are planned like any other qual (see [How RLS is implemented](#how-rls-is-implemented) and [Do RLS filter conditions need to be in the query?](#do-rls-filter-conditions-need-to-be-in-the-query)).

A note on the functions: `auth.uid()` and `auth.jwt()` are external helper functions, not part of core PostgreSQL 14, so the pinned `raw/postgres-14/` checkout cannot verify their definitions or volatility. The PostgreSQL mechanism described here is source-verified for any uncorrelated scalar sub-SELECT. If a JWT helper is implemented as a claim reader over a session setting and declared `STABLE`, it has the same volatility class as core `current_setting()` (`provolatile => 's'`) [pg_proc.dat#current_setting](../../../raw/postgres-14/src/include/catalog/pg_proc.dat#L6009-L6015). If a helper is declared `VOLATILE`, the uncorrelated sub-SELECT still follows the InitPlan rule below, but that intentionally changes the number of calls compared with a bare per-row filter; verify that once-per-execution semantics are correct before using the wrapper.

#### The mechanism: an uncorrelated sub-SELECT becomes an InitPlan

`(SELECT auth.uid())` is a scalar sub-SELECT that references no column of the outer row — an *uncorrelated* `EXPR_SUBLINK`. During planning, `SS_process_sublinks()` hands each sublink to `make_subplan()`, which calls `build_subplan()` [subselect.c#make_subplan](../../../raw/postgres-14/src/backend/optimizer/plan/subselect.c#L238-L241). For an `EXPR_SUBLINK` with no correlation parameters (`parParam == NIL`), `build_subplan()` allocates a `PARAM_EXEC` parameter, records it in the subplan's `setParam`, marks the subplan `isInitPlan = true`, and returns that parameter in place of the subquery [subselect.c#build_subplan](../../../raw/postgres-14/src/backend/optimizer/plan/subselect.c#L396-L410). The comment states the rule directly: "Un-correlated ... plans of EXISTS, EXPR, ARRAY, ... types can be used as initPlans. For EXISTS, EXPR, or ARRAY, we return a Param referring to the result of evaluating the initPlan" [subselect.c#initplans](../../../raw/postgres-14/src/backend/optimizer/plan/subselect.c#L375-L385). The subplan is then attached to the query level's InitPlan list [subselect.c#init_plans](../../../raw/postgres-14/src/backend/optimizer/plan/subselect.c#L548-L549), and a nearby comment notes that an initplan "won't get re-run without parameter changes anyway" [subselect.c#initplan-not-rerun](../../../raw/postgres-14/src/backend/optimizer/plan/subselect.c#L551-L556). So `user_id = (SELECT auth.uid())` is planned as `user_id = $0`, where `$0` is produced by a once-run InitPlan.

At execution time the InitPlan runs lazily, exactly once, and its result is cached in the parameter slot. `ExecEvalParamExec()` runs the InitPlan only while the parameter's `execPlan` field is still set, and `ExecSetParamPlan()` clears that field after evaluating, so every later reference reads the stored `value` instead of re-running the subplan [execExprInterp.c#ExecEvalParamExec](../../../raw/postgres-14/src/backend/executor/execExprInterp.c#L2427-L2440) [nodeSubplan.c#ExecSetParamPlan](../../../raw/postgres-14/src/backend/executor/nodeSubplan.c#L1051-L1073). Because this sublink-to-InitPlan conversion runs inside `preprocess_expression()`, and the planner sends every RLS security qual and `WITH CHECK` option through that same `preprocess_expression()` / `SS_process_sublinks()` path, the InitPlan is created even when the sub-SELECT sits inside a policy expression — security quals through the per-`securityQuals`-element loop and `WITH CHECK` options through their own preprocessing loop [planner.c#securityQuals-preprocess](../../../raw/postgres-14/src/backend/optimizer/plan/planner.c#L931-L941) [planner.c#withCheckOptions-preprocess](../../../raw/postgres-14/src/backend/optimizer/plan/planner.c#L818-L828) [planner.c#preprocess_expression](../../../raw/postgres-14/src/backend/optimizer/plan/planner.c#L1154-L1156).

#### Without the wrapper: a bare `STABLE` function is re-called per row

Left unwrapped, a `STABLE` helper such as `auth.uid()` stays a `FuncExpr` in the qual. `STABLE` and `VOLATILE` functions are not constant-folded during planning — only `IMMUTABLE` functions are pre-evaluated: "Functions that are not marked 'immutable' in pg_proc will not be pre-evaluated here" [clauses.c#eval_const_expressions](../../../raw/postgres-14/src/backend/optimizer/util/clauses.c#L2135-L2139), and the folding checks gate on `PROVOLATILE_IMMUTABLE` [clauses.c#contain_mutable_functions_checker](../../../raw/postgres-14/src/backend/optimizer/util/clauses.c#L374-L378) [clauses.c#ece_function_is_safe](../../../raw/postgres-14/src/backend/optimizer/util/clauses.c#L3577-L3591). So the call survives into the executable qual.

When that qual is applied as a scan filter, it runs for every tuple: the scan loop places each fetched tuple in the expression context and calls `ExecQual()` on it [execScan.c#ExecScan](../../../raw/postgres-14/src/backend/executor/execScan.c#L202-L234), and evaluating the qual invokes the function through the `EEOP_FUNCEXPR` step each time, with no cross-row memoization [execExprInterp.c#EEOP_FUNCEXPR](../../../raw/postgres-14/src/backend/executor/execExprInterp.c#L727-L735). For an RLS policy predicate applied as a per-row security filter, that is one `auth.uid()` call per candidate row — exactly the per-row cost listed in [Scalability and performance issues](#scalability-and-performance-issues) (item 1).

#### Why it matters for RLS policies specifically

RLS `USING` expressions become scan-level security quals during rewrite and are transferred into the table's `baserestrictinfo` (see [Do RLS filter conditions need to be in the query?](#do-rls-filter-conditions-need-to-be-in-the-query)). If the policy predicate is served by an index — for example a tenant key with a matching index — the comparison can drive an index scan, and the non-indexed side is computed once per scan as a *runtime key*, not per row: `ExecReScanIndexScan()` recomputes all runtime keys once and sets `iss_RuntimeKeysReady`, after which the AM reuses them [nodeIndexscan.c#ExecReScanIndexScan](../../../raw/postgres-14/src/backend/executor/nodeIndexscan.c#L554-L572). In that case a bare `STABLE` `auth.uid()` is already evaluated about once per scan, so the wrapper's marginal benefit is small.

The clear win is when the policy predicate is applied as a **filter** rather than an index condition — no usable index, a sequential scan, a bitmap recheck, or a predicate the planner cannot convert into an index qual. There the bare function runs once per candidate row, and the `(SELECT ...)` form collapses it to a single InitPlan evaluation. Wrapping also turns the compared value into a plain parameter (`user_id = $0`), which the planner can still match to an index on `user_id` — the level-0 policy qual is securely promotable, as covered in [Do RLS filter conditions need to be in the query?](#do-rls-filter-conditions-need-to-be-in-the-query) — so the wrapper does not cost you index usability.

#### Caveats and limits

- **It caches once per execution, not a general memoization.** The value is captured the first time the parameter is read and reused for the rest of that execution [nodeSubplan.c#ExecSetParamPlan](../../../raw/postgres-14/src/backend/executor/nodeSubplan.c#L1051-L1073). It is not a cross-statement or cross-transaction cache; each new execution re-runs the InitPlan once.
- **Only *uncorrelated* sub-SELECTs become InitPlans.** `(SELECT auth.uid())` references no outer column, so it qualifies. A *correlated* sub-SELECT (one that references the current row) keeps `parParam != NIL` and is built as a per-invocation `SubPlan`, not an InitPlan [subselect.c#build_subplan-SubPlan](../../../raw/postgres-14/src/backend/optimizer/plan/subselect.c#L487-L539) — it would run per row, defeating the purpose.
- **Wrapping introduces a sublink into the policy.** A policy whose `USING`/`WITH CHECK` contains a sub-SELECT gets `hassublinks` set, which adds the rewrite-time sublink handling from [Scalability and performance issues](#scalability-and-performance-issues) (item 3) [policy.c#hassublinks](../../../raw/postgres-14/src/backend/commands/policy.c#L301-L303) [rewriteHandler.c#policy-sublinks](../../../raw/postgres-14/src/backend/rewrite/rewriteHandler.c#L2285-L2336). Because `(SELECT auth.uid())` references no table in the PostgreSQL query tree, there is no referenced relation for that lock/RIR-rule walker to process; the meaningful effect is the plan-time InitPlan conversion, not extra rewrite work.
- **This is orthogonal to restating the predicate in the query.** [Do RLS filter conditions need to be in the query?](#do-rls-filter-conditions-need-to-be-in-the-query) is about *where* the condition lives; this is about *how the function call is written*. You still do not need to restate the policy in your query, and when you do reference such a function in your own query predicates, the same `(SELECT ...)` trick applies there.

### RLS and aggregation

Yes, RLS can slow aggregation statements, but not because PostgreSQL 14 has a separate RLS-aware aggregate executor. RLS adds `USING` expressions as scan-level security quals during rewrite [rowsecurity.c overview](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L1-L34), the planner transfers those `securityQuals` into the base relation's `baserestrictinfo` [initsplan.c#process_security_barrier_quals](../../../raw/postgres-14/src/backend/optimizer/plan/initsplan.c#L1070-L1127), and aggregate paths sit above a chosen input subpath [pathnode.c#create_agg_path](../../../raw/postgres-14/src/backend/optimizer/util/pathnode.c#L3100-L3158). At execution time, `ExecAgg` receives tuples from its outer subplan and advances aggregate state for each input tuple [nodeAgg.c#ExecAgg](../../../raw/postgres-14/src/backend/executor/nodeAgg.c#L2145-L2190) [nodeAgg.c#agg-input-loop](../../../raw/postgres-14/src/backend/executor/nodeAgg.c#L2360-L2465). So `COUNT(*)`, `SUM(...)`, and `GROUP BY` aggregate only the rows that survive RLS, and they pay the cost of reaching that filtered input.

There is no single PostgreSQL 14 setting that makes RLS cheap for aggregates while preserving the same row visibility. Practical mitigations are:

1. **Make the policy predicate cheap and indexable.** Because RLS quals become `baserestrictinfo`, ordinary index path generation can match them to indexes and bitmap paths [indxpath.c#create_index_paths](../../../raw/postgres-14/src/backend/optimizer/path/indxpath.c#L198-L336). For tenant-style policies, put the tenant/security key in a plain column expression that can use a normal or partial index, and avoid wrapping the indexed column in per-row functions or policy subqueries unless the security model requires it. Partial-index predicates are also proved against the relation's `baserestrictinfo`, so an RLS predicate can help or hurt partial-index usability depending on whether the predicate implication is simple enough for the planner [indxpath.c#check_index_predicates](../../../raw/postgres-14/src/backend/optimizer/path/indxpath.c#L3306-L3452).
2. **Keep selective filters in leakproof/indexable form.** Security-level rules prevent leaky user quals from being used before RLS quals, including as early index quals, unless the clause is leakproof or at a safe security level [optimizer README#security-level-constraints](../../../raw/postgres-14/src/backend/optimizer/README#L899-L978). `order_qual_clauses()` applies the same rule at execution order and only treats cheap leakproof clauses as movable to security level 0 [createplan.c#order_qual_clauses](../../../raw/postgres-14/src/backend/optimizer/plan/createplan.c#L5191-L5300). This is why `WHERE` predicates that are selective in a non-RLS query can stop helping an aggregate query once RLS is active.
3. **Use partitioning when the security key is also the pruning key.** Partition pruning gathers prune quals from `baserestrictinfo`, so an RLS tenant predicate that is visible as a base restriction can remove irrelevant partitions before the aggregate consumes rows [createplan.c#partition-pruneinfo](../../../raw/postgres-14/src/backend/optimizer/plan/createplan.c#L1312-L1342). For partitioned aggregate workloads, `enable_partitionwise_aggregate` lets the planner consider partitionwise aggregation when grouping sets are not present; it is a `PGC_USERSET` GUC, so it is session/transaction scoped and needs no restart or reload [guc.c#enable_partitionwise_aggregate](../../../raw/postgres-14/src/backend/utils/misc/guc.c#L1108-L1117) [planner.c#partitionwise-aggregate](../../../raw/postgres-14/src/backend/optimizer/plan/planner.c#L3378-L3408).
4. **Reduce repeated planning, but do not expect this to remove per-row checks.** Prepared statements and PL/pgSQL can reuse RLS-rewritten trees and generic plans when the role and `row_security` value stay fixed, as described in [RLS and the plan cache](#rls-and-the-plan-cache). This mitigates repeated planning for repeated aggregate statements; it does not remove executor-time policy evaluation.
5. **Pre-aggregate only when the result has its own security boundary.** If users should see aggregates over rows they cannot individually see, that is not the same query under RLS. Use a maintained summary table or a trusted reporting API with its own checks. PostgreSQL's own bypass rules are explicit: superusers and `BYPASSRLS` roles bypass RLS, table owners usually bypass it unless `FORCE ROW LEVEL SECURITY` is set, and `SECURITY DEFINER` functions run under the function owner's user id [rls.c#check_enable_rls](../../../raw/postgres-14/src/backend/utils/misc/rls.c#L80-L118) [fmgr.c#fmgr_security_definer](../../../raw/postgres-14/src/backend/utils/fmgr/fmgr.c#L656-L772). That can be a valid reporting design, but it changes the security boundary and must not be treated as a transparent performance knob.
6. **Do not use `row_security = off` as an optimization for subject users.** `row_security` is `PGC_USERSET` (session/transaction scoped, no restart or reload) [guc.c#row_security](../../../raw/postgres-14/src/backend/utils/misc/guc.c#L1722-L1730), but when a non-bypass user would be affected by policy filtering, `check_enable_rls()` raises an error instead of silently bypassing RLS [rls.c#row_security-off](../../../raw/postgres-14/src/backend/utils/misc/rls.c#L120-L132).

One boundary is worth calling out: policy expressions themselves cannot contain aggregate calls. The parser rejects aggregate and grouping operations in policy expressions [parse_agg.c#EXPR_KIND_POLICY](../../../raw/postgres-14/src/backend/parser/parse_agg.c#L398-L407), and the v14 `rowsecurity` regression test covers `CREATE POLICY p ON t USING (max(c))` failing with "aggregate functions are not allowed in policy expressions" [rowsecurity.sql#policy-aggregate-rejected](../../../raw/postgres-14/src/test/regress/sql/rowsecurity.sql#L1496-L1503) [rowsecurity.out#policy-aggregate-rejected](../../../raw/postgres-14/src/test/regress/expected/rowsecurity.out#L3568-L3578). So "move the aggregation into the policy" is not an available mitigation.

### RLS and MultiXact

RLS does **not** make ordinary policy filtering a MultiXact operation. The RLS path attaches `USING` expressions to `securityQuals` and `WITH CHECK` expressions to `WithCheckOption` lists during rewrite [rowsecurity.c overview](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L1-L34) [rewriteHandler.c#fireRIRrules-RLS](../../../raw/postgres-14/src/backend/rewrite/rewriteHandler.c#L2256-L2349). MultiXacts are row-lock storage: a tuple's `xmax` can hold a `MultiXactId` whose members are `(TransactionId, MultiXactStatus)` pairs, including `ForKeyShare`, `ForShare`, `ForNoKeyUpdate`, and `ForUpdate` row-lock modes [multixact.h#MultiXactStatus](../../../raw/postgres-14/src/include/access/multixact.h#L37-L64).

The RLS-related MultiXact implication is indirect and appears in foreign-key work:

1. `validateForeignKeyConstraint()` first tries `RI_Initial_Check()`, a single bulk validation query. If that returns false, it scans every referencing-table row and calls the insert-check trigger function `RI_FKey_check_ins()` for each row [tablecmds.c#validateForeignKeyConstraint](../../../raw/postgres-14/src/backend/commands/tablecmds.c#L11367-L11415).
2. `RI_Initial_Check()` returns false when RLS is enabled on either the referenced or referencing table and the current user is neither `BYPASSRLS` nor the owner of each RLS-enabled table involved [ri_triggers.c#RI_Initial_Check](../../../raw/postgres-14/src/backend/utils/adt/ri_triggers.c#L1358-L1368).
3. Each row-level FK check builds a query against the referenced table ending in `FOR KEY SHARE OF x` [ri_triggers.c#RI_FKey_check](../../../raw/postgres-14/src/backend/utils/adt/ri_triggers.c#L356-L390).
4. That row lock routes to the heap access method and then to `heap_lock_tuple()`, which sets the backend's oldest MultiXact membership marker and calls `compute_new_xmax_infomask()` to decide the new tuple `xmax` [heapam_handler.c#heapam_tuple_lock](../../../raw/postgres-14/src/backend/access/heap/heapam_handler.c#L365-L367) [heapam.c#heap_lock_tuple](../../../raw/postgres-14/src/backend/access/heap/heapam.c#L5094-L5111).
5. If the row already has a live MultiXact, the heap code expands it with `MultiXactIdExpand()`; if the row has a live single locker or updater, it creates a new MultiXact with `MultiXactIdCreate()` [heapam.c#compute_new_xmax_infomask](../../../raw/postgres-14/src/backend/access/heap/heapam.c#L5333-L5495).

So the performance risk is not "RLS causes MultiXact for every protected row." It is narrower: RLS can turn FK validation from one bulk query into many row-level FK checks; on a hot referenced key, those checks take `FOR KEY SHARE` row locks, and concurrent lockers or locker-plus-updater cases create or expand MultiXacts [ri_triggers.c#RI_Initial_Check](../../../raw/postgres-14/src/backend/utils/adt/ri_triggers.c#L1358-L1368) [heapam.c#compute_new_xmax_infomask](../../../raw/postgres-14/src/backend/access/heap/heapam.c#L5333-L5495). Normal child-table `INSERT`/`UPDATE` FK checks also use the same `FOR KEY SHARE` mechanism regardless of RLS; RLS mainly matters here because it disables the bulk validation shortcut for affected roles [ri_triggers.c#RI_FKey_check](../../../raw/postgres-14/src/backend/utils/adt/ri_triggers.c#L356-L390) [tablecmds.c#validateForeignKeyConstraint](../../../raw/postgres-14/src/backend/commands/tablecmds.c#L11367-L11415).

Once a tuple's `xmax` is a MultiXact, later code that needs its members first checks the backend-local MultiXact cache. That cache lasts only for the current transaction and is capped at 256 entries [multixact.c#cache-purpose](../../../raw/postgres-14/src/backend/access/transam/multixact.c#L296-L324) [multixact.c#mXactCachePut](../../../raw/postgres-14/src/backend/access/transam/multixact.c#L1713-L1758). On a miss, `GetMultiXactIdMembers()` reads the offsets and members SLRUs under the MultiXact SLRU locks [multixact.c#GetMultiXactIdMembers](../../../raw/postgres-14/src/backend/access/transam/multixact.c#L1386-L1580). PostgreSQL 14 has only 8 MultiXact-offset SLRU buffers and 16 MultiXact-member SLRU buffers [multixact.h#buffers](../../../raw/postgres-14/src/include/access/multixact.h#L32-L34). If those pages are not resident, the SLRU path marks a slot read-busy, releases the control lock during physical I/O, and issues a `pg_pread` reported as `SLRURead` [slru.c#SimpleLruReadPage-IO](../../../raw/postgres-14/src/backend/access/transam/slru.c#L439-L457) [slru.c#SlruPhysicalReadPage](../../../raw/postgres-14/src/backend/access/transam/slru.c#L719-L729).

For a deeper description of the MultiXact side, see [How MultiXact Works in PostgreSQL 14, and How Foreign Keys and Other Operations Degrade Performance When the Local Cache Spills to Secondary Storage](multixact-foreign-keys-cache-spill.md).

### RLS and the plan cache

**Yes — query planning has RLS-aware caching, but only through the plan cache, and that cache is deliberately keyed on the role and the `row_security` GUC.** The plan-cache manager lists RLS as one of the few reasons to throw cached work away: it re-does parse analysis and planning "if the active search_path is different from the previous time or, if RLS is involved, if the user changes or the RLS environment changes" [plancache.c#overview](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L14-L20). Two independent caches matter here:

- **The relcache policy set (`rd_rsdesc`)** caches each table's *parsed* policies. `RelationBuildRowSecurity()` deserializes every `polqual`/`polwithcheck` node tree once and reparents the descriptor under `CacheMemoryContext`, so later queries never re-read or re-parse `pg_policy` [policy.c#RelationBuildRowSecurity](../../../raw/postgres-14/src/backend/commands/policy.c#L195-L325). It is **role-independent**: it stores every policy on the table, and role/command filtering happens later at rewrite time, so `SET ROLE` does not invalidate it. A relcache rebuild even keeps the old descriptor when the policy set is unchanged (`equalRSDesc` -> `keep_policies`) [relcache.c#keep_policies](../../../raw/postgres-14/src/backend/utils/cache/relcache.c#L2668-L2725).
- **The plan cache (`CachedPlanSource`/`CachedPlan`)** caches the *derived* security quals and the finished plan, which are specific to the role and `row_security` value in effect when they were built. This is the "special caching for RLS," and the rest of this section is about it.

#### How the RLS plan cache works

A `CachedPlanSource` carries three RLS-specific fields (`rewriteRoleId`, `rewriteRowSecurity`, `dependsOnRLS`) and each derived `CachedPlan` carries `planRoleId` and `dependsOnRole` [plancache.h#CachedPlanSource](../../../raw/postgres-14/src/include/utils/plancache.h#L117-L119) [plancache.h#CachedPlan](../../../raw/postgres-14/src/include/utils/plancache.h#L154-L155). They are wired together as follows:

1. **Rewrite tags the query.** When `get_row_security_policies()` adds any policy quals, `fireRIRrules()` sets `Query->hasRowSecurity` [rewriteHandler.c#hasRowSecurity](../../../raw/postgres-14/src/backend/rewrite/rewriteHandler.c#L2351-L2358).
2. **Dependency extraction records it.** `extract_query_dependencies()` walks the rewritten tree and OR-collects every `hasRowSecurity` flag into the plansource's `dependsOnRLS` [setrefs.c#extract_query_dependencies](../../../raw/postgres-14/src/backend/optimizer/plan/setrefs.c#L3142-L3167) [setrefs.c#hasRowSecurity](../../../raw/postgres-14/src/backend/optimizer/plan/setrefs.c#L3219-L3221).
3. **The environment is captured.** At the moment the tree is cached, the plansource records what it was rewritten under: `rewriteRoleId = GetUserId()` and `rewriteRowSecurity = row_security` [plancache.c#capture](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L396-L403), and again after any re-analysis [plancache.c#recapture](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L755-L757).
4. **Reuse is gated on the environment.** Every `GetCachedPlan()` first calls `RevalidateCachedQuery()`, which invalidates the cached query tree when the query depends on RLS and either the user id or `row_security` has changed since capture [plancache.c#RevalidateCachedQuery](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L600-L607).
5. **The plan is tagged role-specific.** `BuildCachedPlan()` sets `plan->planRoleId = GetUserId()` and `plan->dependsOnRole = plansource->dependsOnRLS` [plancache.c#BuildCachedPlan](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L976-L994). A cached *generic* plan is then discarded by `CheckCachedPlan()` when the current user id differs from `planRoleId` [plancache.c#CheckCachedPlan](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L814-L819).

Net effect: a prepared statement or PL/pgSQL statement over an RLS table can reuse its cached query tree and, when the generic-plan path wins, its cached generic plan as long as the same role runs it with the same `row_security` value and no relevant DDL fires. The RLS rewrite (deriving and combining the security quals) is done once and reused; the planner may still re-run for custom plans.

#### In what scenarios does it not work

Each of these forces the RLS rewrite and/or planning to be redone:

- **The role changes.** `SET ROLE`, `SET SESSION AUTHORIZATION`, and entering a `SECURITY DEFINER` function all change `GetUserId()` [miscinit.c#GetUserId](../../../raw/postgres-14/src/backend/utils/init/miscinit.c#L477-L481) — `SET ROLE` assigns through `SetCurrentRoleId()` [variable.c#assign_role](../../../raw/postgres-14/src/backend/commands/variable.c#L955-L961) [miscinit.c#SetCurrentRoleId](../../../raw/postgres-14/src/backend/utils/init/miscinit.c#L905-L942), `SET SESSION AUTHORIZATION` assigns through `SetSessionAuthorization()` [variable.c#assign_session_authorization](../../../raw/postgres-14/src/backend/commands/variable.c#L840-L850) [miscinit.c#SetSessionAuthorization](../../../raw/postgres-14/src/backend/utils/init/miscinit.c#L873-L888), and a `SECURITY DEFINER` call uses `SetUserIdAndSecContext()` inside `fmgr_security_definer()` [fmgr.c#fmgr_security_definer](../../../raw/postgres-14/src/backend/utils/fmgr/fmgr.c#L716-L718). Any RLS-dependent cached query tree and generic plan are then rebuilt on next use. Connection poolers that `SET ROLE` per request are the classic case.
- **`row_security` changes.** It is a `PGC_USERSET` boolean (session/transaction scope; no restart or reload needed) [guc.c#row_security](../../../raw/postgres-14/src/backend/utils/misc/guc.c#L1722-L1730), and any change invalidates RLS-dependent cached trees on next use [plancache.c#RevalidateCachedQuery](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L600-L607).
- **The fast "simple validity" revalidation path never applies.** `CachedPlanAllowsSimpleValidityCheck()` returns false as soon as `dependsOnRLS` or `dependsOnRole` is set [plancache.c#simple-validity](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L1338-L1348). This is a belt-and-suspenders check: that cheap path exists only for *table-free* generic plans (it also rejects any plan whose range table contains an `RTE_RELATION`), and RLS always applies to a table, so an RLS plan would fail the table check regardless. RLS queries therefore always take the full `RevalidateCachedQuery()` path (search-path check, RLS check, and lock acquisition), never the cheap flag check used for scalar PL/pgSQL expressions.
- **Ad-hoc (simple-protocol) queries are never plan-cached at all.** `exec_simple_query()` runs `pg_analyze_and_rewrite()` then `pg_plan_queries()` directly, with no `CachedPlanSource` [postgres.c#exec_simple_query](../../../raw/postgres-14/src/backend/tcop/postgres.c#L1098-L1102), so a directly issued `SELECT` re-derives its RLS quals and re-plans on every call. SPI one-shot plans (`CreateOneShotCachedPlan`) are likewise always treated as custom and never saved [plancache.c#choose_custom_plan](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L1027-L1029).
- **Parameterized statements re-plan for their first executions.** `choose_custom_plan()` builds a fresh custom plan for the first five executions of a parameterized prepared statement (and indefinitely if custom plans keep winning) [plancache.c#choose_custom_plan](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L1050-L1069). Each custom build re-runs `pg_plan_queries()` — including the RLS security-level qual ordering — though it reuses the cached, already-rewritten tree when the role and GUC are unchanged.
- **`plan_cache_mode` can force the generic/custom choice.** It is a `PGC_USERSET` enum (session/transaction scope; no restart or reload needed) with `auto`, `force_generic_plan`, and `force_custom_plan` values [guc.c#plan_cache_mode](../../../raw/postgres-14/src/backend/utils/misc/guc.c#L4937-L4946) [guc.c#plan_cache_mode_options](../../../raw/postgres-14/src/backend/utils/misc/guc.c#L491-L495). `choose_custom_plan()` first rules out custom planning for cases where it is not useful, such as statements with no bound parameters, and then checks `plan_cache_mode` before the normal heuristic [plancache.c#choose_custom_plan](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L1031-L1042). For a parameterized RLS prepared statement where custom planning is possible, `force_custom_plan` preserves the cached rewritten tree when the role and `row_security` value are unchanged, but forces a fresh plan build on each execution.
- **SQL `DECLARE CURSOR` is not an additional cached-plan reuse surface.** `PerformCursorOpen()` rewrites and plans the cursor query immediately, copies the plan tree into the portal, and defines the portal with no `CachedPlan` reference [portalcmds.c#PerformCursorOpen](../../../raw/postgres-14/src/backend/commands/portalcmds.c#L75-L110). `PortalDefineQuery()` records a cached-plan reference only when its caller passes one, and prepared-statement execution is the path that passes the `CachedPlan` from `GetCachedPlan()` [portalmem.c#PortalDefineQuery](../../../raw/postgres-14/src/backend/utils/mmgr/portalmem.c#L265-L302) [prepare.c#ExecuteQuery](../../../raw/postgres-14/src/backend/commands/prepare.c#L229-L242). A `WITH HOLD` cursor survives by copying rows into a temporary memory/file tuplestore, not by reusing a plan across transactions [portalcmds.c#PersistHoldablePortal](../../../raw/postgres-14/src/backend/commands/portalcmds.c#L308-L314) [declare.sgml#WITH-HOLD](../../../raw/postgres-14/doc/src/sgml/ref/declare.sgml#L203-L213).
- **Policy or table DDL invalidates the caches.** `CREATE`/`ALTER`/`DROP POLICY` and `ALTER TABLE ... {ENABLE|DISABLE|FORCE|NO FORCE} ROW LEVEL SECURITY` emit relcache invalidations that free `rd_rsdesc` [relcache.c#rd_rsdesc-free](../../../raw/postgres-14/src/backend/utils/cache/relcache.c#L2463-L2467) and, through sinval, invalidate dependent cached plans [plancache.c#overview](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L14-L20). The next use rebuilds the policy set and re-plans.

#### The performance overhead of having no cache

When any of the above forces a rebuild, `RevalidateCachedQuery()` discards the cached query tree and re-runs full parse analysis and rewriting via `pg_analyze_and_rewrite()` [plancache.c#reanalyze](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L637-L699), then `BuildCachedPlan()` re-runs `pg_plan_queries()` [plancache.c#replan](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L936-L940). For an RLS table that means paying again for:

- **Re-deriving the security quals** — `get_row_security_policies()` re-selects the matching permissive/restrictive policies for the current command and role and rebuilds the OR/AND qual trees and `WITH CHECK` options [rowsecurity.c#add_security_quals](../../../raw/postgres-14/src/backend/rewrite/rowsecurity.c#L558-L637).
- **Re-locking and re-expanding policy sublinks** — if any applicable policy contains a subquery, the rewriter re-locks the referenced relations and re-fires RIR (view) rules on them [rewriteHandler.c#policy-sublinks](../../../raw/postgres-14/src/backend/rewrite/rewriteHandler.c#L2285-L2336).
- **Re-ordering quals for leakproofness** — the planner re-computes `qual_security_level` and re-runs `order_qual_clauses()`, so RLS quals still precede non-leakproof user quals [createplan.c#order_qual_clauses](../../../raw/postgres-14/src/backend/optimizer/plan/createplan.c#L5191-L5300).

Two mitigations are visible in source. First, the role-independent `rd_rsdesc` cache means even a full re-plan does **not** re-read or re-parse `pg_policy`; only the derivation and planning are repeated [policy.c#RelationBuildRowSecurity](../../../raw/postgres-14/src/backend/commands/policy.c#L195-L325). Second, a plain non-RLS query pays none of this: `check_enable_rls()` returns `RLS_NONE` for a table without `relrowsecurity`, so `dependsOnRLS` is never set and the ordinary (non-RLS) caching applies [rls.c#check_enable_rls](../../../raw/postgres-14/src/backend/utils/misc/rls.c#L61-L78). The pinned checkout contains no benchmark that quantifies the re-plan cost; the magnitude depends on policy count, whether policies contain sublinks, and how often the role or `row_security` changes.

### Settings related to the feature

There are six categories of settings.

#### `row_security` (GUC)

`row_security` is a boolean GUC declared `PGC_USERSET` in the `CLIENT_CONN_STATEMENT` group, defaulting to **on** [guc.c#row_security](../../../raw/postgres-14/src/backend/utils/misc/guc.c#L1722-L1730) [rls.h#row_security](../../../raw/postgres-14/src/include/utils/rls.h#L17). Because the context is `PGC_USERSET`, it is **session/transaction scoped**: any user can change it with `SET row_security = on|off` or `SET LOCAL`, and it needs no server restart or reload. It does not turn RLS off for the data — when it is `off`, a query that *would* be filtered by a policy raises an error instead (for users who are actually subject to RLS); owners and `BYPASSRLS`/superusers still bypass regardless [rls.c#row_security-off](../../../raw/postgres-14/src/backend/utils/misc/rls.c#L120-L132). `pg_dump` sets it `off` by default so a dump fails loudly rather than silently omitting rows [pg_dump.c#row_security](../../../raw/postgres-14/src/bin/pg_dump/pg_dump.c#L1226-L1233) [config.sgml#row_security](../../../raw/postgres-14/doc/src/sgml/config.sgml#L8226-L8234).

#### `plan_cache_mode` (GUC)

`plan_cache_mode` is not RLS-specific, but it directly controls the generic-vs-custom plan choice described in [RLS and the plan cache](#rls-and-the-plan-cache). It is a `PGC_USERSET` enum in the `QUERY_TUNING_OTHER` group, defaulting to `auto`, with `force_generic_plan` and `force_custom_plan` alternatives [guc.c#plan_cache_mode](../../../raw/postgres-14/src/backend/utils/misc/guc.c#L4937-L4946) [guc.c#plan_cache_mode_options](../../../raw/postgres-14/src/backend/utils/misc/guc.c#L491-L495). Because the context is `PGC_USERSET`, it is **session/transaction scoped**: any user can change it with `SET plan_cache_mode = ...` or `SET LOCAL`, and it needs no server restart or reload. For prepared statements where custom planning is possible, `force_custom_plan` makes each execution build a fresh custom plan, while `force_generic_plan` makes `choose_custom_plan()` take the generic path when planning is needed [plancache.c#choose_custom_plan](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L1031-L1042) [config.sgml#plan_cache_mode](../../../raw/postgres-14/doc/src/sgml/config.sgml#L5903-L5916). RLS-dependent generic plans still remain guarded by role and `row_security` revalidation [plancache.c#CheckCachedPlan](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L814-L819) [plancache.c#RevalidateCachedQuery](../../../raw/postgres-14/src/backend/utils/cache/plancache.c#L600-L607).

#### Table-level settings (`ALTER TABLE`)

Two `pg_class` booleans control RLS per table, both set through `ALTER TABLE`:

| Statement | Catalog effect | Set by |
|---|---|---|
| `ENABLE ROW LEVEL SECURITY` / `DISABLE ROW LEVEL SECURITY` | `relrowsecurity = true/false` | [tablecmds.c#ATExecSetRowSecurity](../../../raw/postgres-14/src/backend/commands/tablecmds.c#L15835-L15857) |
| `FORCE ROW LEVEL SECURITY` / `NO FORCE ROW LEVEL SECURITY` | `relforcerowsecurity = true/false` | [tablecmds.c#ATExecForceNoForceRowSecurity](../../../raw/postgres-14/src/backend/commands/tablecmds.c#L15862-L15883) |

The four spellings are distinct `ALTER TABLE` subcommands in the grammar [gram.y#alter-table-rls](../../../raw/postgres-14/src/backend/parser/gram.y#L2659-L2685). Enabling/disabling RLS and adding policies is restricted to the table owner [ddl.sgml#owner-only](../../../raw/postgres-14/doc/src/sgml/ddl.sgml#L2287-L2289). `DISABLE ROW LEVEL SECURITY` leaves the policy rows in `pg_policy` but stops applying them; `FORCE` makes the owner subject to RLS too (except in RI contexts).

#### Role-level setting (`BYPASSRLS`)

The `BYPASSRLS` / `NOBYPASSRLS` role attribute maps to `pg_authid.rolbypassrls` [pg_authid.h#rolbypassrls](../../../raw/postgres-14/src/include/catalog/pg_authid.h#L41). It is given on `CREATE ROLE`/`ALTER ROLE`; the parser turns the `BYPASSRLS`/`NOBYPASSRLS` words into a `bypassrls` option [gram.y#bypassrls](../../../raw/postgres-14/src/backend/parser/gram.y#L1156-L1159), and only a superuser may set or change it [user.c#CreateRole-bypassrls](../../../raw/postgres-14/src/backend/commands/user.c#L240-L309) [user.c#AlterRole-bypassrls](../../../raw/postgres-14/src/backend/commands/user.c#L658-L737). Superusers implicitly always bypass RLS even without the attribute [aclchk.c#has_bypassrls_privilege](../../../raw/postgres-14/src/backend/catalog/aclchk.c#L5471-L5488).

#### Per-policy options (`CREATE POLICY` / `ALTER POLICY`)

`CREATE POLICY name ON table` accepts, in order, the per-policy "settings" that become `pg_policy` columns [gram.y#CreatePolicyStmt](../../../raw/postgres-14/src/backend/parser/gram.y#L5237-L5252):

- `AS PERMISSIVE | RESTRICTIVE` — **default `PERMISSIVE`** [gram.y#permissive-default](../../../raw/postgres-14/src/backend/parser/gram.y#L5288-L5304).
- `FOR ALL | SELECT | INSERT | UPDATE | DELETE` — **default `ALL`** [gram.y#cmd-default](../../../raw/postgres-14/src/backend/parser/gram.y#L5306-L5317).
- `TO role[, ...]` — **default `PUBLIC`** [gram.y#to-default](../../../raw/postgres-14/src/backend/parser/gram.y#L5278-L5281); a `PUBLIC` entry mixed with named roles warns and collapses to `PUBLIC` alone [policy.c#policy_role_list_to_array](../../../raw/postgres-14/src/backend/commands/policy.c#L139-L186).
- `USING (expr)` — the read/visibility filter (optional) [gram.y#using](../../../raw/postgres-14/src/backend/parser/gram.y#L5268-L5271).
- `WITH CHECK (expr)` — the write check (optional; falls back to `USING` when absent) [gram.y#with-check](../../../raw/postgres-14/src/backend/parser/gram.y#L5273-L5276).

`ALTER POLICY` can change only the roles, `USING`, and `WITH CHECK`; it has no `AS` or `FOR` clause, so a policy's permissive/restrictive nature and its command **cannot** be altered after creation (drop and recreate instead) [gram.y#AlterPolicyStmt](../../../raw/postgres-14/src/backend/parser/gram.y#L5254-L5266). Policy DDL requires table ownership and rejects non-tables and system catalogs [policy.c#RangeVarCallbackForPolicy](../../../raw/postgres-14/src/backend/commands/policy.c#L66-L99). Policies are visible through the `pg_policies` system view, which decodes `polpermissive`, `polroles`, and `polcmd` into readable text [system_views.sql#pg_policies](../../../raw/postgres-14/src/backend/catalog/system_views.sql#L73-L101).

#### Extension hooks

Not user settings, but configurable behavior: `row_security_policy_hook_permissive` and `row_security_policy_hook_restrictive` let a loaded module add policies [rowsecurity.h#hooks](../../../raw/postgres-14/src/include/rewrite/rowsecurity.h#L37-L42).

## Open Questions

- This page documents mechanisms and the source-evident performance consequences of RLS in PostgreSQL 14, but it does **not** include a quantified benchmark (rows/sec or latency per policy, role, aggregate shape, partition count, or RLS-induced FK/MultiXact workload), and that includes the no-cache re-plan cost described under [RLS and the plan cache](#rls-and-the-plan-cache): the source shows *what* work is repeated on a role/`row_security` change, but not its measured cost. The pinned checkout's `rowsecurity` regression test exercises correctness, not performance [rowsecurity.sql](../../../raw/postgres-14/src/test/regress/sql/rowsecurity.sql); no in-tree benchmark quantifying RLS overhead was located.
- The exact definitions and volatility declarations for external JWT helper functions such as `auth.uid()` and `auth.jwt()` are not present in the pinned PostgreSQL 14 checkout. The InitPlan behavior is verified for PostgreSQL's planner and executor, but a production policy should verify the helper function's volatility and whether once-per-execution evaluation is semantically correct.
- The exact set and minor-release provenance of RLS-related fixes shipped within the 14.x series (the v14 checkout is pinned at `REL_14_23-3-g5c00f4e2e3b`) has not been traced here. This page describes the behavior as it stands at the pin, not its change history.
