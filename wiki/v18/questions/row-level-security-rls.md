## Answer

### Answer Up Front

PostgreSQL 18 implements Row-Level Security during query rewrite, not as a table access method or executor-only feature. For each ordinary or partitioned table range-table entry, the rewriter calls `get_row_security_policies()`, decides whether RLS applies for the RTE's permission-check role (`checkAsUser`, or the current effective role when that OID is invalid) and the `row_security` setting, then injects policy expressions as `RangeTblEntry.securityQuals` for row visibility and as `WithCheckOption` entries for writes.[rowsecurity.c#get_row_security_policies](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L97-L150) [rewriteHandler.c#fireRIRrules](../../../raw/postgres-18/src/backend/rewrite/rewriteHandler.c#L2224-L2334)

The visibility rule is "OR permissive policies, AND restrictive policies"; if RLS applies but no permissive policy matches, PostgreSQL adds a constant-false qual, which is the default-deny behavior.[rowsecurity.c#add_security_quals](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L688-L778) Write checks use `WITH CHECK` expressions when present, fall back to `USING` expressions when needed, and create error-producing `WithCheckOption` entries for `INSERT`, `UPDATE`, `ON CONFLICT DO UPDATE`, and `MERGE` actions.[rowsecurity.c#add_with_check_options](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L780-L909) [parsenodes.h#WCOKind](../../../raw/postgres-18/src/include/nodes/parsenodes.h#L1386-L1404)

The main costs are copying and repeatedly walking policy trees at rewrite, planning larger OR/AND trees under security-ordering constraints, estimating opaque functions, evaluating residual quals, rebuilding custom physical plans, duplicating parent restrictions across surviving partitions, and acquiring `AccessExclusiveLock` for policy DDL.[rowsecurity.c#get_policies_for_relation](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L532-L654) [createplan.c#order_qual_clauses](../../../raw/postgres-18/src/backend/optimizer/plan/createplan.c#L5386-L5470) [plancat.c#function_selectivity](../../../raw/postgres-18/src/backend/optimizer/util/plancat.c#L2055-L2108) [plancache.c#BuildCachedPlan](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L1047-L1075) [inherit.c#apply_child_basequals](../../../raw/postgres-18/src/backend/optimizer/util/inherit.c#L830-L920) [policy.c#CreatePolicy-lock](../../../raw/postgres-18/src/backend/commands/policy.c#L626-L633) Suitable visibility quals can still become index conditions or partition-pruning steps.[indxpath.c#match_clause_to_index](../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L2598-L2612) [partprune.c#prune_append_rel_partitions](../../../raw/postgres-18/src/backend/partitioning/partprune.c#L769-L833) Relation policy rows and role-membership expansions are cached, so neither catalog scan is repeated for every policy test.[policy.c#RelationBuildRowSecurity](../../../raw/postgres-18/src/backend/commands/policy.c#L192-L322) [acl.c#roles_is_member_of-cache](../../../raw/postgres-18/src/backend/utils/adt/acl.c#L5133-L5170)

The most important cache boundary is not an overhead issue but an authorization-staleness risk: PostgreSQL keys an RLS-dependent cached query tree on effective role OID and `row_security`, not on membership edges, `BYPASSRLS`, superuser status, or current-database ownership.[plancache.c#RLS-invalidation](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L710-L717) [acl.c#roles_is_member_of](../../../raw/postgres-18/src/backend/utils/adt/acl.c#L5209-L5246) [aclchk.c#has_bypassrls_privilege](../../../raw/postgres-18/src/backend/catalog/aclchk.c#L4188-L4205) The exact-pin reproductions and mitigation are detailed under [RLS and the plan cache](#rls-and-the-plan-cache).

The only RLS-specific server GUC is `row_security`; it is `PGC_USERSET`, defaults to `on`, and therefore has session or transaction scope, not reload or restart scope.[guc_tables.c#row_security](../../../raw/postgres-18/src/backend/utils/misc/guc_tables.c#L1696-L1703) Direct related surfaces include table and policy DDL, role membership and `BYPASSRLS`, `security_invoker` views, `row_security_active()`, logical-subscription `run_as_owner`, adjacent `plan_cache_mode` and `enable_partitionwise_aggregate`, catalog/`psql` inspection, and dump/restore options.[pg_class.h#relrowsecurity](../../../raw/postgres-18/src/include/catalog/pg_class.h#L110-L114) [pg_policy.h#FormData_pg_policy](../../../raw/postgres-18/src/include/catalog/pg_policy.h#L29-L43) [reloptions.c#view_reloptions](../../../raw/postgres-18/src/backend/access/common/reloptions.c#L132-L148) [rls.c#row_security_active](../../../raw/postgres-18/src/backend/utils/misc/rls.c#L135-L167) [Settings and Related Surfaces](#settings-and-related-surfaces) states the exact scope and restart impact for each.

The reproducible history audit identifies 21 in-scope corrections or RLS-specific security, operational, performance, metadata, and documentation changes that were not already present in the PostgreSQL 14.0 release. See [Fixes Since PostgreSQL 14](#fixes-since-postgresql-14) and [Context Reviewed](#context-reviewed).

### Implementation Path

RLS starts with table metadata. `pg_class` stores whether a relation has row security enabled and whether owners are forced through policies, and `pg_policy` stores policy name, command, permissive/restrictive mode, role array, `USING` expression, and `WITH CHECK` expression.[pg_class.h#FormData_pg_class](../../../raw/postgres-18/src/include/catalog/pg_class.h#L110-L114) [pg_policy.h#FormData_pg_policy](../../../raw/postgres-18/src/include/catalog/pg_policy.h#L29-L43)

When relcache initializes or rebuilds an RLS-enabled relation descriptor, it calls `RelationBuildRowSecurity()`. That function scans `pg_policy`, copies each policy's roles and serialized expression trees into a dedicated `RowSecurityDesc` memory context, and caches whether policy expressions contain sublinks.[relcache.c#RelationBuildRowSecurity-caller](../../../raw/postgres-18/src/backend/utils/cache/relcache.c#L1248-L1267) [policy.c#RelationBuildRowSecurity](../../../raw/postgres-18/src/backend/commands/policy.c#L192-L322) The in-memory `RowSecurityPolicy` stores the command kind, permissive flag, roles, policy qual, `WITH CHECK` qual, and sublink marker; `RelationData.rd_rsdesc` holds the relation-level descriptor.[rowsecurity.h#RowSecurityPolicy](../../../raw/postgres-18/src/include/rewrite/rowsecurity.h#L20-L35) [rel.h#rd_rsdesc](../../../raw/postgres-18/src/include/utils/rel.h#L111-L120)

`pg_policy.h` is also a build input, not only a C struct declaration. It includes the generated `pg_policy_d.h`; the Make and Meson catalog builds pass `pg_policy.h` through `genbki.pl` to produce that header and `postgres.bki`. The generated header supplies catalog, index, and attribute-number constants such as `PolicyRelationId`, `PolicyPolrelidPolnameIndexId`, and `Anum_pg_policy_*` used by `policy.c`.[pg_policy.h#generated-header](../../../raw/postgres-18/src/include/catalog/pg_policy.h#L18-L56) [catalog/Makefile#generated-headers](../../../raw/postgres-18/src/include/catalog/Makefile#L16-L88) [catalog/Makefile#genbki](../../../raw/postgres-18/src/include/catalog/Makefile#L117-L143) [catalog/meson.build#generated_catalog_headers](../../../raw/postgres-18/src/include/catalog/meson.build#L104-L145) [policy.c#generated-catalog-constants](../../../raw/postgres-18/src/backend/commands/policy.c#L218-L286)

During rewrite, `fireRIRrules()` loops over range-table entries, skips non-table and non-partitioned-table entries, calls `get_row_security_policies()`, prepends returned security quals to the RTE, appends returned write checks to the query, and marks the query if RLS or sublinks are present.[rewriteHandler.c#fireRIRrules](../../../raw/postgres-18/src/backend/rewrite/rewriteHandler.c#L2224-L2334) When a policy expression contains sublinks, rewrite recurses into those sublinks and also locks relations referenced by the sublink query.[rewriteHandler.c#fireRIRrules-sublinks](../../../raw/postgres-18/src/backend/rewrite/rewriteHandler.c#L2281-L2323)

`get_row_security_policies()` first rejects non-table and non-partitioned-table relations, finds the user to check from the RTE permission info, and calls `check_enable_rls()` to classify the relation as no RLS, no RLS but environment-dependent, or RLS enabled.[rowsecurity.c#get_row_security_policies](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L97-L150) The environment-dependent case adds no quals but marks `Query.hasRowSecurity` so a cached plan is invalidated if the role or `row_security` setting later changes.[rowsecurity.c#get_row_security_policies](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L136-L150) [plancache.c#RLS-invalidation](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L710-L717)

Policy selection is command-specific and can require several passes over the policy list. The query command is the baseline; `SELECT FOR UPDATE` or `SELECT FOR SHARE` first adds `UPDATE` visibility policies, `UPDATE`/`DELETE`/`MERGE` adds `SELECT` policies when the statement needs SELECT rights, and `INSERT`/`UPDATE ... RETURNING` adds `SELECT` policies as write checks. `ON CONFLICT DO UPDATE` adds its UPDATE and SELECT passes, while `MERGE` uses action-specific SELECT, UPDATE, DELETE, and INSERT paths rather than a separate MERGE policy kind.[rowsecurity.c#get_row_security_policies](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L153-L301) [rowsecurity.c#ON-CONFLICT](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L303-L378) [rowsecurity.c#MERGE](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L381-L514)

PostgreSQL copies the protected RTE's `checkAsUser` into relation permission records inside `Query` nodes found in policy quals and write checks, so relations referenced through those query nodes are permission-checked under that identity.[rowsecurity.c#setRuleCheckAsUser-caller](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L516-L523) [rewriteDefine.c#setRuleCheckAsUser](../../../raw/postgres-18/src/backend/rewrite/rewriteDefine.c#L625-L684) Policy functions still follow the normal `SECURITY INVOKER` default or `SECURITY DEFINER` rule; the querying identity must otherwise have access to objects referenced by the policy expression.[create_policy.sgml#policy-expression-permissions](../../../raw/postgres-18/doc/src/sgml/ref/create_policy.sgml#L727-L739) [create_function.sgml#SECURITY-INVOKER-DEFINER](../../../raw/postgres-18/doc/src/sgml/ref/create_function.sgml#L405-L419) Direct or mutual recursion through policy subqueries raises `infinite recursion detected in policy for relation` during rewrite.[rewriteHandler.c#policy-recursion](../../../raw/postgres-18/src/backend/rewrite/rewriteHandler.c#L2257-L2309) [rowsecurity.sql#policy-recursion](../../../raw/postgres-18/src/test/regress/sql/rowsecurity.sql#L479-L577)

Extensions can add policies through two exported in-process hooks. Permissive hook policies are OR-combined with internal permissive policies, and restrictive hook policies are AND-combined with internal restrictive policies.[rowsecurity.h#hook-API](../../../raw/postgres-18/src/include/rewrite/rowsecurity.h#L37-L47) [rowsecurity.c#hooks](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L77-L87) [rowsecurity.c#hook-callers](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L608-L653) Hook policies arrive only at rewrite; `pg_policies` and pg_dump read `pg_policy`, so they do not expose or dump hook-provided policies.[system_views.sql#pg_policies](../../../raw/postgres-18/src/backend/catalog/system_views.sql#L73-L106) [pg_dump.c#getPolicies](../../../raw/postgres-18/src/bin/pg_dump/pg_dump.c#L4124-L4233) The only in-tree hook assignment is the `src/test/modules/test_rls_hooks` module; no v18 `contrib` module consumes either hook.[test_rls_hooks.c#hooks](../../../raw/postgres-18/src/test/modules/test_rls_hooks/test_rls_hooks.c#L32-L162) [test_rls_hooks.sql#coverage](../../../raw/postgres-18/src/test/modules/test_rls_hooks/sql/test_rls_hooks.sql#L20-L161)

### Visibility and Write Checks

For visibility, `add_security_quals()` gathers policy `USING` expressions. It appends restrictive policy expressions as separate ANDed quals, ORs all permissive policy expressions into one qual, and injects a constant-false qual if no permissive policy exists.[rowsecurity.c#add_security_quals](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L688-L778)

For writes, `add_with_check_options()` builds `WithCheckOption` entries. Permissive policies are combined into one OR expression, restrictive policies become separate checks with policy names for error reporting, and a no-permissive-policy case becomes a false check.[rowsecurity.c#add_with_check_options](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L780-L909) The executor evaluates those entries per tuple and suppresses row data in RLS error messages.[execMain.c#ExecWithCheckOptions](../../../raw/postgres-18/src/backend/executor/execMain.c#L2222-L2370)

Default deny has different visible effects by operation. A false visibility qual makes `SELECT`, `UPDATE`, and `DELETE` find no eligible rows; a false RLS write check rejects a proposed `INSERT` or new `UPDATE` row with an RLS violation.[rowsecurity.c#default-deny-visibility](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L755-L777) [rowsecurity.c#default-deny-write-check](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L894-L908) [execMain.c#ExecWithCheckOptions](../../../raw/postgres-18/src/backend/executor/execMain.c#L2222-L2370)

`INSERT` and `UPDATE` use `WITH CHECK` when a policy has it, otherwise they use the policy's `USING` expression for write checks when needed.[rowsecurity.c#INSERT-UPDATE-WCO](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L258-L301) `ON CONFLICT DO UPDATE` uses conflict-check WCOs for update `USING`, adds `SELECT` policies if the statement needs SELECT rights, and then adds update `WITH CHECK` checks.[rowsecurity.c#ON-CONFLICT](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L303-L378) `MERGE` uses the dedicated `WCO_RLS_MERGE_UPDATE_CHECK` and `WCO_RLS_MERGE_DELETE_CHECK` kinds for existing-row checks, while a `MERGE` INSERT action uses the ordinary `WCO_RLS_INSERT_CHECK`; the executor applies an UPDATE or DELETE MERGE check only after that action's `WHEN` qual passes.[parsenodes.h#WCOKind](../../../raw/postgres-18/src/include/nodes/parsenodes.h#L1386-L1404) [rowsecurity.c#MERGE](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L381-L514) [nodeModifyTable.c#MERGE-WCO](../../../raw/postgres-18/src/backend/executor/nodeModifyTable.c#L3168-L3178)

The SQL documentation matches the source rule: `USING` filters visible rows, `WITH CHECK` checks new rows for `INSERT` and `UPDATE`, `WITH CHECK` defaults to the `USING` expression when absent, and policy expressions run before ordinary user conditions except where leakproof functions can move earlier.[create_policy.sgml#USING-WITH-CHECK](../../../raw/postgres-18/doc/src/sgml/ref/create_policy.sgml#L43-L68) [ddl.sgml#RLS-expression-order](../../../raw/postgres-18/doc/src/sgml/ddl.sgml#L2643-L2656)

For INSERT, PostgreSQL runs BEFORE ROW triggers, computes stored generated columns, checks RLS WCOs, and only then checks ordinary and partition constraints; UPDATE follows the same WCO-before-ordinary-constraints boundary after its BEFORE ROW trigger and generated-column work.[nodeModifyTable.c#ExecInsert-check-order](../../../raw/postgres-18/src/backend/executor/nodeModifyTable.c#L895-L913) [nodeModifyTable.c#ExecInsert-WCO](../../../raw/postgres-18/src/backend/executor/nodeModifyTable.c#L1057-L1107) [nodeModifyTable.c#ExecUpdate-check-order](../../../raw/postgres-18/src/backend/executor/nodeModifyTable.c#L2084-L2153) [nodeModifyTable.c#ExecUpdate-WCO](../../../raw/postgres-18/src/backend/executor/nodeModifyTable.c#L2181-L2215) A cross-partition UPDATE maps the statement's reference WCO list to the destination partition, routes the moved row through `ExecInsert()`, and runs the destination's UPDATE WCO check there.[execPartition.c#ExecInitPartitionInfo-WCO](../../../raw/postgres-18/src/backend/executor/execPartition.c#L550-L614) [nodeModifyTable.c#cross-partition-ExecInsert](../../../raw/postgres-18/src/backend/executor/nodeModifyTable.c#L2050-L2071) [nodeModifyTable.c#ExecInsert-routed-update-WCO](../../../raw/postgres-18/src/backend/executor/nodeModifyTable.c#L1066-L1090)

### Policy Storage and DDL

`CREATE POLICY` and expression-changing `ALTER POLICY` parse policy expressions with the policy expression kind, store serialized expression trees in `pg_policy`, record role and expression dependencies, and invalidate the relation cache.[policy.c#CreatePolicy](../../../raw/postgres-18/src/backend/commands/policy.c#L568-L759) [policy.c#AlterPolicy](../../../raw/postgres-18/src/backend/commands/policy.c#L767-L1089) `ALTER POLICY ... RENAME TO` follows a separate `rename_policy()` path that checks duplicate/missing names, updates the catalog tuple, and invalidates relcache.[gram.y#policy-rename](../../../raw/postgres-18/src/backend/parser/gram.y#L9506-L9527) [policy.c#rename_policy](../../../raw/postgres-18/src/backend/commands/policy.c#L1091-L1195) All three paths lock the table with `AccessExclusiveLock`.[policy.c#CreatePolicy-lock](../../../raw/postgres-18/src/backend/commands/policy.c#L626-L633) [policy.c#AlterPolicy-lock](../../../raw/postgres-18/src/backend/commands/policy.c#L802-L808) [policy.c#rename_policy-lock](../../../raw/postgres-18/src/backend/commands/policy.c#L1107-L1115)

Policy DDL is limited to ordinary tables and partitioned tables, requires table ownership, and rejects system tables unless `allowSystemTableMods` permits them.[policy.c#RangeVarCallbackForPolicy](../../../raw/postgres-18/src/backend/commands/policy.c#L48-L96) `CREATE POLICY` rejects `WITH CHECK` for `SELECT`/`DELETE` and `USING` for `INSERT`; omitted clauses default to `AS PERMISSIVE`, `FOR ALL`, and `TO PUBLIC`.[policy.c#CreatePolicy-expression-errors](../../../raw/postgres-18/src/backend/commands/policy.c#L593-L616) [gram.y#CreatePolicyStmt](../../../raw/postgres-18/src/backend/parser/gram.y#L5890-L5982) [create_policy.sgml#parameters](../../../raw/postgres-18/doc/src/sgml/ref/create_policy.sgml#L76-L99)

`CREATE POLICY` does not enable RLS. `ALTER TABLE ... ENABLE/DISABLE ROW LEVEL SECURITY` changes `pg_class.relrowsecurity`, and `ALTER TABLE ... FORCE/NO FORCE ROW LEVEL SECURITY` changes `pg_class.relforcerowsecurity`.[create_policy.sgml#enablement-separate](../../../raw/postgres-18/doc/src/sgml/ref/create_policy.sgml#L35-L40) [tablecmds.c#ATExecSetRowSecurity](../../../raw/postgres-18/src/backend/commands/tablecmds.c#L18602-L18630) [tablecmds.c#ATExecForceNoForceRowSecurity](../../../raw/postgres-18/src/backend/commands/tablecmds.c#L18633-L18659) Those owner-only subcommands require `AccessExclusiveLock`, apply to tables and partitioned tables, and do not recurse to inheritance children or partitions.[tablecmds.c#ATPrepCmd-locks](../../../raw/postgres-18/src/backend/commands/tablecmds.c#L4708-L4718) [tablecmds.c#ATSimplePermissions](../../../raw/postgres-18/src/backend/commands/tablecmds.c#L5251-L5258)

Dropping a policy removes the catalog row, opens the target relation with `AccessExclusiveLock`, and invalidates the relcache; if RLS remains enabled and no policy permits a row, the default-deny path still applies.[policy.c#RemovePolicyById](../../../raw/postgres-18/src/backend/commands/policy.c#L331-L400)

### Bypass and Environment Decisions

`check_enable_rls()` returns `RLS_NONE` if the relation has no RLS or is a built-in relation that should not apply it.[rls.c#check_enable_rls](../../../raw/postgres-18/src/backend/utils/misc/rls.c#L51-L78) Superusers and roles with `BYPASSRLS` bypass policies, and table owners bypass policies unless the table is forced through RLS or PostgreSQL is inside a no-force-RLS operation.[rls.c#check_enable_rls](../../../raw/postgres-18/src/backend/utils/misc/rls.c#L80-L118)

Referential-integrity code is the concrete no-force-RLS caller: it prepares and executes internal foreign-key checks as the relevant table owner with `SECURITY_NOFORCE_RLS`, so FORCE RLS does not filter those internal checks.[ri_triggers.c#ri_PlanCheck](../../../raw/postgres-18/src/backend/utils/adt/ri_triggers.c#L2437-L2475) [ri_triggers.c#ri_PerformCheck](../../../raw/postgres-18/src/backend/utils/adt/ri_triggers.c#L2577-L2590) [rls.c#owner-no-force-bypass](../../../raw/postgres-18/src/backend/utils/misc/rls.c#L90-L118) Separately, PostgreSQL documents that unique, primary-key, and foreign-key integrity checks bypass RLS to preserve integrity and can therefore reveal that a hidden value exists.[create_policy.sgml#referential-integrity-bypass](../../../raw/postgres-18/doc/src/sgml/ref/create_policy.sgml#L698-L714)

If RLS applies and the `row_security` GUC is off, `check_enable_rls()` raises an error unless its caller requested no error.[rls.c#check_enable_rls](../../../raw/postgres-18/src/backend/utils/misc/rls.c#L120-L132) The SQL functions `row_security_active(oid)` and `row_security_active(text)` expose the same decision path to SQL callers.[rls.c#row_security_active](../../../raw/postgres-18/src/backend/utils/misc/rls.c#L135-L167) [pg_proc.dat#row_security_active](../../../raw/postgres-18/src/include/catalog/pg_proc.dat#L12262-L12270)

The role attribute is stored as `pg_authid.rolbypassrls`, and only a current user with `BYPASSRLS` can create or alter a role to have that attribute.[pg_authid.h#rolbypassrls](../../../raw/postgres-18/src/include/catalog/pg_authid.h#L35-L41) [user.c#CreateRole-BYPASSRLS](../../../raw/postgres-18/src/backend/commands/user.c#L339-L344) [user.c#AlterRole-BYPASSRLS](../../../raw/postgres-18/src/backend/commands/user.c#L796-L817)

### Planner and Executor Effects

RLS quals are stored in `RangeTblEntry.securityQuals`, the same security-barrier qual list used for security-barrier views.[parsenodes.h#RangeTblEntry.securityQuals](../../../raw/postgres-18/src/include/nodes/parsenodes.h#L1031-L1036) [parsenodes.h#RangeTblEntry.securityQuals-field](../../../raw/postgres-18/src/include/nodes/parsenodes.h#L1277-L1278) The planner computes the maximum security level from those lists and preprocesses each security qual separately.[planner.c#securityQuals-level](../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L828-L836) [planner.c#preprocess-securityQuals](../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L1044-L1055)

`process_security_barrier_quals()` moves RLS security quals into base-relation `RestrictInfo` nodes with increasing security levels. They therefore participate in ordinary planning while retaining security-ordering metadata.[initsplan.c#process_security_barrier_quals](../../../raw/postgres-18/src/backend/optimizer/plan/initsplan.c#L1602-L1655) A securely promotable qual that matches an index can become an index qual, and a partition-key qual in `baserestrictinfo` can prune partitions; a higher-level non-leakproof qual cannot move ahead of a lower security level.[indxpath.c#match_clause_to_index](../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L2598-L2612) [restrictinfo.c#restriction_is_securely_promotable](../../../raw/postgres-18/src/backend/optimizer/util/restrictinfo.c#L415-L434) [partprune.c#prune_append_rel_partitions](../../../raw/postgres-18/src/backend/partitioning/partprune.c#L769-L833) The whole rewritten query, including policy functions in `securityQuals`, also goes through the ordinary parallel-hazard walk, so a policy's function parallel-safety markings can limit parallel plans.[planner.c#max_parallel_hazard](../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L368-L382) [clauses.c#max_parallel_hazard](../../../raw/postgres-18/src/backend/optimizer/util/clauses.c#L721-L740) [clauses.c#query-tree-walk](../../../raw/postgres-18/src/backend/optimizer/util/clauses.c#L945-L970) [nodeFuncs.c#securityQuals-walk](../../../raw/postgres-18/src/backend/nodes/nodeFuncs.c#L2864-L2879)

Cached query trees store whether rewrite depends on RLS, the effective role OID used for rewrite, and the `row_security` setting; validation rejects the cached tree if that role OID or setting differs.[plancache.h#RLS-cache-fields](../../../raw/postgres-18/src/include/utils/plancache.h#L122-L133) [plancache.c#RLS-dependencies](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L445-L452) [plancache.c#RLS-invalidation](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L710-L717) `extract_query_dependencies_walker()` also records role dependence when a `Query` node has RLS.[setrefs.c#extract_query_dependencies](../../../raw/postgres-18/src/backend/optimizer/plan/setrefs.c#L3634-L3660) [setrefs.c#dependsOnRole](../../../raw/postgres-18/src/backend/optimizer/plan/setrefs.c#L3711-L3713)

That cache key does **not** contain a role-membership generation. Policy role matching calls `has_privs_of_role()`, and `pg_auth_members` invalidation clears the ACL membership cache, but `InitPlanCache()` registers no auth-membership callback. A prepared RLS query reused under the same effective role can therefore retain the policy set selected before a membership `GRANT` or `REVOKE`; reconnecting, deallocating and preparing again, or the session-local `DISCARD PLANS` forces fresh rewrite.[rowsecurity.c#check_role_for_policy](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L911-L932) [acl.c#role-membership-invalidation](../../../raw/postgres-18/src/backend/utils/adt/acl.c#L5037-L5084) [plancache.c#InitPlanCache](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L141-L156) [discard.c#DISCARD_PLANS](../../../raw/postgres-18/src/backend/commands/discard.c#L27-L41) The exact-pin reproduction is recorded under [Context Reviewed](#context-reviewed); the in-tree prepared-statement tests change effective roles, not membership under an unchanged effective role.[rowsecurity.sql#role-plan-invalidation](../../../raw/postgres-18/src/test/regress/sql/rowsecurity.sql#L1361-L1385)

Executor permission checks do not implement RLS visibility; they run ordinary ACL checks at executor startup, while RLS write checks run through `ExecWithCheckOptions()` for the relevant WCO kind.[execMain.c#ExecCheckPermissions](../../../raw/postgres-18/src/backend/executor/execMain.c#L565-L576) [execMain.c#ExecWithCheckOptions](../../../raw/postgres-18/src/backend/executor/execMain.c#L2222-L2370) Insert, update, `ON CONFLICT`, partition-movement, and `MERGE` paths choose the WCO kind before calling that executor check.[nodeModifyTable.c#INSERT-WCO](../../../raw/postgres-18/src/backend/executor/nodeModifyTable.c#L1068-L1090) [nodeModifyTable.c#UPDATE-WCO](../../../raw/postgres-18/src/backend/executor/nodeModifyTable.c#L2205-L2214) [nodeModifyTable.c#ON-CONFLICT-WCO](../../../raw/postgres-18/src/backend/executor/nodeModifyTable.c#L2874-L2890) [nodeModifyTable.c#MERGE-WCO](../../../raw/postgres-18/src/backend/executor/nodeModifyTable.c#L3168-L3178)

RLS also affects error detail paths. When RLS is active for the reporting role, foreign-key, unique/exclusion, ordinary constraint, and no-partition-found helpers omit row or key details so an error does not disclose a hidden row.[ri_triggers.c#ri_ReportViolation](../../../raw/postgres-18/src/backend/utils/adt/ri_triggers.c#L2684-L2723) [genam.c#BuildIndexValueDescription](../../../raw/postgres-18/src/backend/access/index/genam.c#L192-L208) [execMain.c#ExecBuildSlotValueDescription](../../../raw/postgres-18/src/backend/executor/execMain.c#L2410-L2416) [execPartition.c#ExecFindPartition-error-detail](../../../raw/postgres-18/src/backend/executor/execPartition.c#L1611-L1655)

### Partitions Views COPY and Replication

For inheritance and partition expansion, PostgreSQL deliberately leaves each generated child RTE's `securityQuals` empty and translates the parent's base restrictions, including the parent's RLS quals, to children. A query through the parent therefore uses the parent's policies regardless of child policy flags; a query that names a child directly rewrites that child as its own RTE and uses the child's policies.[inherit.c#expand_single_inheritance_child](../../../raw/postgres-18/src/backend/optimizer/util/inherit.c#L478-L505) [inherit.c#apply_child_basequals](../../../raw/postgres-18/src/backend/optimizer/util/inherit.c#L830-L920) [rowsecurity.sql#direct-partition-access](../../../raw/postgres-18/src/test/regress/sql/rowsecurity.sql#L349-L404) Child-specific `securityQuals` are handled separately for UNION ALL append relations, not ordinary inheritance children.[inherit.c#apply_child_securityQuals](../../../raw/postgres-18/src/backend/optimizer/util/inherit.c#L922-L959)

Views normally set the underlying table's `checkAsUser` to the view owner, so that owner's privileges and policies apply; a `security_invoker` view leaves it invalid, causing the invoking effective role to be checked instead.[relcache.c#view-rule-checkAsUser](../../../raw/postgres-18/src/backend/utils/cache/relcache.c#L854-L881) [rewriteHandler.c#security-invoker-target-view](../../../raw/postgres-18/src/backend/rewrite/rewriteHandler.c#L3561-L3586) [create_policy.sgml#views](../../../raw/postgres-18/doc/src/sgml/ref/create_policy.sgml#L727-L739)

`COPY TO` on an RLS-applicable table is converted to a query `COPY`, while `COPY FROM` raises an error because the copy-from path does not support RLS checks.[copy.c#DoCopy-RLS](../../../raw/postgres-18/src/backend/commands/copy.c#L208-L234) The generated RLS `COPY TO` query marks the source relation as `ONLY`, so inheritance children are not silently copied through the generated query.[copy.c#COPY-TO-RLS-ONLY](../../../raw/postgres-18/src/backend/commands/copy.c#L289-L299)

The source query of `CREATE TABLE AS` goes through `QueryRewrite()` and therefore gets ordinary RLS treatment, but its destination receiver rejects the write only when RLS is active for the destination and caller because that receiver does not implement policy checks.[createas.c#CTAS-source-rewrite](../../../raw/postgres-18/src/backend/commands/createas.c#L283-L324) [createas.c#CTAS-RLS](../../../raw/postgres-18/src/backend/commands/createas.c#L525-L546) `TRUNCATE` and `REFERENCES` have no policy command: ordinary `TRUNCATE` uses table ACLs rather than per-row policies.[create_policy.sgml#policy-commands](../../../raw/postgres-18/doc/src/sgml/ref/create_policy.sgml#L22-L29) [tablecmds.c#truncate_check_perms](../../../raw/postgres-18/src/backend/commands/tablecmds.c#L2417-L2429)

Logical replication does not evaluate policy expressions per replicated row. For replicated `INSERT`, `UPDATE`, and `DELETE`, apply switches to the table owner when `run_as_owner = false` and stays as the subscription owner when it is true; each operation then calls `TargetPrivilegesCheck()`, which rejects the operation when RLS applies to that selected role. Initial table synchronization selects the same role before its ACL/RLS check and local `COPY FROM`.[worker.c#INSERT-role-and-check](../../../raw/postgres-18/src/backend/replication/logical/worker.c#L2423-L2496) [worker.c#UPDATE-role-and-check](../../../raw/postgres-18/src/backend/replication/logical/worker.c#L2589-L2723) [worker.c#DELETE-role-and-check](../../../raw/postgres-18/src/backend/replication/logical/worker.c#L2793-L2890) [tablesync.c#initial-copy-role-and-check](../../../raw/postgres-18/src/backend/replication/logical/tablesync.c#L1511-L1547) Default DML apply therefore normally bypasses unforced RLS as table owner but rejects a forced-RLS table; subscription-owner mode depends on that owner's own bypass or ownership status.[027_nosuperuser.pl#forced-RLS](../../../raw/postgres-18/src/test/subscription/t/027_nosuperuser.pl#L204-L246)

Replicated `TRUNCATE` has a different boundary. Apply calls `TargetPrivilegesCheck()` as the subscription owner before `ExecuteTruncateGuts()` sees `run_as_owner`; when `run_as_owner = false`, the later table-owner switches cover the BEFORE and AFTER statement triggers, not that prior ACL/RLS gate.[worker.c#TRUNCATE-role-boundary](../../../raw/postgres-18/src/backend/replication/logical/worker.c#L3240-L3346) [tablecmds.c#TRUNCATE-BEFORE-trigger-role](../../../raw/postgres-18/src/backend/commands/tablecmds.c#L2125-L2136) [tablecmds.c#TRUNCATE-AFTER-trigger-role](../../../raw/postgres-18/src/backend/commands/tablecmds.c#L2334-L2345)

### Scalability and Performance Issues

A fresh analysis/rewrite copies applicable policy trees, and planning preprocesses each security qual. A valid cached query tree avoids that repeated rewrite work, but a changed effective role or `row_security` value forces it again.[rowsecurity.c#add_security_quals](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L688-L778) [planner.c#preprocess-securityQuals](../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L1044-L1055) [plancache.c#RLS-invalidation](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L710-L717) At execution, RLS visibility expressions can be per-candidate-tuple filters, while write WCO expressions are checked for each proposed tuple of the relevant kind; this is not an unconditional per-row surcharge because ordinary optimization can turn suitable visibility quals into index conditions or partition-pruning steps.[execMain.c#ExecWithCheckOptions](../../../raw/postgres-18/src/backend/executor/execMain.c#L2222-L2370) [indxpath.c#match_clause_to_index](../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L2598-L2612) [partprune.c#prune_append_rel_partitions](../../../raw/postgres-18/src/backend/partitioning/partprune.c#L769-L833)

Policy count affects both tree size and rewrite work. Permissive expressions form one OR tree; restrictive expressions remain separate ANDed quals or WCOs. Each call to `get_policies_for_relation()` walks every cached policy, checks command and role applicability, sorts matching restrictive policies by name, and invokes both extension hooks; command-specific layering can call it several times, so complex write statements scale roughly with policy count times policy-selection passes.[rowsecurity.c#get_policies_for_relation](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L532-L654) [rowsecurity.c#command-specific-policy-passes](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L186-L514) [rowsecurity.c#add_security_quals](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L688-L778) [rowsecurity.c#add_with_check_options](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L780-L909) The `pg_policy` scan itself occurs when relcache builds or rebuilds `rd_rsdesc`, not on every rewrite, and repeated `has_privs_of_role()` calls for one effective role reuse the ACL membership expansion cache.[policy.c#RelationBuildRowSecurity](../../../raw/postgres-18/src/backend/commands/policy.c#L192-L322) [rowsecurity.c#check_role_for_policy](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L911-L932) [acl.c#roles_is_member_of-cache](../../../raw/postgres-18/src/backend/utils/adt/acl.c#L5133-L5170)

Security levels can constrain predicate ordering and early index/TID use: a higher-level non-leakproof qual cannot be promoted ahead of lower-level security quals, while leakproof quals may move earlier. Policy functions also participate in the query's parallel-safety walk, so a parallel-restricted or parallel-unsafe function in a policy can reduce parallel execution.[restrictinfo.c#restriction_is_securely_promotable](../../../raw/postgres-18/src/backend/optimizer/util/restrictinfo.c#L415-L434) [createplan.c#order_qual_clauses](../../../raw/postgres-18/src/backend/optimizer/plan/createplan.c#L5386-L5470) [ddl.sgml#RLS-expression-order](../../../raw/postgres-18/doc/src/sgml/ddl.sgml#L2643-L2656) [planner.c#max_parallel_hazard](../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L368-L382)

RLS quals also affect cardinality and CPU-cost estimates because the planner includes `baserestrictinfo` in base-row selectivity and restriction cost. Sequential scans charge residual restriction cost against base tuples, while index paths charge residual quals against fetched tuples.[costsize.c#set_baserel_size_estimates](../../../raw/postgres-18/src/backend/optimizer/path/costsize.c#L5336-L5368) [costsize.c#cost_seqscan](../../../raw/postgres-18/src/backend/optimizer/path/costsize.c#L295-L360) [costsize.c#cost_index](../../../raw/postgres-18/src/backend/optimizer/path/costsize.c#L799-L814) An opaque Boolean policy function without planner support gets the default selectivity `0.3333333`; its estimated execution cost comes from a support function or `pg_proc.procost * cpu_operator_cost`.[clausesel.c#clause_selectivity_ext](../../../raw/postgres-18/src/backend/optimizer/path/clausesel.c#L863-L876) [plancat.c#function_selectivity](../../../raw/postgres-18/src/backend/optimizer/util/plancat.c#L2055-L2108) [plancat.c#add_function_cost](../../../raw/postgres-18/src/backend/optimizer/util/plancat.c#L2111-L2168) Opaque Boolean helpers and large permissive OR trees can therefore produce inaccurate estimates and poor join or aggregate choices even when enforcement is correct; the planner estimates remaining OR branches as independent, and within one security level it orders quals by estimated evaluation cost rather than selectivity.[clausesel.c#clauselist_selectivity_or](../../../raw/postgres-18/src/backend/optimizer/path/clausesel.c#L345-L418) [createplan.c#order_qual_clauses](../../../raw/postgres-18/src/backend/optimizer/plan/createplan.c#L5386-L5470)

Policy subqueries require post-parse relation locking and recursive RIR rewrite. Their execution frequency depends on shape: uncorrelated scalar/`EXISTS`/array sublinks can become InitPlans, hashable uncorrelated `ANY` subplans can use a hash table, and correlated subplans remain dependent on outer tuples.[rewriteHandler.c#fireRIRrules-sublinks](../../../raw/postgres-18/src/backend/rewrite/rewriteHandler.c#L2281-L2323) [subselect.c#InitPlans](../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L375-L445) [subselect.c#ANY-and-materialization](../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L511-L539) The documentation's function/subquery policy examples therefore add ordinary function and subquery costs, but not necessarily one full subquery execution per protected row.[ddl.sgml#RLS-subquery-example](../../../raw/postgres-18/doc/src/sgml/ddl.sgml#L2984-L3001)

Prepared statements can save analysis and rewrite work while an RLS-dependent cached query tree remains valid; only a valid generic physical plan also saves planning. Custom plans copy the rewritten tree and run the planner again, and automatic mode tries at least five custom plans for parameterized statements before its generic-versus-custom cost decision.[plancache.c#RevalidateCachedQuery](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L653-L735) [plancache.c#BuildCachedPlan](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L1047-L1075) [plancache.c#choose_custom_plan](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L1152-L1205) [plancache.c#GetCachedPlan](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L1261-L1365) Role or `row_security` changes invalidate the RLS-dependent query tree, while SQL-function inlining propagates role dependence when it introduces RLS.[plancache.c#RLS-invalidation](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L710-L717) [clauses.c#inline_function-RLS](../../../raw/postgres-18/src/backend/optimizer/util/clauses.c#L5334-L5339) The same-effective-role authorization boundary described under [RLS and the plan cache](#rls-and-the-plan-cache) instead preserves reuse too aggressively; `DISCARD PLANS` is a session-local mitigation, not a reload or restart.[discard.c#DISCARD_PLANS](../../../raw/postgres-18/src/backend/commands/discard.c#L27-L41)

Partition expansion translates parent RLS restrictions to children, so large surviving append sets duplicate those restriction trees across child planning. Quals on partition keys can reduce the set through plan-time or runtime pruning.[inherit.c#apply_child_basequals](../../../raw/postgres-18/src/backend/optimizer/util/inherit.c#L830-L920) [partprune.c#make_partition_pruneinfo](../../../raw/postgres-18/src/backend/partitioning/partprune.c#L217-L320) [partprune.c#prune_append_rel_partitions](../../../raw/postgres-18/src/backend/partitioning/partprune.c#L769-L833)

Policy and table-RLS DDL has high lock impact because create, expression-alter, rename, drop, and `ALTER TABLE ... ROW LEVEL SECURITY` paths take `AccessExclusiveLock` on the table. That lock conflicts with every standard table lock mode; policy DDL closes the table with `NoLock`, retaining its table lock until transaction end.[policy.c#CreatePolicy-lock](../../../raw/postgres-18/src/backend/commands/policy.c#L626-L633) [policy.c#CreatePolicy-unlock](../../../raw/postgres-18/src/backend/commands/policy.c#L744-L759) [policy.c#AlterPolicy-lock](../../../raw/postgres-18/src/backend/commands/policy.c#L802-L808) [policy.c#rename_policy-lock](../../../raw/postgres-18/src/backend/commands/policy.c#L1107-L1115) [policy.c#RemovePolicyById](../../../raw/postgres-18/src/backend/commands/policy.c#L331-L400) [tablecmds.c#ATPrepCmd-locks](../../../raw/postgres-18/src/backend/commands/tablecmds.c#L4708-L4718) [lock.c#LockConflicts](../../../raw/postgres-18/src/backend/storage/lmgr/lock.c#L65-L105) [table.c#table_close](../../../raw/postgres-18/src/backend/access/table/table.c#L109-L123)

`COPY TO` under active RLS uses query planning and policy evaluation instead of the direct relation-copy path.[copy.c#DoCopy-RLS](../../../raw/postgres-18/src/backend/commands/copy.c#L208-L234) `COPY FROM`, a CTAS destination, logical-replication DML, and initial table synchronization reject rather than become slower per-row enforcement paths when `check_enable_rls()` says RLS applies to the relevant role. Replicated `TRUNCATE` uses the subscription owner for that gate even when later trigger code runs as table owner.[copy.c#DoCopy-RLS](../../../raw/postgres-18/src/backend/commands/copy.c#L230-L234) [createas.c#CTAS-RLS](../../../raw/postgres-18/src/backend/commands/createas.c#L525-L546) [worker.c#TargetPrivilegesCheck](../../../raw/postgres-18/src/backend/replication/logical/worker.c#L2351-L2381) [tablesync.c#initial-copy-role-and-check](../../../raw/postgres-18/src/backend/replication/logical/tablesync.c#L1511-L1547) [worker.c#TRUNCATE-role-boundary](../../../raw/postgres-18/src/backend/replication/logical/worker.c#L3240-L3346)

The pinned source gives qualitative, not measured, RLS guidance. It calls policies based only on the current row's values the simplest and best-performing case; it says subqueries/functions add their costs; and it warns that using `SELECT ... FOR SHARE` to close the documented policy race can become a problem under heavy row-share locking and frequent updates.[ddl.sgml#RLS-best-performing](../../../raw/postgres-18/doc/src/sgml/ddl.sgml#L2944-L2954) [ddl.sgml#RLS-row-share-lock](../../../raw/postgres-18/doc/src/sgml/ddl.sgml#L3040-L3056)

The checkout has no benchmark that quantifies overhead by policy, role, partition, or predicate count. Core and hook tests use non-ANALYZE `EXPLAIN`, contain no `\timing`, `EXPLAIN (ANALYZE)`, or `pg_sleep`, and use at most 100 generated rows in the inheritance/partition/leaky-operator cases.[rowsecurity.sql#EXPLAIN-COSTS-OFF](../../../raw/postgres-18/src/test/regress/sql/rowsecurity.sql#L133-L142) [rowsecurity.sql#partition-plan-shape](../../../raw/postgres-18/src/test/regress/sql/rowsecurity.sql#L2192-L2217) [test_rls_hooks.sql#EXPLAIN](../../../raw/postgres-18/src/test/modules/test_rls_hooks/sql/test_rls_hooks.sql#L61-L91) The 101 `CREATE POLICY` statements are separate correctness scenarios, not a policy-count workload. Whole-tree benchmark searches are recorded under [Context Reviewed](#context-reviewed), so this page reports mechanisms rather than inventing an overhead percentage.

### RLS and the plan cache

There is no separate RLS plan cache. PostgreSQL's ordinary caches provide three relevant layers: the relation cache stores parsed policy definitions in `rd_rsdesc`; a `CachedPlanSource` can retain the analyzed and rewritten query tree; and a valid generic `CachedPlan` can retain the physical plan. Custom plans reuse the query tree but run the planner again.[policy.c#RelationBuildRowSecurity](../../../raw/postgres-18/src/backend/commands/policy.c#L192-L322) [plancache.c#RevalidateCachedQuery](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L653-L735) [plancache.c#BuildCachedPlan](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L1047-L1075) [plancache.c#GetCachedPlan](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L1261-L1365)

During rewrite, `get_row_security_policies()` sets `Query.hasRowSecurity` when RLS applies or could apply after an environment change (`RLS_NONE_ENV`). `fireRIRrules()` propagates that flag from view actions, subqueries, CTEs, and sublinks to the containing query.[rowsecurity.c#RLS_NONE_ENV](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L136-L149) [rewriteHandler.c#view-hasRowSecurity](../../../raw/postgres-18/src/backend/rewrite/rewriteHandler.c#L1864-L1883) [rewriteHandler.c#nested-query-hasRowSecurity](../../../raw/postgres-18/src/backend/rewrite/rewriteHandler.c#L1998-L2012) [rewriteHandler.c#CTE-and-sublink-hasRowSecurity](../../../raw/postgres-18/src/backend/rewrite/rewriteHandler.c#L2190-L2223) Dependency extraction OR-collects the flag into `CachedPlanSource.dependsOnRLS`.[setrefs.c#extract_query_dependencies](../../../raw/postgres-18/src/backend/optimizer/plan/setrefs.c#L3617-L3660) [setrefs.c#dependsOnRLS](../../../raw/postgres-18/src/backend/optimizer/plan/setrefs.c#L3710-L3714)

The cached source records the effective role OID (`rewriteRoleId`) and `row_security` value (`rewriteRowSecurity`) used for rewrite. Revalidation invalidates the query tree when either differs.[plancache.h#RLS-cache-fields](../../../raw/postgres-18/src/include/utils/plancache.h#L122-L133) [plancache.c#RLS-invalidation](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L710-L717) A generic plan separately records `planRoleId` and `dependsOnRole`, and `CheckCachedPlan()` rejects it when the current role OID differs.[plancache.c#BuildCachedPlan-role](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L1106-L1120) [plancache.c#CheckCachedPlan](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L930-L963) The simple-validity fast path is unavailable when `dependsOnRLS` or `dependsOnRole` is set.[plancache.c#CachedPlanAllowsSimpleValidityCheck](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L1473-L1483)

That key is narrower than the authorization state used to select policies and bypass RLS. Inherited policy-role access follows each `pg_auth_members.inherit_option`, including the special current-database-owner case, while bypass also depends on superuser, `rolbypassrls`, table ownership, and FORCE RLS.[acl.c#roles_is_member_of](../../../raw/postgres-18/src/backend/utils/adt/acl.c#L5209-L5246) [acl.c#has_privs_of_role](../../../raw/postgres-18/src/backend/utils/adt/acl.c#L5276-L5301) [aclchk.c#has_bypassrls_privilege](../../../raw/postgres-18/src/backend/catalog/aclchk.c#L4188-L4205) [rls.c#check_enable_rls](../../../raw/postgres-18/src/backend/utils/misc/rls.c#L51-L132) Role-level `INHERIT` only supplies the default for a newly created membership; changing an existing edge requires `GRANT ... WITH INHERIT TRUE/FALSE`.[user.c#AddRoleMems](../../../raw/postgres-18/src/backend/commands/user.c#L1845-L1938)

`InitPlanCache()` registers no authorization-catalog callback. A cached statement reused under the same effective role can therefore retain its old RLS policy set or bypass decision after membership `GRANT`/`REVOKE`, an edge's `WITH INHERIT` change, `BYPASSRLS` or superuser changes, or a current-database ownership change.[plancache.c#InitPlanCache](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L141-L156) The exact-pin reproductions for all four categories are recorded under [Context Reviewed](#context-reviewed). `DISCARD PLANS` invalidates revalidatable saved plans and cached expressions but retains prepared-statement definitions; their next use revalidates and replans.[discard.c#DISCARD_PLANS](../../../raw/postgres-18/src/backend/commands/discard.c#L27-L41) [plancache.c#ResetPlanCache](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L2297-L2339) [discard.sgml#PLANS](../../../raw/postgres-18/doc/src/sgml/ref/discard.sgml#L45-L51)

Caching does not apply uniformly. Simple-protocol statements are parsed, analyzed/rewritten, and planned on every execution; one-shot SPI plans are temporary and always choose a custom plan; parameterized statements in automatic mode build at least five custom plans and may continue doing so, while `force_custom_plan` always rebuilds the physical plan.[postgres.c#exec_simple_query-parse](../../../raw/postgres-18/src/backend/tcop/postgres.c#L1061-L1065) [postgres.c#exec_simple_query-plan](../../../raw/postgres-18/src/backend/tcop/postgres.c#L1167-L1194) [spi.c#_SPI_prepare_oneshot_plan](../../../raw/postgres-18/src/backend/executor/spi.c#L2310-L2370) [plancache.c#choose_custom_plan](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L1152-L1205)

The miss cost depends on the layer. ### RLS and MultiXact

RLS rewrite itself does not create MultiXacts; it returns `USING` quals and write checks.[rowsecurity.c#get_row_security_policies](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L97-L114) Two concrete ways RLS can add MultiXact work are locking policy subqueries and the foreign-key validation fallback.[nodeLockRows.c#ExecLockRows](../../../raw/postgres-18/src/backend/executor/nodeLockRows.c#L159-L189) [ri_triggers.c#RI_Initial_Check-RLS](../../../raw/postgres-18/src/backend/utils/adt/ri_triggers.c#L1555-L1610)

A policy subquery that explicitly locks referenced rows — for example `SELECT ... FOR SHARE` — reaches `ExecLockRows`, which maps `ROW_MARK_SHARE` to `LockTupleShare` and calls `table_tuple_lock`.[nodeLockRows.c#ExecLockRows](../../../raw/postgres-18/src/backend/executor/nodeLockRows.c#L159-L189) `heap_lock_tuple()` can then expand an existing MultiXact or create a new one through `MultiXactIdExpand()`/`MultiXactIdCreate()` while computing the tuple's new `xmax`.[heapam.c#heap_lock_tuple](../../../raw/postgres-18/src/backend/access/heap/heapam.c#L5154-L5163) [heapam.c#compute_new_xmax_infomask](../../../raw/postgres-18/src/backend/access/heap/heapam.c#L5415-L5582) How often that locking subquery runs depends on its sublink shape: a correlated subplan can execute per outer tuple, while an eligible uncorrelated scalar sublink becomes an InitPlan evaluated at most once per occurrence.[subselect.c#build_subplan](../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L375-L445)

Foreign-key validation can also fall back from one bulk query to per-row checks. `RI_Initial_Check()` returns false when either table has RLS enabled unless the validating role has `BYPASSRLS` or owns every RLS-enabled table among the referenced and referencing tables, so `validateForeignKeyConstraint()` scans the referencing table and calls `RI_FKey_check_ins()` for each row.[ri_triggers.c#RI_Initial_Check-RLS](../../../raw/postgres-18/src/backend/utils/adt/ri_triggers.c#L1555-L1610) [tablecmds.c#validateForeignKeyConstraint](../../../raw/postgres-18/src/backend/commands/tablecmds.c#L13727-L13779) Those checks build a `FOR KEY SHARE` lookup when a referenced key is found, which can reach the same tuple-lock/MultiXact machinery.[ri_triggers.c#RI_FKey_check-query](../../../raw/postgres-18/src/backend/utils/adt/ri_triggers.c#L369-L426)

Once a MultiXact is created, member lookup first consults a backend-local cache capped at 256 entries; a miss reads the MultiXact offset and member SLRUs through `SimpleLruReadPage`.[multixact.c#MXactCacheEnt](../../../raw/postgres-18/src/backend/access/transam/multixact.c#L378-L403) [multixact.c#GetMultiXactIdMembers-cache](../../../raw/postgres-18/src/backend/access/transam/multixact.c#L1490-L1510) [multixact.c#GetMultiXactIdMembers-SLRU](../../../raw/postgres-18/src/backend/access/transam/multixact.c#L1583-L1690)

### RLS and aggregation

RLS can slow aggregation by changing the rows and plan that feed `ExecAgg`; PostgreSQL has no separate RLS aggregate executor.[initsplan.c#process_security_barrier_quals](../../../raw/postgres-18/src/backend/optimizer/plan/initsplan.c#L1602-L1655) [nodeAgg.c#ExecAgg](../../../raw/postgres-18/src/backend/executor/nodeAgg.c#L2230-L2274)

`process_security_barrier_quals()` moves RLS `USING` expressions into `baserestrictinfo`.[initsplan.c#process_security_barrier_quals](../../../raw/postgres-18/src/backend/optimizer/plan/initsplan.c#L1602-L1655) `ExecAgg` then receives the tuples produced by its outer subplan after those restrictions.[nodeAgg.c#ExecAgg](../../../raw/postgres-18/src/backend/executor/nodeAgg.c#L2230-L2274) Practical mitigations visible in v18 source are:

1. **Make the predicate cheap and indexable.** Because RLS quals live in `baserestrictinfo`, `match_clause_to_index()` can promote safely-leveled clauses into index quals and `check_index_predicates()` can use them to prove partial-index predicates [indxpath.c#match_clause_to_index](../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L2586-L2612) [indxpath.c#check_index_predicates](../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L3921-L4059).
2. **Use partitioning and consider `enable_partitionwise_aggregate`.** `prune_append_rel_partitions()` consumes `baserestrictinfo`, so an RLS predicate on the partition key can prune partitions before aggregation.[partprune.c#prune_append_rel_partitions](../../../raw/postgres-18/src/backend/partitioning/partprune.c#L769-L833) `enable_partitionwise_aggregate` is `PGC_USERSET` (session/transaction scope, no reload or restart) and lets the planner consider partitionwise aggregation when grouping sets are absent.[guc_tables.c#enable_partitionwise_aggregate](../../../raw/postgres-18/src/backend/utils/misc/guc_tables.c#L951-L960) [planner.c#create_ordinary_grouping_paths](../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L3869-L3874)
3. **Keep policy functions parallel-safe.** The planner's `max_parallel_hazard()` walk descends into `securityQuals`; a parallel-unsafe policy function disables parallel mode for the aggregate query.[planner.c#max_parallel_hazard](../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L368-L384) [clauses.c#max_parallel_hazard](../../../raw/postgres-18/src/backend/optimizer/util/clauses.c#L721-L741) [nodeFuncs.c#securityQuals-walk](../../../raw/postgres-18/src/backend/nodes/nodeFuncs.c#L2864-L2879)
4. **Separate query-tree reuse from physical-plan reuse.** A stable effective role and `row_security` value can preserve the rewritten tree, but only a valid generic plan avoids planning; custom plans still invoke the planner.[plancache.c#RevalidateCachedQuery](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L653-L735) [plancache.c#GetCachedPlan](../../../raw/postgres-18/src/backend/utils/cache/plancache.c#L1261-L1365)
5. **Do not use `row_security = off` as a shortcut.** For a non-bypass role it raises an error rather than disabling RLS.[rls.c#check_enable_rls](../../../raw/postgres-18/src/backend/utils/misc/rls.c#L120-L132)

Direct aggregates, grouping operations, and window functions are rejected in a policy expression itself; a subquery inside the policy can contain them, with ordinary subquery planning and execution costs.[parse_agg.c#aggregate-policy-error](../../../raw/postgres-18/src/backend/parser/parse_agg.c#L409-L413) [parse_agg.c#window-policy-error](../../../raw/postgres-18/src/backend/parser/parse_agg.c#L934-L936)

### Do RLS filter conditions need to be in the query?

No. PostgreSQL 18 already gives the planner every applicable `USING` expression, so the complete effective visibility predicate does not need to be copied into `WHERE` for the planner to see it.[rewriteHandler.c#fireRIRrules](../../../raw/postgres-18/src/backend/rewrite/rewriteHandler.c#L2242-L2334) [initsplan.c#process_security_barrier_quals](../../../raw/postgres-18/src/backend/optimizer/plan/initsplan.c#L1602-L1655)

`fireRIRrules()` prepends the returned RLS quals to the range-table entry's `securityQuals` [rewriteHandler.c#fireRIRrules](../../../raw/postgres-18/src/backend/rewrite/rewriteHandler.c#L2242-L2334). `process_security_barrier_quals()` then transfers them into the table's `baserestrictinfo` at successively higher security levels [initsplan.c#process_security_barrier_quals](../../../raw/postgres-18/src/backend/optimizer/plan/initsplan.c#L1602-L1655). The planner therefore already uses them for index paths [indxpath.c#match_clause_to_index](../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L2586-L2612), partial-index proofs [indxpath.c#check_index_predicates](../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L3921-L4059), and partition pruning [partprune.c#prune_append_rel_partitions](../../../raw/postgres-18/src/backend/partitioning/partprune.c#L769-L833).

Restating the predicate adds another qual but does not lower the original RLS qual's security level. Restrictive policy sublists are inserted before the permissive OR sublist, successive policy sublists receive increasing security levels, and user-written quals are distributed at the maximum `qual_security_level`.[rowsecurity.c#add_security_quals](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L688-L778) [planner.c#qual_security_level](../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L828-L836) [initsplan.c#distribute-user-quals](../../../raw/postgres-18/src/backend/optimizer/plan/initsplan.c#L1498-L1505) Only genuinely leakproof filters may cross a lower security level, and `LEAKPROOF` is a superuser-set security property rather than a tuning hint.[restrictinfo.c#restriction_is_securely_promotable](../../../raw/postgres-18/src/backend/optimizer/util/restrictinfo.c#L415-L434) [create_function.sgml#LEAKPROOF](../../../raw/postgres-18/doc/src/sgml/ref/create_function.sgml#L356-L378) Copying only one branch of a permissive-policy OR is not an optimization of the same condition; it changes which rows the query asks for.[rowsecurity.c#permissive-policy-OR](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L734-L753)

`WITH CHECK` expressions are write-time checks, not read restrictions. The planner preprocesses them separately from `RangeTblEntry.securityQuals`, so an index or pruning predicate needed for reading must come from a `USING` policy or the query, not only from `WITH CHECK`.[planner.c#preprocess-WCOs](../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L908-L917) [planner.c#preprocess-securityQuals](../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L1044-L1055)

### Wrapping a function in a subquery to evaluate it once

Sometimes. When the wrapper survives planning as an **uncorrelated scalar sublink**, it can remove repeated executor calls. The call-count rule is zero or one InitPlan evaluation per surviving planner occurrence per execution of the outer plan that contains it. That guarantee does not by itself prove the wrapped query is faster, and it is not one global function call per SQL text, transaction, session, or prepared statement.[subselect.c#scalar-InitPlan](../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L376-L411) [nodeSubplan.c#lazy-InitPlan](../../../raw/postgres-18/src/backend/executor/nodeSubplan.c#L1048-L1081) [perform.sgml#initplan-execution](../../../raw/postgres-18/doc/src/sgml/perform.sgml#L674-L701)

For `(SELECT helper())`, the planner creates a `PARAM_EXEC`, registers the SubPlan as an InitPlan, and replaces that scalar sublink with the parameter. The executor leaves the InitPlan unevaluated until the parameter is first demanded, stores the result in the current `EState`, and clears the parameter's `execPlan` link. Later reads of that parameter reuse the stored value. A new `ExecutorStart` creates a new `EState` and zeroed `PARAM_EXEC` workspace, so each execution of the containing saved or prepared plan starts fresh.[subselect.c#scalar-InitPlan](../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L397-L411) [subselect.c#register-InitPlan](../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L542-L551) [nodeSubplan.c#mark-InitPlan-unevaluated](../../../raw/postgres-18/src/backend/executor/nodeSubplan.c#L853-L875) [execExprInterp.c#ExecEvalParamExec](../../../raw/postgres-18/src/backend/executor/execExprInterp.c#L3056-L3070) [execMain.c#per-execution-PARAM_EXEC](../../../raw/postgres-18/src/backend/executor/execMain.c#L172-L193) Because evaluation is lazy, an occurrence that is never demanded executes zero times.[nodeSubplan.c#ExecSetParamPlan](../../../raw/postgres-18/src/backend/executor/nodeSubplan.c#L1048-L1077)

RLS uses this ordinary planner mechanism. PostgreSQL preprocesses sublinks in both RLS security quals and write checks, but the RLS rewriter first copies stored policy expressions into the generated `securityQuals` and `WithCheckOption` trees.[planner.c#preprocess-WCOs](../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L908-L917) [planner.c#preprocess-securityQuals](../../../raw/postgres-18/src/backend/optimizer/plan/planner.c#L1044-L1055) [rowsecurity.c#copy-policy-quals](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L714-L765) [rowsecurity.c#copy-policy-WCOs](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L817-L875) Each surviving `SubLink` node is processed separately, so a policy used in more than one RTE or copied into visibility and write-check layers can produce more than one InitPlan; structurally equal policy quals can also be deduplicated before planning.[subselect.c#process_sublinks_mutator](../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L2026-L2064) [rowsecurity.c#list_append_unique](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L742-L765) [list.c#list_append_unique](../../../raw/postgres-18/src/backend/nodes/list.c#L1334-L1349) Wrapping a query-written helper affects only that occurrence; it does not cache a separate bare helper copied from a policy. The regression suite likewise shows one written scalar subquery becoming two InitPlans after pull-up, while another survives as one.[subselect.sql#surviving-sublink-occurrences](../../../raw/postgres-18/src/test/regress/sql/subselect.sql#L626-L639) [subselect.out#surviving-InitPlans](../../../raw/postgres-18/src/test/regress/expected/subselect.out#L1156-L1217) A correlated scalar subquery has outer parameters and follows the regular SubPlan path instead, where it can be recomputed for outer rows.[subselect.c#build-parParam](../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L347-L374) [subselect.c#correlated-regular-SubPlan](../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L488-L540)

The main win is a residual filter. Marking a function `STABLE` promises one result for the same arguments within the statement and permits optimizations, but it does not install a general executor memoization cache. If the bare call remains in a filter evaluated for many candidate tuples, its function opcode runs whenever that expression is evaluated; a lossy bitmap heap scan can also recheck the original qual for every tuple on a lossy page. Replacing the call with an InitPlan parameter avoids those repeated function calls.[xfunc.sgml#function-volatility](../../../raw/postgres-18/doc/src/sgml/xfunc.sgml#L1612-L1653) [execExprInterp.c#EEOP_FUNCEXPR](../../../raw/postgres-18/src/backend/executor/execExprInterp.c#L928-L939) [nodeBitmapHeapscan.c#lossy-recheck](../../../raw/postgres-18/src/backend/executor/nodeBitmapHeapscan.c#L130-L165)

The call count is not monotonically lower in every plan. An index runtime key can demand the InitPlan before a scan that finds no tuples, while a bare residual call is not evaluated when the access method returns no tuple because scan quals run only after a tuple is fetched.[nodeIndexscan.c#ExecReScanIndexScan](../../../raw/postgres-18/src/backend/executor/nodeIndexscan.c#L520-L570) [execScan.h#ExecScanExtended](../../../raw/postgres-18/src/include/executor/execScan.h#L160-L224) PostgreSQL's cost model conservatively charges each InitPlan as if it runs once even though the executor may run it later or not at all.[subselect.c#SS_compute_initplan_cost](../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L2301-L2336)

An indexed comparison is different. If the qual is securely promotable and its table-side operand, collation, operator family, and nonvolatile comparison side match an index, a value with no Vars from the indexed table can already be an index runtime key.[indxpath.c#match_clause_to_index](../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L2586-L2629) [indxpath.c#match_opclause_to_indexcol](../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L2903-L3014) [indxpath.c#is_pseudo_constant_for_index](../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L4502-L4529) PostgreSQL evaluates that key when the scan starts and again on a rescan. On an exact scan, the bare helper in that index condition is therefore not called for every candidate tuple.[nodeIndexscan.c#ExecIndexBuildScanKeys](../../../raw/postgres-18/src/backend/executor/nodeIndexscan.c#L1245-L1305) [nodeIndexscan.c#ExecReScanIndexScan](../../../raw/postgres-18/src/backend/executor/nodeIndexscan.c#L520-L570) If an index access method reports a lossy match, however, `IndexScan` and `IndexOnlyScan` re-evaluate the original qual for each fetched tuple; a bare helper in that recheck can repeat, while an InitPlan parameter reuses its stored value.[nodeIndexscan.c#lossy-recheck](../../../raw/postgres-18/src/backend/executor/nodeIndexscan.c#L131-L148) [nodeIndexonlyscan.c#lossy-recheck](../../../raw/postgres-18/src/backend/executor/nodeIndexonlyscan.c#L215-L226) The wrapper may therefore save no call for one exact scan, but can avoid helper calls during lossy rechecks and recalculation of a bare runtime key across rescans because the uncorrelated InitPlan value remains in the execution's `PARAM_EXEC` slot.[subselect.c#InitPlan-rewind-boundary](../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L553-L562)

Wrapping can also worsen estimates. For ordinary equality selectivity, PostgreSQL applies `estimate_expression_value()` to the non-table side, and that estimation mode may execute a bare `STABLE` function and reduce it to a `Const`.[selfuncs.c#get_restriction_variable](../../../raw/postgres-18/src/backend/utils/adt/selfuncs.c#L5175-L5221) [clauses.c#estimate_expression_value](../../../raw/postgres-18/src/backend/optimizer/util/clauses.c#L2379-L2411) When the statistics security check permits value comparisons, the constant branch can match most-common values.[selfuncs.c#var_eq_const-MCV](../../../raw/postgres-18/src/backend/utils/adt/selfuncs.c#L325-L444) [selfuncs.c#statistics-security-check](../../../raw/postgres-18/src/backend/utils/adt/selfuncs.c#L6236-L6260) The wrapped form is a not-yet-known `PARAM_EXEC`; expression estimation substitutes only eligible bound `PARAM_EXTERN` values.[clauses.c#parameter-substitution](../../../raw/postgres-18/src/backend/optimizer/util/clauses.c#L2438-L2525) For a non-unique expression with statistics, the non-constant equality branch averages the non-null fraction over the estimated distinct values and caps that estimate by the largest most-common-value frequency. Unique expressions and no-statistics cases take separate branches.[selfuncs.c#eqsel-Const-vs-non-Const](../../../raw/postgres-18/src/backend/utils/adt/selfuncs.c#L244-L290) [selfuncs.c#var_eq_non_const](../../../raw/postgres-18/src/backend/utils/adt/selfuncs.c#L469-L545) On a skewed column, losing that value-specific estimate can change the chosen plan. A runtime parameter also generally cannot prove a value-dependent partial-index predicate at planning time.[indxpath.c#check_index_predicates](../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L3921-L4048) [indices.sgml#partial-index-parameters](../../../raw/postgres-18/doc/src/sgml/indices.sgml#L983-L1008)

Do not use this wrapper merely to suppress calls to a truthfully `VOLATILE` function. InitPlan conversion checks correlation and sublink type, not function volatility, so `(SELECT volatile_helper())` can still become an InitPlan. That changes observable results, errors, or side effects from per-needed-row behavior to lazy zero-or-one behavior; the resulting `Param` can even qualify as an index comparison value although the bare volatile call cannot.[subselect.c#scalar-InitPlan](../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L376-L411) [indxpath.c#is_pseudo_constant_for_index](../../../raw/postgres-18/src/backend/optimizer/path/indxpath.c#L4502-L4529) [xfunc.sgml#VOLATILE-semantics](../../../raw/postgres-18/doc/src/sgml/xfunc.sgml#L1621-L1667) The in-tree plan test confirms that an uncorrelated `(SELECT random())` can appear under one InitPlan.[subselect.sql#volatile-scalar-sublink](../../../raw/postgres-18/src/test/regress/sql/subselect.sql#L631-L633) [subselect.out#volatile-InitPlan](../../../raw/postgres-18/src/test/regress/expected/subselect.out#L1173-L1185) Conversely, an `IMMUTABLE` call with constant arguments can be folded during planning; a saved plan can then reuse that folded value, so the wrapper does not guarantee one helper call on every execution.[clauses.c#evaluate_function](../../../raw/postgres-18/src/backend/optimizer/util/clauses.c#L4488-L4500) [xfunc.sgml#saved-plan-IMMUTABLE-hazard](../../../raw/postgres-18/doc/src/sgml/xfunc.sgml#L1677-L1689) Function volatility must describe the helper truthfully; it is not a tuning switch.

Only the scalar subquery's target expression becomes the InitPlan output parameter.[primnodes.h#EXPR_SUBLINK](../../../raw/postgres-18/src/include/nodes/primnodes.h#L963-L1003) [subselect.c#EXPR_SUBLINK-target](../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L397-L411) For example, `(SELECT auth.jwt()) ->> 'claim'` stores the JSON result but leaves extraction in the outer expression, whereas `(SELECT auth.jwt() ->> 'claim')` places both operations in the InitPlan. Outside an index runtime key or another one-time placement, that outer work can still repeat with a residual filter.[execExprInterp.c#ExecEvalParamExec](../../../raw/postgres-18/src/backend/executor/execExprInterp.c#L3056-L3070) [execExprInterp.c#expression-evaluation](../../../raw/postgres-18/src/backend/executor/execExprInterp.c#L928-L939)

Wrapping does not grant `EXECUTE`, change which function the subquery calls, or alter that function's `SECURITY INVOKER`/`SECURITY DEFINER` mode or catalog `LEAKPROOF` declaration.[subselect.c#EXPR_SUBLINK-target](../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L397-L411) [execExpr.c#ExecInitFunc-ACL](../../../raw/postgres-18/src/backend/executor/execExpr.c#L2703-L2718) [create_policy.sgml#policy-expression-rights](../../../raw/postgres-18/doc/src/sgml/ref/create_policy.sgml#L727-L739) [create_function.sgml#LEAKPROOF](../../../raw/postgres-18/doc/src/sgml/ref/create_function.sgml#L356-L378) [create_function.sgml#SECURITY-INVOKER-DEFINER](../../../raw/postgres-18/doc/src/sgml/ref/create_function.sgml#L405-L419) Wrapping also does not automatically make the enclosing RLS qual leakproof. In the uncorrelated zero- or constant-argument form here, the helper has no current-level table `Var` beneath it; the comparison operator around `user_id` controls whether that `Var` is passed to a leaky function both before and after sublink replacement. That classification controls secure promotion at nonzero security levels.[clauses.c#contain_leaked_vars](../../../raw/postgres-18/src/backend/optimizer/util/clauses.c#L1252-L1324) [restrictinfo.c#compute-leakproof](../../../raw/postgres-18/src/backend/optimizer/util/restrictinfo.c#L118-L137) [restrictinfo.c#restriction_is_securely_promotable](../../../raw/postgres-18/src/backend/optimizer/util/restrictinfo.c#L415-L434)

A general scalar subquery that returns no row produces NULL, while more than one row raises a cardinality violation; the direct `(SELECT helper())` form normally produces exactly one row, whose value may itself be NULL. An RLS predicate admits a row only when its final expression is true, so a NULL comparison does not pass.[nodeSubplan.c#scalar-InitPlan-cardinality](../../../raw/postgres-18/src/backend/executor/nodeSubplan.c#L1125-L1240) [ddl.sgml#RLS-true-only](../../../raw/postgres-18/doc/src/sgml/ddl.sgml#L2643-L2655) PostgreSQL charges each InitPlan's startup plus per-call cost to the final paths, and an InitPlan that is not parallel-safe removes partial paths and parallel consideration.[subselect.c#SS_charge_for_initplans](../../../raw/postgres-18/src/backend/optimizer/plan/subselect.c#L2234-L2336) Core PostgreSQL 18 does not define `auth.uid()` or `auth.jwt()`, so their volatility, parallel safety, cost, internal token caching, security mode, and side effects must be checked in the installed definitions; that boundary remains under [Open Questions](#open-questions).

## Open Questions

- “All fixes” has no repository-defined taxonomy. This page uses the broad rule stated above and found no further change within it. A stricter primary-purpose-only taxonomy would omit some RLS-dependent `run_as_owner`, dump/upgrade, and SQL-function plan-cache changes; a feature inventory would instead add independent RLS-facing additions such as `security_invoker` views, `createuser --bypassrls`, the original `run_as_owner` feature, and `--no-policies`. In particular, `66ddac6982c` is the separate CVE-2026-2004 restriction on non-built-in selectivity estimators, not an RLS-specific companion fix.
- The same-effective-role authorization result is source-backed and reproduced, but the pinned source contains no comment or test saying whether retaining the prior policy set or bypass decision is intentional. Until that is resolved outside this evidence base, long-lived sessions that change membership edges, bypass attributes, superuser status, or current-database ownership need a fresh session, statement re-prepare, or session-local `DISCARD PLANS` before relying on the new authorization state.
- The hook API has no invalidation callback, and hook expressions are copied into the rewritten tree.[rowsecurity.h#hook-API](../../../raw/postgres-18/src/include/rewrite/rowsecurity.h#L37-L47) [rowsecurity.c#hook-callers](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L608-L653) [rowsecurity.c#copy-hook-visibility-quals](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L716-L753) [rowsecurity.c#copy-hook-write-checks](../../../raw/postgres-18/src/backend/rewrite/rowsecurity.c#L828-L870) It follows that an extension whose hook output changes with extension state must arrange plan invalidation or re-prepare, but the static in-tree hook test does not verify that dynamic case.[test_rls_hooks.c#hooks](../../../raw/postgres-18/src/test/modules/test_rls_hooks/test_rls_hooks.c#L32-L162)
- Core PostgreSQL 18 does not define the example helpers `auth.uid()` or `auth.jwt()`. Their volatility, parallel safety, function cost, selectivity support, security mode, side effects, and whether their own implementation caches a parsed token remain outside this evidence base.
- Exact first-minor-release and complete backpatch matrices are not asserted because the repository has no pinned PostgreSQL 15 or 16 checkouts, the pinned PostgreSQL 17 checkout has no tags or cross-branch refs, and the PostgreSQL 14 checkout has locally unavailable promisor objects. The release-based scope needs only the locally verified PostgreSQL 14.0 baseline and equivalent-commit ancestry.
